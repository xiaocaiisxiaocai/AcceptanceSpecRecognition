## Context
业务需要将“严格复用”从“智能填充任务快照来源”扩展出第二种来源模式：用户上传的人工已回复文档。新能力需要独立菜单和独立权限，但底层校验规则与文档写回逻辑应尽量复用现有严格复用基础设施。

## Goals / Non-Goals
- Goals:
  - 支持从已回复 `docx/xlsx` 来源文档批量回复同模板目标文件
  - 支持多表格配置与本地多目标上传
  - 复用现有严格判定和写回逻辑
  - 保持和智能填充后的严格复用能力解耦
- Non-Goals:
  - 不引入 AI、匹配或语义检索
  - 不支持跨格式回复
  - 不转成长期模板管理

## Architecture
- `BatchReplyController`
  - 负责接收 HTTP 上传、权限校验和响应包装
- `BatchReplyAppService`
  - 负责预检、执行、下载编排
- `BatchReplySessionService`
  - 负责临时文件保存、来源回复值抽取和会话读写
- Shared collaborators
  - `DocumentTableAccessService`
  - `MatchingResultWriteBackService`
  - 文件存储服务

## Data Flow
1. 前端上传来源文件和目标文件，并提交表格配置。
2. 服务端从来源文件提取 `项目/规格/验收/备注`，建立 `sessionId`。
3. 服务端逐个目标文件按“严格复用”规则预检，返回可执行清单与差异原因。
4. 用户确认执行后，服务端再次复检并写回目标文件。
5. 单文件直接下载，多文件打包 zip。

## Key Decisions
- 独立来源模型：
  - 不复用 `MatchingFillTask` 快照作为批量回复来源，避免语义耦合。
- 规则复用：
  - 沿用现有严格复用的“文件类型、列配置、数据区行数、项目+规格顺序”判定标准。
- 临时存储：
  - 来源文件、目标文件和执行产物按临时文件存储，不写入正式业务主表。
- 权限独立：
  - `batch-reply` 作为独立资源配置菜单、页面和按钮权限。

## Risks
- Word 与 Excel 的读取和写回差异可能导致两端行为不一致。
- 批量上传需要控制临时文件生命周期，避免长期堆积。
- 多表格配置错误时，失败原因必须足够具体，否则用户难以修正。

- API 集成测试覆盖预检失败、执行成功、下载结果
- 前端构建通过并覆盖权限与交互回归
