## Context

验收规格匹配是高风险的业务判定流程，既要求支持“多语义表达仍能召回正确候选”，又要求“关键参数、型号、品牌、方向条件不能错”。现有 Embedding 主导链路天然偏向语义接近，对数值、区间、单位、编号和实体同一性缺乏足够强的约束表达能力。

现有仓库内已经存在：

- Embedding 召回能力
- 文本预处理 pipeline
- LLM 复核与提示词模板管理基础设施
- 多阶段重排的第一版实现雏形

本次变更不再做“单阶段兼容增强”，而是直接升级为统一的证据驱动匹配架构。

## Goals / Non-Goals

- Goals:
  - 统一匹配引擎为固定多阶段流程，移除 `SingleStage`
  - 让关键字段冲突先于文本语义参与裁决
  - 保留 Embedding 对多语义表达的召回能力
  - 将业务知识改为配置化，而不是散落在代码和 prompt 中
  - 仅对高歧义样本触发 LLM 复核，并保证复核失败时默认保守
- Non-Goals:
  - 不在本次变更中引入全量 LLM 主裁决
  - 不在本次变更中覆盖所有行业术语；首版只覆盖高价值且可稳定解析的字段类型
  - 不要求本次变更一次性提供完备的后台词典管理 UI；允许先复用现有配置源与提示词模板管理能力

## Decisions

### Decision: 使用统一的六阶段匹配流水线

匹配引擎固定按下列顺序执行：

1. 文本预处理
2. Embedding TopK 召回
3. 结构化证据生成
4. 硬冲突过滤
5. 证据重排
6. 高歧义 LLM 复核与自动采用门禁

其中 Embedding 只负责“召回可能正确的候选”，不再单独决定最终高置信结果。

### Decision: 引入统一证据模型而非继续堆叠分数项

每个候选在进入最终排序前必须产出 `MatchEvidence`，至少包含：

- `NumericConstraints`
  - 字段语义槽位、运算符、区间、单位、归一化数值、关系类型
- `Identifiers`
  - 型号、料号、图号、版本号等
- `Entities`
  - 品牌、公司、事业部、部门等实体及标准名、关系类型
- `DirectionTerms`
  - 输入/输出、左/右、投板/收板等方向词
- `BooleanConstraints`
  - 有/无、允许/禁止、必须/无需等条件
- `SemanticSignals`
  - Embedding 分、项目文本接近度、规格文本接近度、关键词覆盖率

### Decision: 硬冲突优先于文本相似

下列场景一旦形成明确冲突，直接禁止高置信自动采用：

- 数值约束冲突
- 型号/料号冲突
- 方向词或布尔条件冲突
- 同语义槽位下的品牌/单位实体明确不同

若结构化解析无法达到冲突判定置信度，则不做硬杀，而是进入高歧义路径。

### Decision: 业务知识配置化

以下内容不得散写死在代码逻辑中，应从可配置源加载：

- 品牌/组织别名字典
- 单位定义与换算规则
- 冲突词对、方向词、布尔条件词表
- 关键字段槽位与识别规则
- 自动采用门槛与歧义阈值
- LLM 复核 Prompt 模板

首版实现允许配置源落在数据库、受控 JSON 配置或现有模板配置体系中，但必须具备可替换能力，避免代码硬编码。

### Decision: LLM 只做高歧义复核

LLM 不参与常规候选排序，只在以下情况下触发：

- Top1 / Top2 证据接近
- 存在 `Overlap`、`ParentChild`、`PossiblyRelated` 等边界关系
- 结构化证据不能直接放行，也不能直接拒绝

LLM 输入应为结构化证据摘要，而非裸文本自由判断。若样本进入 LLM 复核流程但失败或超时，则最终状态为“需要人工确认”，不得自动采用。

### Decision: UI 从“策略切换”改为“决策透明”

智能填充界面不再展示 `SingleStage / MultiStage` 切换。前端重点展示：

- 最佳候选的最终决策状态
- 关键证据摘要
- 是否存在硬冲突
- 是否进入高歧义复核
- 复核是否通过、失败或超时

## Risks / Trade-offs

- 结构化解析引入更多处理步骤，会增加部分匹配耗时
  - Mitigation: 只对 TopK 召回结果做证据提取与复核，不对全量候选做重处理
- 规则过严可能导致召回后的候选被过度拦截
  - Mitigation: 仅对高置信明确冲突做硬杀，不确定场景进入歧义复核或人工确认
- 配置化知识库初期覆盖不足可能影响品牌/组织别名识别
  - Mitigation: 首版先覆盖高频品牌、单位、冲突词，并保留逐步扩充能力
- API 与前端存在破坏性变更
  - Mitigation: 在同一版本内同步升级前后端与测试基线，并在发布说明中明确移除 `SingleStage`

## Migration Plan

1. 新增证据提取、冲突判定、决策门禁与复核编排模块
2. 将现有 Embedding 逻辑下沉为召回阶段
3. 移除前后端 `SingleStage` 策略切换与兼容分支
4. 更新匹配结果 DTO，使其输出证据、冲突、歧义和复核状态
5. 同步调整前端配置页、预览页、详情弹窗与执行填充流程
6. 补齐典型正反例测试集，重点覆盖数值、型号、品牌、方向词与复核超时场景

## Open Questions

- 首版配置源是否直接复用现有数据库与提示词模板管理，还是同时引入独立的匹配策略配置表
- 首版是否需要在前端提供完整的词典维护入口，还是先以后台配置和数据库初始化为主
