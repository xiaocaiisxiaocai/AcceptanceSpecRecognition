## Context
现有 RBAC 组织关系模型允许一个用户关联多条 `AuthUserOrgUnit` 记录，并通过 `IsPrimary` 标识主组织；系统用户 API 和前端页面也同时暴露“关联组织列表”和“主组织”两个概念。这与已经确认的业务规则“一个用户只允许一个组织”不一致。另一方面，现有权限字典虽然有页面、按钮和 API 权限，但像“配置管理”“权限中心”这类菜单容器没有独立权限码，导航显隐只能间接依赖子页面权限。

## Goals / Non-Goals
- Goals:
  - 从数据库、API、认证上下文到前端表单统一为单组织模型
  - 为历史多组织和无组织用户提供确定性的迁移规则
  - 在不推翻现有权限表结构的前提下补齐菜单权限类型和种子
  - 让左侧导航容器菜单具备独立显隐控制能力
- Non-Goals:
  - 不调整组织树层级模型和组织维护页面本身
  - 不改变数据范围类型枚举，只调整用户组织来源
  - 不引入长期兼容字段或双写逻辑

## Decisions
- Decision: 保留 `AuthUserOrgUnits` 表，不新增 `SystemUsers.OrgUnitId`
  - Why: 当前仓储、数据范围计算和种子初始化都依赖关系表；本次目标是约束单组织，而不是重构模型。
- Decision: 通过数据迁移 + 唯一约束强制单组织
  - Why: 只改 DTO/接口无法防止后台或历史数据再次写入多组织；数据库必须提供硬边界。
- Decision: 历史多组织按固定规则裁剪
  - Rule:
    1. 若存在且仅存在一条 `IsPrimary = true` 记录，保留该条
    2. 否则按 `CreatedAt` 升序、`Id` 升序保留第一条
  - Why: 规则确定、可重复执行，并尽量贴近现有主组织语义。
- Decision: 历史无组织用户迁移到公司根组织
  - Why: 根组织是现有系统中最保守、最稳定的默认组织上下文。
- Decision: API、前端缓存与系统用户页面统一使用 `orgUnitId` / `orgUnitName`
  - Why: 用户明确要求彻底不再暴露组织数组；保留旧字段只会制造双重口径。
- Decision: 新增 `Menu` 权限类型，菜单节点使用独立 `menu:*` 权限码
  - Why: 菜单显隐和页面访问是两个层次，必须分开控制；否则容器菜单永远只能靠子页面权限间接推导。
- Decision: 保留页面权限用于实际页面访问控制
  - Why: 菜单可见不应天然等同于页面可访问，避免把导航逻辑和页面鉴权耦死。

## Risks / Trade-offs
- 风险: 迁移后少量用户会失去历史协作组织范围
  - Mitigation: 这是业务规则本身要求的纠偏；保留规则固定并通过迁移日志可审计。
- 风险: 数据范围服务当前显式依赖 `IsPrimary`
  - Mitigation: 统一改为读取唯一组织关系，把“主组织”解释彻底移除。
- 风险: 新增菜单权限后，已有非管理员角色如果未补齐权限，菜单可能全部隐藏
  - Mitigation: 种子初始化时为 `admin` 授予全部菜单权限，为 `common` 授予最小业务菜单权限，并补测试锁定。

## Migration Plan
1. 扫描 `AuthUserOrgUnits`，按“唯一主组织优先，否则最早记录优先”清洗每个用户的组织关系。
2. 为无组织用户补齐公司根组织关系。
3. 在 `AuthUserOrgUnits.UserId` 上增加唯一约束，形成数据库硬边界。
4. 后端 DTO、控制器、仓储查询、认证访问上下文和数据范围服务切换为单组织字段。
5. 权限类型、权限种子、权限字典和动态路由过滤补齐菜单权限。
6. 前端系统用户页、用户缓存和权限展示切换为单组织和菜单权限模型。
