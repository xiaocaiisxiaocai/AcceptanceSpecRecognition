## Context
当前匹配知识配置页和 API 直接使用运行时字典模型：
- 实体、单位、字段都按 `别名 -> 标准值` 存储与编辑
- 冲突词按 `左词 / 右词` 成对维护

这种模型虽然贴近程序内部实现，但对维护者不友好：
- 标准词本身也必须显式登记为自映射，形成 `a -> a`、`功率 -> 功率` 这类表项
- 同一标准值的多个别名分散在多行，难以整体审查
- 冲突词对无法表达“左侧一组同义词”对“右侧一组同义词”的业务语义

## Goals / Non-Goals
- Goals:
  - 将匹配知识配置改为面向业务用户的分组式维护模型
  - 隐藏运行时内部的自映射与配对展开细节
  - 保持运行时匹配能力和持久化兼容性，避免不必要的引擎重写
  - 让四类配置在页面语义上尽量统一
- Non-Goals:
  - 不改变匹配引擎对实体、字段、单位和冲突规则的最终裁决逻辑
  - 不引入新的匹配知识存储表结构
  - 不在本次变更中扩展新的匹配知识分类

## Decisions

### Decision: 将三类别名统一为“首项为标准值”的单列分组
- 实体别名改为 `实体组`
- 单位别名改为 `单位组`
- 字段别名改为 `字段组`

每行是一个组，支持 `、`、`，`、`,` 作为分隔符。首项为标准值，其余项都归一到首项。

示例：
- `ABB、abb、艾波比股份有限公司`
- `a、amp、amps`
- `功率、功耗、power`

保存时展开为运行时现有字典模型。例如 `a、amp、amps` 展开为：
- `a -> a`
- `amp -> a`
- `amps -> a`

### Decision: 冲突词采用“左右冲突组”而不是单组
冲突词与别名不同，表达的是“对立关系”而非“同义关系”。因此冲突词配置改为每行两个组：
- 左冲突组
- 右冲突组

示例：
- 左组：`输入、进料`
- 右组：`输出、出料`

保存时执行左右组笛卡尔展开，生成所有冲突词对：
- `输入 / 输出`
- `输入 / 出料`
- `进料 / 输出`
- `进料 / 出料`

### Decision: API 提供分组化作者视图，内部继续保留展开模型
为避免前端自己做复杂的聚合与冲突判断，匹配知识读取与保存 API 都以分组模型为主：
- 读取时由后端把当前生效的展开配置聚合为作者视图
- 保存时由后端校验作者视图并展开为运行时模型

这样前端和 AI 草稿导入都围绕统一的分组语义工作，运行时继续消费熟悉的展开结构。

### Decision: 分组校验优先于持久化
保存前执行以下校验：
- 组内去空白、去重复
- 三类别名组必须至少有一个有效词项
- 同一个词不能归属到两个不同的实体组 / 单位组 / 字段组
- 冲突组左右两侧都必须至少有一个有效词项
- 冲突组内部去重，展开后对称重复冲突对自动折叠

### Decision: 单位换算仍保持独立配置
本次“单位组”只覆盖单位别名归一化；单位换算系数继续单独维护，不合并进分组模型。

## Alternatives Considered

### 方案一：只改前端展示，前端自行展开与聚合
- 优点：后端改动较小
- 缺点：前端要承担冲突检测、分组聚合和兼容逻辑，易与后端实际运行时语义漂移

### 方案二：前后端都改为分组式作者视图
- 优点：语义统一，校验集中，前端更轻，便于后续 AI 导入与审计
- 缺点：需要调整 API DTO 与测试

结论：选择方案二。

## Risks / Trade-offs
- 从旧字典视图聚合到分组视图时，无法总是精确恢复用户当初的录入顺序，只能基于标准值和现有映射稳定聚合。
- AI 草稿目前是单条候选，导入分组视图时需要定义合并策略，否则会出现“同一标准值分散到多组”的体验问题。
- 冲突组笛卡尔展开后规则数量可能增多，需要避免重复组合污染最终持久化结果。

## Migration Plan
1. 后端新增分组 DTO，并实现“分组视图 <-> 展开模型”的双向转换。
2. 读取现有数据库配置时，按标准值聚合为实体组、单位组、字段组，以及左右冲突组。
3. 前端页面切换到分组式交互模型。
4. AI 草稿导入改为按组语义合并。
5. 保留原有运行时消费的展开模型，避免影响匹配引擎。

## Open Questions
- 旧数据聚合为分组视图时，组内显示顺序是否统一采用“标准值优先，其余按长度和字典序稳定排序”？
- AI 草稿导入时，如候选标准值已存在对应组，是否总是自动并入现有组？
