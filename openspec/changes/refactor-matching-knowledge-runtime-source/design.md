## Context
当前匹配知识配置采用“系统内置规则 + 自定义扩展规则 + 最终生效规则”的三层模型。配置文件中的默认规则在运行时始终参与合并，前端页面和 API 也围绕 `builtIn / custom / effective` 三层结构组织。

这个模型在功能上可用，但在实际运维和开发中暴露出几个问题：

- 用户在页面上删除某些默认规则后，这些规则仍可能由于运行时内置层继续生效，形成“界面已删、运行时仍在”的认知偏差。
- 默认规则中存在部分当前业务并不会用到的条目，管理员无法真正移除它们。
- AI 草稿生成、配置页展示、后端 Provider 和匹配运行时都需要理解分层合并语义，增加了复杂度。
- 对开发者而言，匹配知识缺少单一事实来源，不利于复现问题、迁移环境和审计配置变化。

因此，本次调整希望将默认内置从“运行时基线”改为“初始化种子”，并明确数据库是运行时唯一知识来源。

## Goals / Non-Goals

### Goals
- 将数据库中的匹配知识配置收敛为运行时唯一事实来源。
- 允许管理员真正新增、编辑和删除所有当前生效规则。
- 保留默认规则模板，但仅用于首次初始化和显式恢复默认。
- 降低配置页、API、草稿生成和运行时 Provider 的语义复杂度。
- 保持当前数据库单例表模型，避免一次性引入更大规模的数据结构迁移。

### Non-Goals
- 本次不将单例 JSON 配置表拆分为逐条知识项明细表。
- 本次不引入匹配知识版本管理、草稿版本、审批流或历史回滚 UI。
- 本次不改变匹配主引擎的证据驱动判定逻辑。
- 本次不自动将 AI 草稿直接写入正式配置。

## Decisions

### Decision: 数据库配置作为唯一运行时来源
- 运行时匹配链路只读取数据库中的当前匹配知识配置。
- `appsettings` 中的默认匹配知识不再参与每次请求的运行时合并。
- `ConfigurationMatchingKnowledgeProvider` 直接从数据库读取当前配置并转换为领域模型。

### Decision: 默认规则改为初始化种子与恢复模板
- 系统首次启动且数据库中不存在匹配知识配置时，将默认种子导入数据库。
- 后续只有用户显式执行“恢复默认配置”时，才重新使用默认种子覆盖数据库内容。
- 用户显式清空当前配置后，系统保持清空状态，不在重启后自动恢复默认。

### Decision: API 语义改为单层完整配置
- `GET /api/matching-knowledge` 返回当前完整配置。
- `PUT /api/matching-knowledge` 保存当前完整配置。
- 原“重置默认”拆分为明确动作：
  - 清空当前配置
  - 恢复默认种子

### Decision: 前端页面取消运行时分层展示
- 页面只展示一份当前数据库配置。
- 不再展示“系统内置规则”“自定义扩展规则”“最终生效规则”三块运行时视图。
- 默认模板的概念通过“恢复默认配置”入口体现，而不是常驻展示为运行时一层。

## Risks / Trade-offs

### Risk: 用户误删默认规则后影响匹配效果
- **Mitigation**:
  - 提供“恢复默认配置”按钮。
  - 后续可补充“导出/导入配置”能力，支持手工备份与恢复。
  - 可在前端对“清空当前配置”增加二次确认和风险提示。

### Risk: API 返回结构变化影响前端与测试
- **Mitigation**:
  - 在同一变更中同步修改前端 API 封装和页面实现。
  - 补充 API 集成测试和前端交互验证。
  - 在变更说明中明确这是行为调整。

### Risk: 现有 AI 草稿去重逻辑仍依赖旧分层视图
- **Mitigation**:
  - 将草稿生成服务的“当前有效配置”来源切换为数据库当前配置。
  - 保证草稿比对和正式运行时使用同一份配置语义。

### Trade-off: 继续使用单例 JSON 表
- **Pros**:
  - 改造范围小，能快速完成语义收敛。
  - 不需要额外的数据迁移复杂度。
- **Cons**:
  - 逐条审计、差异回溯和知识项级别管理能力仍较弱。
- **Decision**:
  - 当前先不拆表，后续若需要版本化、审批和逐条审计，再演进到明细表结构。

## Migration Plan
1. 修改匹配知识 DTO、Controller 和 Provider，去掉运行时分层语义。
2. 重构 `MatchingKnowledgeComposition`，保留标准化、序列化和种子构建逻辑，移除运行时合并职责。
3. 调整 `MatchingKnowledgeBootstrapper`：空库时导入默认种子，而不是写空配置。
4. 调整前端 API 与页面，改成单一配置视图。
5. 调整 AI 草稿生成链路的当前配置读取来源。
6. 补充测试，验证：
   - 删除默认规则后不会被隐式回补
   - 清空后保持清空
   - 恢复默认后正确回填
   - 服务重启后仍保持数据库配置

## Open Questions

- 是否需要在本次同步提供“导出/导入匹配知识配置”接口？
- 默认种子是否继续来自 `appsettings`，还是改为单独的 JSON 模板文件以便版本管理？
