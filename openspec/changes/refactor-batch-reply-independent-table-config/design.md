## Context
现有批量回复是“来源文件上传 -> 来源表配置 -> 目标文件上传 -> 整批预检 -> 执行下载”的线性流程。它默认来源配置可以直接复用于目标文件，导致一旦来源与目标在 `Sheet/表格` 级别存在结构差异，用户就无法完成配置。

这次改动不是简单补一个字段，而是把批量回复调整为“来源与目标都逐表配置”的独立工作流，同时保留“只复制验收/备注、不调用 AI”的严格边界。

## Goals / Non-Goals
- Goals:
  - 来源文件支持逐表独立行配置与列映射
  - 目标文件支持逐文件、逐表独立行配置与列映射
  - 每个目标表允许显式选择来源表
  - 目标表支持即时预览，不再依赖整批预检门禁
  - 执行时以“单个目标文件配置完整”为最小执行单元
- Non-Goals:
  - 不引入 AI、模糊匹配或长期模板管理
  - 不自动推断重复键的处理策略
  - 不修改现有文档写回器的“仅改单元格内容”边界

## Architecture
- `BatchReplySessionService`
  - 负责保存来源文件元数据、来源逐表配置、目标文件临时信息与目标逐表配置快照
- `BatchReplyAppService`
  - 负责来源表预览、目标表预览、执行前校验、逐文件执行与执行历史写入
- `DocumentTableAccessService`
  - 继续负责基于行配置/列映射抽取来源项与目标项，Word/Excel 共用列映射语义
- `MatchingResultWriteBackService`
  - 继续负责按“目标表 -> 目标行 -> 单元格值”写回，不删行不删列

## Data Model Changes
- 将“批量回复表配置”拆成两层：
  - 来源表配置：描述来源文件每张表的行配置与列映射
  - 目标表配置：描述目标文件中每张表的行配置、列映射、来源表选择与是否参与执行
- 每个目标表配置都必须显式包含：
  - `targetTableIndex`
  - `sourceTableIndex`
  - `project/specification/acceptance/remark` 列索引
  - `headerRowStart/headerRowCount/dataStartRow`
  - `filterEmptySourceRows`

## Data Flow
1. 用户上传来源文件后，在“来源配置”Tab 内逐表配置并预览。
2. 用户上传多个目标文件后，在“目标配置”Tab 内按文件进入子 Tab，为每个目标表选择来源表并配置行/列映射。
3. 用户点击某个目标表的预览时，服务端按“目标表配置 + 来源表配置”抽取数据，并以 `项目 + 规格` 为键生成预览结果。
4. 用户执行时，系统只处理“该目标文件内所有参与表都配置完整且校验通过”的文件。
5. 写回仍只更新验收列和备注列；执行历史保留文件、Sheet/表与目标行级结果。

## Key Decisions
- 显式来源表选择优先于按索引猜测：
  - 默认仍可带出同索引来源表，但最终以用户选择为准。
- 取消“整批预检门禁”：
  - 预览结果直接承担校验反馈职责，避免用户在来源/目标都逐表独立配置后再重复做整批预检。
- 保持 `项目 + 规格` 键匹配：
  - 行顺序允许不同；重复键直接报错并要求人工处理。
- Word 复用列映射模型：
  - Word 也允许按列配置项目/规格/验收/备注列，而不是沿用固定列假设。

## Risks / Trade-offs
- 页面状态显著增多，必须避免不同目标文件/表之间的配置串写。
- 来源表和目标表均可单独配置后，接口模型会比当前更复杂，前后端需要同步升级。
- 预览从“整批”下沉到“逐表”后，执行前仍需做最小必要复检，避免用户改配置后直接执行脏状态。

## Migration Plan
1. 先扩展 DTO 和会话模型，允许表达来源配置与目标配置。
2. 先用失败测试锁定新的预览/执行语义，再替换旧的预检编排。
3. 最后重构前端页面为多 Tab 模式，并接入新接口。

## Open Questions
- 本轮默认保持“一个目标文件内只执行被勾选参与的表”；未参与的表既不校验也不写回。
