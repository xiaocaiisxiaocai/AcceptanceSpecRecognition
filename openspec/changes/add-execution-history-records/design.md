## Context
智能填充当前通过 `MatchingFillTask` 保存临时快照，批量回复通过 manifest 保存临时下载信息。这些数据足够支持下载与严格复用，但不足以支持“任务级历史查询 + 文件级/Sheet级逐行复盘”。

用户已经明确：
- 智能填充与批量回复都要纳入记录。
- 列表按“一次任务一条”展示。
- 批量任务进入后再看每个文件。
- 文件内按 Sheet 分 Tab。
- 每个 Sheet 直接展示逐行记录，不再要求点击行详情。
- 每一行都要展示置信度百分比与人工选择标记。
- 未匹配、跳过、未采用、已采用都要保留。

## Goals / Non-Goals
- Goals:
  - 为智能填充与批量回复建立统一的可查询执行记录。
  - 保持任务列表查询走结构化摘要字段，避免靠扫描 JSON 汇总。
  - 在详情中完整保留文件、Sheet 与逐行结果。
- Non-Goals:
  - 不保留候选列表与二级详情弹窗。
  - 不在本次变更中把逐行明细完全拆成独立关系表。
  - 不将现有严格复用临时会话改造成长期模板系统。

## Decisions
- Decision: 新增一张执行记录主表，保存任务级汇总字段与详情 JSON。
  - Why: 相比“全 JSON”更利于分页与筛选；相比“三层拆表”实现成本更低。
  - Alternatives considered:
    - 全本地 JSON 文件：多实例与清理场景不可靠，不适合作为正式查询来源。
    - 三层拆表：查询能力最强，但当前需求主要是任务级列表 + 单任务详情，复杂度偏高。

- Decision: 明细 JSON 存数据库，不存本地 JSON 文件。
  - Why: 避免本地文件丢失、清理误删和多实例不一致问题；权限控制与备份都更简单。

- Decision: 详情 JSON 统一按 `files[].sheets[].rows[]` 组织。
  - Why: 直接贴合前端“任务 -> 文件 -> Sheet -> 行记录”的展示层级，避免详情接口二次拼装。

- Decision: 行状态统一为 `unmatched`、`skipped`、`not-adopted`、`adopted`。
  - Why: 直接覆盖用户要求的四类结果，便于前后端统一枚举与统计。

- Decision: 行级保留 `confidencePercent` 与 `isManualSelected`。
  - Why: 用户明确要求每条记录都显示置信度，并将人工选择单独成列。

## Risks / Trade-offs
- 详情 JSON 会随着文件行数增长而增大。
  - Mitigation: 列表只读摘要字段；详情按任务单条读取；面向“几百行”规模当前可接受。
- 智能填充与批量回复需要产出统一的行记录模型。
  - Mitigation: 在 Application 层增加统一的执行记录组装逻辑，避免控制器和页面各自拼装。
- 现有临时快照与新正式记录可能重复存储部分信息。
  - Mitigation: 保留快照用于下载/严格复用，正式记录只负责查询与展示，职责明确分离。

## Migration Plan
1. 新增执行记录主表与必要索引。
2. 扩展智能填充与批量回复执行完成后的持久化流程。
3. 新增记录查询接口。
4. 新增前端记录列表与详情页面。
5. 补充测试覆盖任务持久化、查询和详情展示契约。
