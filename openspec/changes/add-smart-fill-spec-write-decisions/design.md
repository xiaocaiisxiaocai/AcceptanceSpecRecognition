## Context

智能填充预览已经把记录划分为“100%精准直达”“AI/普通可填充”“需要确认”“不建议填充”和“无匹配”。现有回填弹窗只收集手动编辑过验收或备注的记录，并通过 `SpecId` 是否存在隐式决定更新或新增；更新时也只修改验收和备注。

本次需要把“是否写入验收规格库”从隐式行为改为用户显式决策，同时保证该决策不改变当前文件的填充选择。

## Goals / Non-Goals

- Goals:
  - 一次展示本次执行涉及的全部相关候选，而不是逐条弹窗。
  - 明确区分覆盖、增加和跳过写库，并保持跳过后继续填充文件。
  - 覆盖时更新项目、规格、验收标准和备注四个业务字段。
  - 保持现有数据权限、业务归属和 Embedding 缓存一致性规则。
- Non-Goals:
  - 不改变匹配算法、置信度分桶或“需要确认”的人工采用门禁。
  - 不让“100%精准直达”“不建议填充”或“无匹配”自动进入写库决策。
  - 不增加数据库表或修改验收规格表结构。

## Decisions

### Decision: 复用现有回填 API，并增加显式决策字段

扩展 `SmartFillSpecBackfillItem`，增加显式写入决策 `overwrite | create | skip`。新前端始终发送显式决策；旧客户端未发送该字段时仍按现有 `SpecId` 规则处理，以保持兼容。

备选方案是把写库决策并入文件填充 API。该方案能减少一次请求，但会扩大已有填充幂等、文件锁、执行历史和事务边界，当前需求不需要修改这些核心路径，因此不采用。

### Decision: 候选来源按“实际参与本次填充”收口

前端从所有 Sheet 的当前预览和持久化选择中汇总候选，只纳入：

- 已选择参与本次文件填充；
- 存在当前最佳匹配；
- 当前分类为“AI/普通可填充”或“需要确认”；
- “需要确认”记录已经通过既有人工采用门禁。

弹窗使用单个可滚动表格完整呈现候选，不按记录逐个打开，也不因当前页面筛选或分页漏掉其他 Sheet 的记录。

### Decision: 写库决策默认安全且可批量操作

每行默认 `skip`。用户可逐行选择，也可使用“全部覆盖 / 全部增加 / 全部跳过”。弹窗同时展示数据库已有四字段与当前行四字段，帮助用户判断。

### Decision: 三种决策与文件填充相互独立

- `overwrite`: 必须提供可访问的匹配规格 ID；完整更新项目、规格、验收标准、备注并使旧 Embedding 缓存失效。
- `create`: 不修改匹配记录，在当前客户、机型、制程与组织归属下新增当前行四字段。
- `skip`: 不产生数据库写入。

无论三种决策为何，当前行是否写入目标文件仍由既有填充选择决定；`skip` 不会从文件填充请求中移除该行。

## Risks / Trade-offs

- 风险：大量记录逐行选择成本较高。缓解：默认跳过并提供三个批量动作。
- 风险：覆盖项目或规格后旧向量失效。缓解：沿用现有缓存删除机制，并补充覆盖四字段的集成测试。
- 风险：新增可能产生业务上相似的多条规格。该行为是用户明确选择的结果，不增加唯一约束；弹窗必须同时展示原值和新值。
- 风险：写库与文件填充仍是两个顺序请求；若写库成功后文件填充失败，已写入主数据不会自动回滚。页面必须显示真实错误，用户重试文件填充时可选择“全部跳过”避免重复写库。

## Migration Plan

1. 先扩展后端契约并保持未传决策字段时的旧行为。
2. 前端切换为显式决策并汇总全部相关候选。
3. 验证覆盖、增加、跳过及混合批次后，再移除前端旧的隐式选择逻辑。
4. 无数据库迁移；源码回退后旧客户端与旧请求仍可继续工作。
