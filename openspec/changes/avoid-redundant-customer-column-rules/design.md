## Context

`ColumnMappingRules` 允许全局规则和客户规则同时存在。当前唯一约束只保证同一作用域内不重复，`SmartConfigurationLearningService` 也只查询当前客户作用域，因此全局规则已经覆盖相同匹配词时仍会写入客户级 `Learned` 规则。有效规则读取会优先选择客户规则，掩盖了存储层重复。

## Goals / Non-Goals

- Goals:
  - 相同匹配词、相同目标字段已经由启用全局规则覆盖时，不保存客户级学习副本。
  - 保留真正的客户差异、人工配置和显式禁用语义。
  - 全局提升后清理冗余客户学习记录，并安全处理并发确认。
  - 清理现有历史冗余记录，不改变最终列映射结果。
- Non-Goals:
  - 不改变列映射规则 API、表结构或前端配置功能。
  - 不删除客户手动规则、禁用规则或不同目标字段的覆盖规则。
  - 不把正则规则仅凭文本相同视为安全覆盖。
  - 不改变结构模板的删除语义。

## Decisions

### Decision: 只把可证明覆盖的全局规则视为去重依据

全局规则必须满足以下条件才覆盖待学习客户规则：

- 规则已启用且 `CustomerId` 为空；
- 目标字段相同；
- 规范化匹配词相同；
- 匹配模式为 `Equals` 或 `Contains`。

`Regex` 即使文本相同也不自动清理客户规则，因为模式文本不等于其实际匹配集合，跨数据库迁移中也无法可靠复用运行时正则语义。

备选方案是只比较规范化匹配词和目标字段。该方案更简单，但可能把不能匹配实际表头的正则规则误判为覆盖，因此不采用。

### Decision: 客户覆盖和人工意图优先保留

全局规则映射到不同目标字段时，客户确认结果仍保存为客户级学习规则。来源为 `Manual` 的规则和任何禁用规则不参与自动删除，避免自动学习覆盖管理员意图。

### Decision: 学习、提升和清理使用同一匹配词锁

对规范化匹配词使用现有工作单元操作锁，将以下步骤放入同一串行化边界：

1. 检查启用全局覆盖；
2. 按需写入客户学习规则；
3. 判断是否达到全局提升阈值；
4. 提升成功后删除被覆盖的客户学习规则。

数据库唯一约束继续裁决跨实例的全局规则并发赢家；操作锁避免赢家清理后另一个请求又写回客户副本。

### Decision: 使用一次性迁移清理历史冗余数据

迁移只删除满足以下全部条件的客户规则：

- 来源为 `Learned` 且已启用；
- 客户规则匹配模式为自动学习产生的 `Equals`；
- 存在相同规范化匹配词、相同目标字段的启用全局规则；
- 全局规则匹配模式为 `Equals` 或 `Contains`。

迁移分别提供 MySQL 与 SQLite 兼容 SQL。该数据清理不可恢复原客户记录，但映射行为仍由对应全局规则提供；源码回退后不会丢失实际识别能力。

## Risks / Trade-offs

- 删除历史冗余记录后无法还原其创建时间等元数据。缓解：只删除可由启用全局规则完整替代的自动学习记录。
- 操作锁增加同一匹配词并发确认的串行等待。该锁粒度仅为规范化匹配词，不阻塞无关表头学习。
- 全局规则之后被管理员删除时，不会自动恢复历史客户副本。管理员删除全局规则本身就是显式行为；后续客户确认可重新学习。

## Migration Plan

1. 先通过回归测试锁定跳过、覆盖保护、提升清理和并发行为。
2. 部署代码与数据迁移，清理现有冗余客户学习规则。
3. 验证有效规则查询结果和智能识别行为保持一致。
4. 回退代码时保留全局规则；无需恢复已删除的冗余客户副本。
