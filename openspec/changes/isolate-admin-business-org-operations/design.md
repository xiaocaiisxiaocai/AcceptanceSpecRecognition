## Context

文件、验收规格与用户已经具备 `OwnerOrgUnitId` 或单组织归属，但管理员的 `All` 数据范围会在导入重复检测和智能填充候选查询中放开到全公司。仪表盘中的智能填充记录又缺少任务发生时的组织快照，只能按创建人的当前组织关系反推。

本次以源文件保存的业务归属作为任务唯一事实来源。页面选择只发生在上传前，文件保存成功后归属不可在当前流程中切换。

## Goals / Non-Goals

- Goals:
  - 管理员代某部门导入或智能填充时，数据、候选和统计始终归属同一部门。
  - 普通用户无法通过请求参数越权选择其他组织。
  - 智能填充预览、LLM 复核、最终重算与回填使用相同的组织范围。
  - 历史执行记录保持可读且统计口径兼容。
- Non-Goals:
  - 不改变管理员在基础数据和仪表盘上的公司级查看能力。
  - 不将执行历史列表从“本人记录”扩展为“部门共享记录”。
  - 不允许一个任务同时归属多个部门。
  - 不移动或批量重写已有文件和验收规格的组织归属。

## Decisions

### Decision: 上传文件绑定不可变业务归属

上传接口接受可选 `businessOrgUnitId`。公司存在有效下级组织时，管理员必须提交当前公司内有效的非公司级组织；尚未配置下级组织时自动使用管理员的根组织，以兼容既有单组织部署。普通用户缺省时自动使用其唯一组织，提交不同组织时返回 403。

文件保存成功后，后续业务接口不再接收独立的部门选择，而是读取 `WordFile.OwnerOrgUnitId`。这样可以避免预览、执行和重试之间的部门漂移。

Alternatives considered:

- 每个预览/执行请求都传部门：容易漏字段，并允许同一文件在不同阶段切换范围。
- 仅在前端过滤：无法防止直接调用 API 越权。

### Decision: 业务操作使用精确组织范围

服务端先使用调用者原始权限确认文件可访问，再把候选和写入范围收窄为文件的单一归属组织。管理员的 `All` 仅用于访问授权，不直接进入候选查询。

当前业务明确禁止跨部门，因此不自动包含所选节点的父级、兄弟或后代。需要在层级组织之间共享时，应另行定义明确规则。

### Decision: 执行历史保存组织快照

`ExecutionHistoryRecord.OwnerOrgUnitId` 保存智能填充执行时源文件的归属。新记录的仪表盘统计直接使用该字段；旧记录字段为空时，继续按创建人的当前有效组织关系兼容统计。

### Decision: 共用上传组件承载组织选择

数据导入与智能填充共用同一个紧凑组织选择区。管理员看到必选下拉框，普通用户看到只读归属提示。文件上传后控件锁定，移出当前流程后才可重新选择。

## Risks / Trade-offs

- 管理员尚未配置非公司级组织时只能形成公司级数据。
  - Mitigation: 页面明确显示“公司级归属”，并提示配置部门后新任务必须选择部门。
- 历史文件可能归属公司根组织。
  - Mitigation: 继续按历史归属执行，不隐式搬迁；管理员需要新的部门隔离任务时重新上传。
- 执行记录新增索引增加轻微写入成本。
  - Mitigation: 使用公司、归属组织、创建时间组合索引，换取仪表盘稳定查询。

## Migration Plan

1. 增加可空 `ExecutionHistoryRecords.OwnerOrgUnitId` 和查询索引。
2. 新执行记录开始保存文件归属；历史记录保持空值。
3. 仪表盘优先按组织快照过滤，空值使用旧用户组织关系回退。
4. 前后端同步发布，管理员上传开始要求选择业务归属。

## Rollback

回退代码时新增可空字段和索引可保留，不影响旧版本读取。若需要完整回退迁移，可删除索引和字段；新版本写入的归属快照不会影响执行记录其他数据。
