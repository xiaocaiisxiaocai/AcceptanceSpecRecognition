# Design: 智能结构列语义召回评估

## Context
当前智能结构识别已经支持前置行扫描、多行表头、确定性列映射规则、客户学习规则、结构健康检查、历史结构模板和 LLM 表头结构裁决。阶段 3 不应重做结构识别，而是补足“表头没有命中规则，但语义明显接近字段”的灰区。

## Goals / Non-Goals
- Goals:
  - 对未命中规则的表头给出 `Project / Specification / Acceptance / Remark / Unknown` 候选建议。
  - 让建议带来源、置信度和理由，便于人工确认和后续学习。
  - 保持确定性规则和客户学习规则为主路径。
  - 保证 AI 结果不能单独自动采用。
- Non-Goals:
  - 不让 AI 重选表头行或数据起始行。
  - 不新增缺项目导入入库能力。
  - 不把所有表格都交给 LLM 全量识别。
  - 不在第一版引入字段 Embedding 向量库。

## Decisions
- Decision: 第一版采用 LLM 列语义裁决，而不是 Embedding 字段召回。
  - Reason: 目标字段只有 4 个，Embedding 对 4 个标签做相似度阈值很难校准；LLM 更适合输出“不确定”和解释。
- Decision: 只对未映射表头和缺失关键字段时调用。
  - Reason: 确定性规则已覆盖的列不需要 AI 介入，避免成本和误覆盖。
- Decision: 语义召回结果以候选建议形式返回。
  - Reason: AI 结果可能把“验收方式”“验收标准”“确认结果”等混淆，必须保留人工确认门禁。
- Decision: 任一必需字段只靠语义召回补齐时，识别结果不得 `AutoApply`。
  - Reason: 自动采用必须由确定性规则、模板或用户确认支撑，AI 召回只降低人工选择成本。
- Decision: 复用现有 LLM 预算与超时，或在现有预算内细分列语义召回调用。
  - Reason: 避免为列召回新增独立成本入口。

## Candidate Flow
1. 规则识别表头和列映射。
2. 执行结构健康检查。
3. 若缺少规格列，或缺少验收列且存在未映射短表头，进入列语义召回候选阶段。
4. 组装输入：表名、表头列表、规则已识别字段、未映射表头、少量样例行、字段定义和禁止映射示例。
5. LLM 输出每个未映射表头的候选字段、置信度、理由和是否建议人工确认。
6. 服务端校验候选字段、重复列、越界列和置信度。
7. 结果回填为候选建议，并把表格保持为 `NeedConfirm`，等待用户确认后走现有学习规则。

## Risks / Trade-offs
- Risk: LLM 把方法列误判为结果列。
  - Mitigation: Prompt 明确区分“验收方式/方法”与“确认结果/OKNG/是否响应”，并用回归测试覆盖。
- Risk: 成本增加。
  - Mitigation: 仅在规则缺口和高价值候选表触发；复用文档级预算。
- Risk: 响应契约膨胀。
  - Mitigation: 新增字段保持可选，不改变既有列索引字段含义。
- Risk: AI 建议被误认为自动结果。
  - Mitigation: 响应中显式标记 `source=SemanticRecall`，并保持 `NeedConfirm`。

## Alternatives
- Embedding 字段召回：
  - 优点：成本低、可离线。
  - 缺点：4 个字段标签过少，阈值难以解释，容易把通用词向最近标签硬拉。
- 不新增 AI：
  - 优点：稳定、成本最低。
  - 缺点：低频语义别名仍需要用户每次手动选择，学习前体验较差。

## Test Plan
- 规则已完整命中时不调用列语义召回。
- 缺少规格列且存在未映射候选表头时返回语义建议。
- `验收方式` 不得被建议为最终验收结果列。
- `是否响应 / 检验结论 / 确认结果` 可被建议为验收结果列。
- AI 建议补齐关键字段时，表格仍为 `NeedConfirm`。
- LLM 超时、失败、返回非法字段时丢弃建议并保留规则结果。
