## Context
现有 `optimize-excel-recognition-pipeline` 已让一次智能结构识别只解码文档一次，但数据导入页面仍先请求表格元数据，再分别请求智能识别、预览和导入。前端的 `file-table-metadata.ts` 只能复用元数据 HTTP 响应，无法让后端的后续请求复用已解析的工作簿。

固定样本观测显示：首次元数据解析约 2370ms；智能识别约 5498ms，其中 AI 约 2512ms、非 AI 约 2986ms；预览和导入另有最多约 588ms 与 738ms 的文档读取。Ollama 模型已经驻留，因此本变更只消除本地重复解析，不改变或短路模型调用。

`DocumentTableSnapshot`、`TableInfo`、`TableData`、`RowData` 和 `CellData` 当前包含可变集合或属性，不能把同一个实例直接暴露给并发请求。全局 `IMemoryCache` 还承载其他业务缓存且没有统一大小单位，也不能直接为它设置 `SizeLimit`。

## Goals / Non-Goals
- Goals: 同一未变化上传文件在元数据、智能识别、预览和导入间复用一次完整解析结果。
- Goals: 保持缓存命中与未命中的表格数据、坐标、结构化内容和错误语义一致。
- Goals: 保持权限、取消、文档资源门禁和内存占用有界且可诊断。
- Non-Goals: 缓存智能识别结果、AI 输出、匹配结果、列映射结论或导入决策。
- Non-Goals: 修改 Prompt、模型参数、规则优先级、置信度、自动采用条件或导入业务规则。
- Non-Goals: 增加持久化缓存、分布式缓存、数据库迁移或 HTTP 字段。

## Decisions

### 1. 在应用边界引入共享快照提供者
Application 定义上传文档快照访问端口，API 适配器负责文件流、解析器、资源预算和内存缓存。`SmartConfigurationAppService` 与 `DocumentTableAccessService` 通过同一端口读取快照，使元数据请求完成的首次解析能够被识别、预览和导入复用，同时保持 Application 不依赖 API 实现。

表格元数据读取从快照投影 `TableInfo`；预览、匹配来源和导入读取从同一完整 `TableData` 按既有 `ColumnMapping` 与行数上限投影。缓存禁用、条目过大或未命中时仍通过同一提供者执行现有完整解析。

### 2. 内容版本决定缓存身份
缓存键由 `FileId + FileHash + FileType` 组成。调用方必须先从当前数据范围内读取 `WordFile`，再把当前内容身份交给提供者。

- 文件写回后 `FileHash` 变化，旧条目不会再命中。
- 文件删除、进入待删除状态或权限变化后，现有文件访问检查会先拒绝请求，不能从缓存直接取回内容。
- 文件成功写回或进入删除流程后主动按 `FileId` 清理旧条目，以尽快释放内存；正确性不依赖该清理成功。

### 3. 缓存值只读，投影结果归调用方所有
缓存内部保存构造完成后不再修改的快照。任何可能被调用方修改的 `TableInfo`、`TableData`、`RowData`、`CellData`、结构化单元格和合并单元格数据，都必须通过深复制或新投影返回。不得把缓存中的可变集合或嵌套对象直接暴露给请求作用域。

现有 `TableDataProjection` 继续承担表头与数据区投影，但实现时必须补齐结构化单元格的隔离，并通过 Word/Excel、多行表头、合并单元格、窗口预览和完整导入的一致性测试证明缓存命中与直接解析相同。

### 4. 同键并发请求使用 single-flight
同一内容版本同时未命中时，只启动一个底层解析任务，其他请求等待该任务。每个等待者仍可使用自己的取消令牌停止等待；单个请求取消不得取消或污染其他等待者共享的解析。宿主停止时取消底层任务。

只有成功完成且通过大小预算的快照进入缓存。解析异常、宿主取消或未完成任务必须从在途表中移除，后续请求可以重新解析；不得缓存异常任务。

### 5. 使用独立有界缓存
快照提供者拥有独立缓存实例，不修改全局 `IMemoryCache` 的 `SizeLimit`。默认配置为启用、120 秒滑动过期、128MiB 估算字节总预算、64MiB 单条目上限和 1MiB 最小条目计费单位。该默认值以现有 50MiB 上传文档上限为输入边界：允许保留少量常用完整快照，同时让展开后明显过大的文档自动退回不缓存路径。所有值均可通过配置收紧或禁用，不能用无界集合保留快照。

条目超过单条目预算时返回当前解析结果但不缓存。缓存逐出只影响后续是否重解析，不改变当前请求结果。容量估算至少覆盖表头、单元格文本、结构化内容、行列对象和合并单元格元数据。

### 6. 权限、资源门禁与可观察性保持在缓存外层
文件数据范围和客户权限校验始终发生在缓存读取之前。底层首次解析继续校验文件大小并持有 `DocumentParsing` 资源租约直到快照构造完成；缓存命中不占用解析租约。

日志仅记录 `FileId`、文件类型、cache hit/miss/shared/skip、解析/等待耗时、表格数、估算大小和 `TraceId`，不记录文件名、单元格文本或客户数据。固定样本验收比较端到端阶段耗时和底层解析次数，不承诺没有依据的绝对延迟阈值。

## Alternatives Considered

### 让智能识别响应携带表格元数据并取消前置元数据请求
该方案会耦合前端流程与识别响应，而且只能减少元数据与识别之间的一次解析，预览和导入仍会重复读取；还会改变 HTTP 契约。未选择。

### 只缓存表格元数据
内存成本较低，但智能识别和导入仍需完整解码工作簿，不能消除已测得的主要非 AI 时间。未选择。

### 继续保持请求级快照
实现最简单且没有跨请求状态，但固定样本已经证明跨请求重复解析占据可观时间。未选择。

## Risks / Trade-offs
- 完整快照会延长文档数据的内存驻留时间。通过独立容量、单条目上限、短 TTL、主动失效和超限不缓存控制。
- single-flight 中单个等待者取消后，底层任务可能继续服务其他请求。通过宿主停止取消、文件大小预算和解析并发门禁控制生命周期。
- 深复制和投影仍有 CPU 与分配成本，但避免 ClosedXML/OpenXML 重复解码；固定样本测量会单独报告解析与投影耗时。
- 内容哈希必须在文件写回后可靠更新。现有写回路径已经更新 `FileHash`，并增加回归测试保护失效语义。

## Migration Plan
无需数据库迁移或前端迁移。先以默认启用的短时有界缓存发布；若运行环境出现内存压力，可通过配置禁用或收紧预算，系统回到现有直接解析行为。源码回退不会影响数据库或文件内容。
