## Context

审计发现的缺陷不是单一页面或单一服务问题：失败后的 EF 跟踪状态会污染审计保存；过期前端响应会写回新上下文；文件系统与数据库无法共享事务；高成本操作缺少与复杂度匹配的预算；AI 出站路径需要统一的目标 Origin 和资源生命周期约束。修复必须保持现有分层、现有业务语义和本地 AI 能力。

详细设计和已确认边界见：

`docs/superpowers/specs/2026-07-27-runtime-correctness-resource-boundaries-design.md`

## Goals / Non-Goals

### Goals

- 建立最终状态审计、稳定错误响应和独立审计持久化。
- 建立异步请求作用域、取消和恢复协议。
- 建立并发缓存、文件删除和高成本操作的一致性边界。
- 建立所有 AI 出站路径共用的精确 Origin、直连和资源生命周期约束。
- 通过 TDD 和可重复依赖恢复所有质量门禁。

### Non-Goals

- 不改变匹配排序和 AI 裁决业务规则。
- 不新增批量回复服务端预览令牌。
- 不全面重构所有大文件。
- 不归档缺少真实发布证据的既有变更。

## Decisions

### Decision 1: 一个变更、四个可回滚切片

统一变更避免多个提案对相同 API、生命周期和测试门禁给出冲突要求；实现仍拆为审计/API、前端流程、后端资源安全、质量治理四个提交序列。

### Decision 2: 审计在最终结果阶段写入独立作用域

Action 阶段采集上下文，Result/Exception 阶段确定最终状态。审计写入从新 DI 作用域获取持久化服务，避免复用业务工作单元的失败实体。

### Decision 3: 过期响应由作用域键和请求代次共同拒绝

仅依赖取消不足以防止已经到达事件队列的响应。执行历史、语义搜索和批量预览同时比较不可变作用域键与单调请求代次。

### Decision 4: 文件删除使用持久状态机

数据库先标记 `PendingDeletion`，幂等清理器完成物理删除后再清理元数据。数据库迁移不直接操作文件系统。

### Decision 5: 高成本请求拒绝不完整结果

重复分析默认最多 2,000 个候选和 1,000,000 次比较。文件比较默认最多扫描 1,000,000 个单元格或等价节点，并最多产生 100,000 条差异。超限返回 422，不返回无明确完整性语义的部分结果。

### Decision 6: AI 出站只约束精确 Origin

Endpoint 只做确定性 URI 结构规范化。内网、公网、域名、IPv4 和 IPv6 均可使用 HTTP 或 HTTPS，不做地址分类、自定义 DNS、Socket 连接或 DNS 重绑定承诺。所有 quick/models/readiness/chat/embedding 路径使用同一受限客户端；每个请求必须与配置端点保持相同 scheme、规范化 host 和有效端口，禁止 Host 覆盖，并固定禁用代理和自动重定向。HTTPS 使用系统 SNI 和证书校验。

## Risks / Trade-offs

- 更准确的 HTTP 状态可能暴露旧客户端假设。通过统一前端错误适配和契约测试降低风险。
- 异步文件删除带来短暂待清理状态。通过状态可见性、幂等重试和运维指标换取可恢复性。
- 资源预算会拒绝超大请求。通过配置项、清晰 422 提示和筛选建议保证行为可解释。
- 不提供 IP/CIDR/DNS 重绑定防护。通过部署网络边界承担该类风险，应用侧只承诺精确 Origin、禁用代理/重定向、禁止 Host 覆盖和正常 TLS 校验。
- 一个提案跨度较大。通过四个独立提交切片、独立测试和独立回滚保持可审查性。

## Migration Plan

1. 先部署不含数据库迁移的审计和错误响应。
2. 部署前端请求作用域与回放恢复。
3. 应用 `PendingDeletion` 迁移但暂不启动清理器，验证旧数据兼容后再启用。
4. 部署 Embedding 并发、资源预算和 AI 精确 Origin 传输。
5. 完成依赖与 CI 治理。
6. 真实 MySQL 和生产式 Docker 完成升级、失败重试与回滚演练。

回滚文件删除切片时，先停用清理器，再回滚应用和迁移；不得在迁移回滚中删除物理文件。

## Open Questions

无。候选上限、比较预算、文件比较预算、上传移除语义、HTTP 超限状态和 AI 出站精确 Origin 边界均已由用户确认。
