## Context

引用次数属于验收规格当前内容版本的派生业务状态。计数必须和智能填充最终提交保持同一事务边界，同时需要兼容 Excel 与 Word 两条执行路径、请求幂等重放以及并发执行。验收规格内容可以通过手工编辑、文档导入、智能填充回填和备注批量替换等入口更新。

## Goals / Non-Goals

- Goals:
  - 只统计智能填充最终成功采用的行。
  - 并发执行时不丢失增量，同一请求重放时不重复累计。
  - 内容版本发生实质变化后从 0 重新计数。
  - 在现有列表、详情 API 和界面中提供一致的只读展示。
- Non-Goals:
  - 不追溯或估算历史执行记录的引用次数。
  - 不提供人工修改引用次数的 API。
  - 不按用户、文件或时间维度拆分引用统计。
  - 不把匹配预览、未采用候选或失败执行计入引用次数。

## Decisions

### 使用验收规格实体上的持久化累计值

在 `AcceptanceSpecs` 增加非空 `BIGINT ReferenceCount`，默认值为 0。该结构能够直接支持列表和详情查询，避免每次展示时扫描执行历史。迁移只增加带默认值的列，历史数据不做推断性回填。

### 在最终提交事务内按采用行原子累加

Excel 与 Word 执行路径都在执行记录、文件产物和数据库状态准备完成后，通过数据库端 `ReferenceCount = ReferenceCount + n` 原子更新，并与最终执行提交处于同一事务。累计单位是最终采用的行数，而不是规格去重后的数量。

现有任务快照和请求指纹继续承担幂等重放门禁；重放已完成任务时直接返回既有结果，不再次进入累计逻辑。

### 引用次数绑定当前内容版本

项目、规格、验收或备注任一字段在归一化后发生变化时，将引用次数重置为 0。空白可选值统一视为 `null`，必填值比较时忽略首尾空格。客户、机型、制程、来源文件和组织归属等元数据变化不改变内容版本计数。

所有能够更新上述内容的应用服务入口复用同一重置策略，避免不同写入流程产生漂移。

## Risks / Trade-offs

- 累计值不能还原每一次引用的来源；详细追溯仍由执行记录负责。
- `Down` 迁移会删除累计值，回滚前需要确认是否接受统计数据丢失。
- 数据库端原子更新不会自动刷新当前 DbContext 中已跟踪实体的旧值；累计后不得再用旧实体覆盖该字段。
- 前端使用 JavaScript `number` 展示 `BIGINT`；实际业务计数远低于安全整数上限，若未来接近该上限需改为字符串契约。

## Migration Plan

1. 通过 EF Core Migration 为 `AcceptanceSpecs` 增加 `ReferenceCount BIGINT NOT NULL DEFAULT 0`。
2. 启动迁移后核对 `__EFMigrationsHistory`、列存在性和待应用迁移数量。
3. 验证新建记录初始值为 0，成功采用、并发累计、幂等重放和内容变更重置行为。
4. 验证列表与详情 API、前端列表与详情展示一致。
5. 回滚时执行迁移 `Down` 删除该列；回滚会丢失累计统计，不承诺恢复。
