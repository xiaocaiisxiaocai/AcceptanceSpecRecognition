## Context

`AcceptanceSpecs.ReferenceCount` 只表示当前内容版本的引用次数。`AcceptanceSpecReferenceEvents` 保存全版本引用历史，但迁移前非零累计只能形成 `ReferencedAtUtc = null` 的基线，因此不能由空的最近引用时间推导“从未引用”。规格内容变更还会递增 `ReferenceVersion` 并清零当前计数。

当前单条和批量删除会直接物理删除规格，批量路径使用数据库端 `ExecuteDeleteAsync`。扫毒清理需要先隔离再删除，并保证匹配、搜索、缓存和后台任务使用同一可用性语义。

## Goals / Non-Goals

- Goals:
  - 以可解释、可复核的规则找出从未引用和长期未引用候选项。
  - 提供真实扫描进度、批量决策、隔离恢复和受控永久删除。
  - 对迁移历史、并发内容修改、权限和数据范围采取保守策略。
  - 在大数据量下保持数据库侧分页、聚合和有界批处理。
- Non-Goals:
  - 不使用 AI 或语义相似度决定删除。
  - 不自动执行隔离或永久删除。
  - 不把现有版本历史当成可单独删除的垃圾。
  - 首期不提供定时自动扫描或邮件通知。

## Decisions

### 1. 使用持久化扫描任务和判定快照

启动扫描后创建扫描任务，后台按有界批次处理当前用户数据范围内的规格。任务保存扫描开始时间、阈值、范围摘要、总数、已处理数、分类计数和状态；结果保存规格 ID、扫描时的 `ReferenceVersion`、内容时间、引用汇总、分类和原因码。

前端轮询任务状态并显示服务器返回的真实进度，不使用定时器伪造百分比。任务失败或取消时保留已完成计数和错误摘要，可重新扫描。扫描结果按任务和规格唯一，历史任务按保留策略定期删除，但不得连带删除规格。

扫描开始后新增、越权或已隔离的规格不进入该任务；扫描期间内容或引用发生变化的结果仍可展示，但执行动作前必须重新校验。

### 2. 判定规则保守且可解释

一次扫描固定两个整数配置：

- `newItemGraceDays`：新导入或刚修改内容的保护期，默认 30 天。
- `unusedDays`：长期未引用阈值，默认 365 天，且必须大于保护期。

每条规格聚合：当前版本引用数、全版本已记录次数、迁移前不可追溯次数、最近可追溯引用时间，以及 `contentActivityAt = max(ImportedAt, UpdatedAt, 当前版本 ChangedAtUtc)`。

分类顺序如下：

1. 已隔离或已标记忽略后续扫描的规格不进入普通扫描。
2. `untrackedReferenceCount > 0` 时分类为“人工确认”，原因是迁移前引用时间不可追溯。
3. 仍在保护期内时分类为“正常”，原因是新导入或刚修改。
4. 全版本引用次数为 0，且内容活动时间早于保护期截止时，分类为“建议清理 / 从未引用”。
5. 最近可追溯引用时间与内容活动时间两者的较晚值早于长期阈值截止时，分类为“建议清理 / 长期未引用”。
6. 当前版本引用数为 0、但旧版本最近引用仍在长期阈值内时，分类为“人工确认 / 新版本尚未引用”。
7. 其余分类为“正常 / 近期仍在使用”。

分类只代表建议，不产生自动动作。每条结果返回原因码、关键时间和引用汇总，页面不只展示一个不透明风险分数。

### 3. 保留与忽略分开表达

“保留”只处理当前扫描结果，不修改规格，便于用户完成本次审阅。“忽略后续扫描”在规格上保存忽略标记、操作人、时间和可选原因；后续普通扫描跳过该规格。

规格四项正文发生实质变化时自动解除忽略标记，使新版本重新接受扫描。用户也可在隔离管理页取消忽略。忽略操作受清理写权限和数据范围保护并写入审计。

### 4. 隔离是规格可用状态，不是物理删除

规格状态至少包含 `Active` 与 `Quarantined`。隔离保存隔离时间、到期时间、操作人、来源扫描、原因和隔离时的内容版本。默认隔离期为 30 天，部署配置可调整但不得小于 1 天。

所有验收规格业务读取必须通过共享的“仅 Active”查询规则，包括常规列表/详情、重复排查、语义搜索、智能填充候选、严格复用、导入冲突判断、Embedding 缓存生成与预热。隔离管理用例显式查询 `Quarantined`，避免各消费者自行遗漏过滤。

隔离动作使用扫描结果中的 `ReferenceVersion` 与当前状态作为条件。版本、引用状态或权限变化时，该项返回冲突并要求重新扫描；批量请求返回逐项成功/失败，不因单项冲突掩盖结果。进入隔离时删除或失效其 Embedding 缓存。

恢复将状态改回 `Active` 并解除隔离元数据；Embedding 在后续请求或预热中重建。恢复不改写正文、内容版本和引用历史。

### 5. 永久删除采用到期门禁和最小留痕

只有已隔离且到期的规格可永久删除。请求必须提交明确的二次确认标记和当前隔离版本；服务端重新检查独立永久删除权限、数据范围、隔离到期时间和并发版本。

永久删除在事务内清理规格专属缓存、引用事件、内容版本、扫描结果关联和规格本体。另写入不含项目、规格、验收、备注正文的删除记录，至少包含原规格 ID、公司、组织、删除人、删除时间、来源扫描和计数摘要，供审计追踪。控制器审计同时记录永久删除动作和批量结果，不记录规格正文。

### 6. API、权限和数据范围

新增独立控制器或明确分组的端点承载：启动/取消扫描、状态、结果分页、忽略、隔离列表、移入隔离、恢复和永久删除。控制器只做协议适配，应用服务负责任务、判定和事务编排。

权限至少拆分为查看扫描、执行隔离/忽略、恢复、永久删除四类；页面入口对拥有查看权限的用户可见，按钮按动作权限控制。所有计数、结果与动作只覆盖当前公司和当前组织数据范围，无权 ID 采用与现有规格接口一致的拒绝语义且不泄露存在性。

### 7. 前端采用单层紧凑工作台

从验收规格页工具栏进入扫毒清理页或全宽抽屉。顶部只有阈值、开始/重新扫描、进度和分类计数；主体使用分段控件切换“建议清理 / 人工确认 / 正常 / 隔离区”，下方为服务端分页表格。

表格默认不勾选任何项，固定展示建议、原因、项目/规格摘要、当前/全版本引用、最近引用和更新时间。批量操作栏只在有选择时出现，提供“保留”“忽略后续扫描”“移入隔离区”。隔离区提供“恢复”和在到期后可用的“永久删除”；永久删除使用明确二次确认弹窗。

视觉使用现有中性令牌与语义色、扫描图标和线性进度形成杀毒扫描感，不使用大面积装饰、拟物雷达或卡片嵌套。扫描、空结果、失败、部分成功和权限不足均有明确状态。

## Risks / Trade-offs

- 为保证真实进度和动作可复核，需要持久化扫描任务与结果，数据模型比一次同步查询更复杂；通过任务保留期和索引控制增长。
- 将隔离过滤统一下沉会触及多个读取消费者；需要共享查询策略和跨消费者回归测试，避免“列表看不见但匹配仍命中”。
- 永久删除引用历史会损失正文级追溯；通过隔离期、二次确认、并发门禁和无正文删除留痕降低风险。
- MySQL 与测试用 InMemory provider 的批量更新能力不同；核心判定应保持纯逻辑可测，持久化路径分别做集成验证。

## Migration Plan

1. 增加状态、忽略元数据、扫描任务/结果和删除留痕结构及索引；现有规格全部迁移为 `Active`。
2. 先让所有消费者统一过滤非 Active 规格，并以回归测试证明行为不变。
3. 发布扫描与隔离 API，再发布前端入口。
4. 首次上线只允许扫描、隔离和恢复；永久删除仍受隔离到期门禁控制。
5. 回滚应用时保留新增表和字段，旧版本仍可读取 Active 规格；不得通过回滚迁移物理删除隔离数据。

## Open Questions

- 无阻塞问题。默认保护期 30 天、长期未引用 365 天、隔离期 30 天；实施时作为可配置默认值，并在定向测试中锁定边界日语义。
