1. 前端 Web

web/src/views、web/src/api

  • 提供数据导入、智能填充、基础数据、配置、RBAC、审计等页面。
  • 负责上传、预览、人工确认、冲突选择、结果下载等交互。
  • 展示服务端决策、证据、语义召回建议、LLM 流式复核进度。
  • 边界：不自行决定匹配是否自动采用，不信任旧兼容字段。

2. API 协议层

src/AcceptanceSpecSystem.Api/Controllers

  • 提供 REST API、JWT 登录刷新、权限码校验、审计、SSE。
  • 按 api:resource:action 执行默认拒绝授权。
  • 把导入、匹配、填充、下载等请求委派给用例服务。
  • 边界：不直接访问 AppDbContext，不承载核心算法。

3. Application 用例层

src/AcceptanceSpecSystem.Application、Api/Services

  • 编排文档上传、表格预览、导入、匹配预览、执行填充、严格复用。
  • 组合 Core 算法、文件服务、仓储、执行历史和权限上下文。
  • 智能结构识别链路保留规则、路由、学习、列语义召回建议。
  • 边界：不把领域算法写成控制器逻辑，也不把持久化细节外泄。

4. 文档智能与表格结构

Core/Documents/Intelligence

  • 识别 Word/Excel 表格结构、表头、数据区、项目/规格/验收/备注列。
  • 支持规则映射、智能路由、跳过非验收规格表、系统元数据列排除。
  • 在缺列时可用 LLM 列语义召回给出建议，前端只展示不自动套用。
  • 边界：识别结果仍需门禁与人工确认，低置信不能直接导入。

5. 匹配引擎

Core/Matching

  • 使用 Embedding 召回项目+规格候选，并生成结构化证据。
  • 处理数值、型号、品牌实体、冲突、歧义和候选重排。
  • 可调用 LLM 做实体关系判别、等价裁决和高歧义复核。
  • 边界：Embedding 不可用时明确失败；LLM 是门禁辅助，不是主排序器。

6. 数据层

src/AcceptanceSpecSystem.Data

  • 通过 EF Core、Repository、UnitOfWork 管理 MySQL 数据。
  • 保存客户、机型、制程、验收规格、上传文件、AI 配置、Prompt、RBAC。
  • 维护单角色、单组织、迁移、Embedding 缓存、执行历史等数据。
  • 边界：只做持久化，不实现 Core 业务接口和用例编排。

7. 文件存储与文档写回

uploads/、DocumentServiceFactory

  • Word 上传落到 uploads/word-files。
  • Excel 上传与回写落到 uploads/excel-files。
  • Word 填充结果落到 uploads/filled-files。
  • 边界：数据库保存文件记录和索引，文件内容主要在文件系统。

8. AI 与 Prompt 配置

AiServices、PromptTemplates

  • 支持 OpenAI、Azure OpenAI、Ollama、LM Studio、OpenAI 兼容端点。
  • 按场景管理 Prompt：匹配复核、导入重复复核、实体判别、等价裁决。
  • 保存关闭思考模式、连接测试、模板预览、恢复默认。
  • 边界：模板无效时拒绝进入运行时；敏感配置走现有配置管理路径。

9. 运维与治理

后台服务、审计、备份、OpenSpec

  • 审计日志、执行历史、匹配任务快照、Embedding 缓存预热。
  • 数据库备份、缓存清理、上传文件删除联动。
  • OpenSpec 记录已实现能力和进行中的变更。
  • 边界：严格复用是临时会话能力，不是长期模板管理。

当前架构判断

  • 系统已经从控制器直写流程收敛到用例服务编排，主线是 Api -> Application -> Core / Data。
  • 核心复杂度集中在两个地方：文档结构识别和智能匹配门禁。
  • AI 的定位是辅助识别、复核和裁决，不是替代业务门禁。
  • 前端当前主要承担确认台和透明展示台职责，服务端仍是最终规则来源。
