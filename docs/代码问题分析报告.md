## P0 — 架构违规：Core 层反向依赖 Data 层

### 问题描述

Core 层（业务逻辑）不应依赖 Data 层（持久化），但当前存在以下违规：

1. **项目引用**：`AcceptanceSpecSystem.Core.csproj` 直接 `<ProjectReference>` 了 `AcceptanceSpecSystem.Data.csproj`，导致 Core 被 Data 强绑定，无法独立测试和替换持久化实现。

2. **SynonymService**（`Core/TextProcessing/Services/SynonymService.cs`）
   - 注入了 `IUnitOfWork`（Data 层接口）
   - 直接调用 `_unitOfWork.Synonyms.GetAllGroupsAsync()`

3. **DefaultTextPreprocessingPipeline**（`Core/TextProcessing/Services/DefaultTextPreprocessingPipeline.cs`）
   - 注入了 `IUnitOfWork`
   - 调用 `_unitOfWork.TextProcessingConfigs.GetConfigAsync()`

4. **LlmMatchingAssistService**（`Core/Matching/Services/LlmMatchingAssistService.cs`）
   - 注入了 `IUnitOfWork`
   - 调用 `_unitOfWork.PromptTemplates.GetOrCreateSystemAsync(...)` 等

5. **AiServiceSelector**（`Core/AI/SemanticKernel/AiServiceSelector.cs`）
   - 注入了 `IUnitOfWork`
   - 调用 `_unitOfWork.AiServiceConfigs.GetByPurposeAsync(purpose)`

### 影响

- Core 层无法独立单元测试（必须 mock 整个 UoW）
- Core 层与数据库实现强耦合，违反依赖倒置原则（DIP）
- 无法替换 ORM 或存储后端而不改动业务代码

### 修复方案

1. 在 Core 层定义纯接口（不依赖 Data 实体）：
   - `ISynonymDataProvider`：`GetAllGroupsAsync()` → 返回 Core 内置的轻量模型
   - `ITextProcessingConfigProvider`：`GetConfigAsync()` → 返回 Core 内置配置模型
   - `IPromptTemplateProvider`：`GetOrCreateSystemAsync(...)` → 返回字符串 Content
   - `IAiServiceConfigProvider`：`GetByPurposeAsync(purpose)` → 返回 Core 内置模型
2. 在 Data 层实现这些接口（薄适配器，内部调用已有 Repository）
3. 更新 Core 层服务注入 Core 接口而非 `IUnitOfWork`
4. 删除 Core.csproj 中对 Data 的 `<ProjectReference>`
5. 在 `Program.cs` 注册新适配器

## P1 — 性能问题：全表加载后内存分页/过滤

### 问题描述

**SpecsController.GetSpecs()**（`Api/Controllers/SpecsController.cs`，第 98 行）：

```csharp
// 问题代码
var allSpecs = await _unitOfWork.AcceptanceSpecs.GetAllWithCustomerAndProcessAsync(); // 全表加载
allSpecs = ApplySpecScope(allSpecs, scope);     // 内存过滤
allSpecs = ApplySpecFilters(allSpecs, ...);     // 内存过滤
var total = allSpecs.Count;                     // 内存计数
var items = allSpecs.OrderByDescending(...).Skip(...).Take(...).ToList(); // 内存分页
```

**SpecsController.GetGroups()**（第 51 行）：

```csharp
var allSpecs = await _unitOfWork.AcceptanceSpecs.GetAllWithCustomerAndProcessAsync(); // 全表加载
allSpecs = ApplySpecScope(allSpecs, scope);  // 内存过滤后分组
```

**AcceptanceSpecRepository.GetGroupSummaryAsync()**（`Data/Repositories/AcceptanceSpecRepository.cs`，第 127 行）：

```csharp
var allSpecs = await GetAllWithCustomerAndProcessAsync(); // 全表加载
var groups = allSpecs.GroupBy(...).Select(...).ToList();  // 内存 GroupBy
```

### 影响

- 规格数据量增大后，每次请求都把全表数据拉入内存
- 内存占用随数据量线性增长
- 响应时间随数据量线性劣化，无法水平扩展

### 修复方案

1. 在 `IAcceptanceSpecRepository` 添加带过滤+分页参数的方法：
   ```csharp
   Task<(IReadOnlyList<AcceptanceSpec> Items, int Total)> GetPagedWithFilterAsync(
       int? customerId, int? processId, int? machineModelId,
       bool? processIdIsNull, bool? machineModelIdIsNull,
       string? keyword, int? ownerOrgUnitId,
       int page, int pageSize);
   Task<IReadOnlyList<GroupSummaryItem>> GetGroupSummaryWithScopeAsync(int? ownerOrgUnitId);
   ```
2. 在 `AcceptanceSpecRepository` 用 EF Core LINQ 在数据库端完成 WHERE + ORDER BY + Skip/Take + COUNT
3. 修改 `SpecsController.GetSpecs()` 和 `GetGroups()` 调用新方法，删除内存过滤逻辑

## P1 — 性能问题：AI 服务静态缓存无上限且无淘汰

### 问题描述

`SemanticKernelServiceFactory`（`Core/AI/SemanticKernel/SemanticKernelServiceFactory.cs`）：

```csharp
// 问题代码
private static readonly ConcurrentDictionary<string, IEmbeddingGenerator<string, Embedding<float>>> _embeddingCache = new();
private static readonly ConcurrentDictionary<string, IChatCompletionService> _chatCache = new();
```

- 两个静态 `ConcurrentDictionary` 永不淘汰条目
- 每次 AI 服务配置变更（修改 Endpoint/Model/ApiKey）都会产生新条目，旧条目永远不被释放
- `OllamaNativeChatCompletionService` 每次都 `new HttpClient()`，不走 `IHttpClientFactory`，会耗尽 socket

### 影响

- 长期运行后内存持续增长（内存泄漏）
- socket 资源泄漏（Ollama 场景）
- 应用重启是唯一释放途径

### 修复方案

1. 将静态 `ConcurrentDictionary` 改为有界缓存（如 `MemoryCache` with size limit 和 sliding expiration）
2. 实现 `IDisposable`，在条目被淘汰时 dispose 连接器
3. 注入 `IHttpClientFactory` 替代手动 `new HttpClient()`

## P2 — 整改完成：时间戳统一使用 UTC

### 原始问题

仓库中曾存在多处“本地时区时间 API”写入数据库、缓存时间戳、权限生效时间和文件路径命名的情况。在服务器时区与用户时区不一致时，这会导致时间语义含混，给排序、过期判断和跨时区排障带来额外成本。

### 整改结果

- 实体默认值、仓储层写入、控制器写入、后台任务清理逻辑均已统一切换为 UTC 时间
- 权限有效期判断、缓存过期判断、审计清理窗口等比较逻辑已统一按 UTC 计算
- 文件存储日期目录、比较结果下载文件名以及测试夹具中的时间生成逻辑已同步统一
- 已新增仓库级回归测试，约束 `src` 与 `tests` 目录下不得再引入本地时区时间 API

### 效果

- 消除服务器部署时区差异带来的时间歧义
- 统一数据库与缓存时间语义，便于跨时区查询、排序和清理
- 为后续代码评审和自动化检查提供可持续的约束

## P2 — 代码缺陷：ExceptionHandlingMiddleware 每次异常都 new JsonSerializerOptions

### 问题描述

`Api/Middleware/ExceptionHandlingMiddleware.cs`（第 70 行）：

```csharp
// 问题代码（在每次异常处理时执行）
var options = new JsonSerializerOptions
{
    PropertyNamingPolicy = JsonNamingPolicy.CamelCase
};
await response.WriteAsync(JsonSerializer.Serialize(apiResponse, options));
```

`JsonSerializerOptions` 构造耗时较高（会进行反射缓存预热），在高并发场景下大量异常会造成不必要的 CPU 和内存压力。

### 影响

- 每次异常都重新创建并丢弃 `JsonSerializerOptions`，无法利用内部缓存
- 高并发异常场景下 GC 压力增大

### 修复方案

```csharp
// 修复后：声明为静态只读字段
private static readonly JsonSerializerOptions JsonOptions = new()
{
    PropertyNamingPolicy = JsonNamingPolicy.CamelCase
};
```
