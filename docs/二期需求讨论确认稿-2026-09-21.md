# 验规系统二期需求讨论确认稿

讨论整理日期：2026-09-21  
状态：业务讨论基线，尚未实施或验收  
依据：本次连续讨论中的用户确认；后续明确修正优先于早期建议。

本次修订：纳入深度审查后确认的答案组合、旧资料复用资格、来源变更核对、占位内容、部门退出后的修订接手、文档重复与版本规则，以及操作体验和迁移验收增强项。

## 1. 目标与适用范围

二期围绕部门历史资料维护、灵活字段识别、多人分工回复和原文溯源，减少整理文件、查找答案及重复填写的工作量。验规回复属于严肃业务内容，系统辅助检索和复用，人对实际回复负责。

主要使用 Word `.docx`、Excel `.xlsx` 完成结构化导入与回填。PDF、无法结构化处理的 Word 可以整份上传到文档资料中，集中查找、预览和下载。

使用规模已确认：使用人数不多，主要涉及机构、电控、智能化三个部门。当前没有确认具体同时在线人数或请求量，不设虚构的并发指标；部门管理仍沿用可配置方式，不将三个部门写死在程序中。

本稿记录业务行为和边界，不代表已经确定全部数据库表、接口、预览引擎或检索组件。JSON 统一升级是已确认方向；RAG 的具体架构和组件仍需技术设计与样本验证。

## 2. 已确认的核心原则

1. 各部门自行清洗并上传自己负责的历史资料，系统不依靠 AI 自动决定维护部门。
2. 一份验规文件可以涉及多个部门，一条验规由一个部门独立负责。
3. 正式回复在系统内填写，首版不做线下编辑后回传合并。
4. 内容统一表达为需求字段组和答案字段组，两组均允许数量可变的字段。
5. AI 自动识别表格、表头、字段分组和处理范围，人工主要核对不确定项。
6. 历史检索先提供答案，各部门自主认领；认领后由该部门独占填写。
7. 明确适用的历史原答案自动进入草稿，部门确认后才算完成。
8. 多份合理但不同的答案展示候选及差异，不按“最新一条”自动决定。
9. AI 不自由生成新的验规答案；没有可靠答案，由认领部门填写。
10. 原件、来源、内容版本与实际采用记录可追溯。
11. 一期历史内容统一升级为新版 JSON 结构，不要求用户重新上传全部资料。

## 3. 角色与权限

| 角色或职责 | 主要操作 |
| --- | --- |
| 部门资料维护人员 | 上传、整理、修改、更新版本、停用或删除本部门资料；选择任务答案入库 |
| 任务发起人／负责人 | 创建任务、选择参与部门和默认历史来源、核对处理范围、协调无人认领内容、检查完整性并生成正式文件；按规则取消任务或转交负责人 |
| 部门填写人员 | 查看参与任务、认领条目、填写与修改本部门答案、选择历史候选、确认完成 |
| 模板维护人员 | 保存、更新同公司共享模板并维护版本 |

同一人可以承担多个职责，最终角色配置及菜单、按钮权限在详细设计中落实。

### 3.1 历史资料共享

- 同一公司内，正式入库的历史资料允许各参与部门查看、匹配和引用。
- 未入库的部门草稿不参与公共匹配。
- 修改、停用、删除权限归所属部门有维护权限的人员。
- 引用后修改的是本次任务答案，不自动修改来源历史资料。
- 全部查询、原文预览和下载应执行相应数据访问校验。
- 清洗后上传的历史资料原件，以及文档资料中的 PDF、Word，默认允许同公司各部门有资料查看权限的人员预览和下载。
- 原文件共享不赋予其他部门修改、覆盖或删除来源文件的权限；维护权限仍归所属部门的授权人员。预览、下载及文件关联均校验公司范围，不跨公司共享。

### 3.2 任务内编辑

- 认领归属于部门，本部门有填写权限的成员可以接手，不绑定单一认领人。
- 记录认领、填写、修改、转交、撤回和完成的实际操作人。
- 其他部门不能修改已经被认领的条目。
- 同时认领只能有一个成功；同时编辑应防止相互覆盖。
- 退出页面不自动取消认领；需要取消或转交时执行明确操作。

## 4. 现有历史资料清理

目前部分机构、智能化内容混在电控上传的历史资料中，存在空答案及“待机构确认”“待智能化确认”等占位回复。

已确认的处理方式：

- 由电控核对并删除这部分不准确、非本部门维护的历史条目。
- 不把这批条目直接移交给机构或智能化作为正式资料。
- 机构、智能化分别清洗准确内容后自行上传。
- 被删除条目退出后续历史匹配及检索索引。
- 已经发生的任务引用和已生成文件保留当时内容，不因来源清理被改写。

本稿不执行任何清理操作，具体清单由部门整理确认。

## 5. 灵活内容结构与表头识别

### 5.1 内容表达

需求和答案均由有顺序的字段列表组成，保留字段标识、原表头或显示名称、原始内容及可获得的来源位置。

允许的示例：

| 文档形式 | 需求字段组 | 答案字段组 |
| --- | --- | --- |
| 常规四列 | 项目、规格 | 验收、备注 |
| 没有项目列 | 规格 | 回复 |
| 条件分列 | 项目、技术要求、使用条件 | 供方能力、补充说明 |
| 回复已经合列 | 项目、规格 | 完整回复 |

项目不是固定必需字段。验收列不限定为 OK／NG 或满足／不满足，可以包含具体能力、参数、实现说明、限制条件等。

不同表格或区域可以有不同的字段组合。内部保留结构，不以罕见分隔符作为唯一保存与还原依据。

### 5.2 AI 识别输出

AI 应识别并给出：

- Sheet、表格或区域及真实表头位置；
- 单行、多行和合并表头的完整层级；
- 需求字段、答案字段、辅助上下文及不参与字段；
- 每个字段的准确位置、名称、分组与组合顺序；
- 数据处理范围；
- 存在歧义的位置及原因。

字段组的列数由识别结果统计，不预设必须四列。答案列为空时，仍需结合表头层级、相邻列和模板经验识别，不能依赖答案中是否出现特定判定词。

程序检查 AI 输出的位置、范围和分组是否有效。无法确定时局部提示，不强行分组或定位。

### 5.3 识别与确认体验

- 在原表预览中标出需求列、答案列、不参与列和不确定项。
- 展示组合后的真实需求及答案预览，帮助核对遗漏与错列。
- 支持按表格、区域及结构相同的多个区域批量调整。
- 模板匹配且结构核对一致时自动配置，减少重复操作。
- 新格式由 AI 提出配置，人工重点核对疑问部分。
- 不要求每个参与部门重复确认整份文件的结构。

### 5.4 表头模板

- 已确认配置可保存为同公司共享模板。
- 单次调整默认只影响当前任务。
- 明确保存或更新模板后，才用于后续识别。
- 共享模板更新由有权限的维护人员操作，并保留版本。
- 已开始任务保持原配置，不随模板更新自动改变。
- 新文件表头结构变化时重新检查，不直接套用旧列号。

## 6. 条目边界与处理范围

### 6.1 独立填写单元

- 普通情况下，一行对应一条验规。
- 多行要求共用一个答案单元格时，作为一个整体认领。
- 多行各有独立答案位置时，可以分别认领，并保留必要上下文。
- 同一答案单元格不能被拆给两个部门填写。
- 无法可靠确定边界的区域，由负责人在结构确认中调整。

### 6.2 范围完整性

- 展示文件中的 Sheet、表格、识别区域及其处理情况，可对照原文。
- 区分已纳入、明确排除和存在疑问的范围。
- 封面、说明及无关表格支持批量排除，不要求逐行操作。
- 任务负责人确认需要回复的内容均已纳入。
- 未解决的范围疑问不妨碍先填写已确认部分，但阻止生成正式文件。
- 不能仅因 AI 识别出的条目全部完成，就自动认定整份文件没有遗漏。

## 7. 历史资料导入与维护

### 7.1 基本流程

部门清洗资料 → 上传并留存原件 → AI 识别需求／答案字段组 → 核对结构及范围 → 检查答案质量和重复项 → 确认入库。

清洗以业务范围和资料质量为主，不强迫所有文件预先改成统一四列表格。

### 7.2 答案质量检查

| 内容情况 | 处理规则 |
| --- | --- |
| 答案完全为空 | 默认不进入可复用历史库，进入待处理清单 |
| 整段只有待确认、后续补充等占位内容 | 集中提示，由上传人核对排除 |
| 明确不支持、不满足 | 可以是有效回复，正常保留 |
| 已有实质回复但部分待确认 | 单独提示，不因包含某个关键词就整条删除 |
| 附带适用、选配或限制条件 | 完整保留，不当作无关说明清理 |

导入预览区分可入库与需处理内容，支持批量操作。未解决疑问项留在导入草稿，不参与公共历史匹配；原文件完整保留。

### 7.3 重复与更新

- 同部门、同适用范围且需求与答案完全相同：不重复新增，关联本次来源。
- 需求相同但答案不同：展示差异，由维护人员选择新增或更新。
- 更新已有资料：产生新内容版本，保留旧内容及引用记录。
- 不同适用范围的资料分别保留，不因文字相同就合并。
- 不同部门的相同内容保留维护归属，可以提示重复，不自动移交或覆盖。
- AI 相似度用于提示疑似重复，不能直接据此覆盖或合并。

### 7.4 适用范围

区分指定范围、已确认通用、范围未明确。

- 指定范围按登记的客户、制程、机型使用。
- 通用性由维护人员明确确认，需明确是哪些维度通用。
- 未明确的资料可检索供参考，但不自动带入答案，由填写人确认采用。
- 一期空值按未明确迁移，不自动解释为全部适用，也不要求一次性补齐所有旧资料。

## 8. 新验规任务与部门认领

### 8.1 创建与参与部门

- 发起人选择参与部门，可复用常用组合。
- 参与部门可查看整份任务，并自主认领未认领条目。
- 可批量认领；选择成功后即占用，不等填写完成后才锁定。
- 占用只针对本次任务的具体条目，不锁住历史资料或其他任务。
- 负责人协调无人认领内容。

### 8.2 新增与移除部门

| 情况 | 处理规则 |
| --- | --- |
| 新增参与部门 | 不改变已有认领和回复 |
| 移除尚未认领的部门 | 直接移除 |
| 移除有未完成条目的部门 | 提示影响，条目退回待认领，已有草稿保留供接手人核对 |
| 移除有已完成条目的部门 | 默认保留已确认答案及操作记录 |
| 同时需要撤回已完成回复 | 明确执行撤回，条目重新进入待处理 |

部门移除后不能继续编辑本次任务，包括已经打开的旧页面。

已完成条目保留的原部门信息属于历史记录。后续该条需要修改、撤回或重新核对，而原部门已不参与时，条目转为待认领，由当前参与部门接手；原回复和原确认记录保留供参考，不自动把填写责任转给任务负责人。

### 8.3 系统内填写

正式填写在系统内完成。下载用于查看或交付，首版不提供下载编辑后上传合并。

已有答案和人工修改要可靠保存。同部门成员可接手；系统显示保存状态，不能在保存失败时显示成功。

### 8.4 取消任务与负责人转交

- 未正式完成的任务，负责人可以取消，并填写取消原因。
- 取消后停止填写，保留已有回复、认领及操作记录；取消与完成是不同状态，不将未处理条目自动标为完成或无需回复。
- 取消操作在服务端生效，已打开的页面和迟到保存不能继续修改已取消任务；已取消版本不得继续生成正式文件。
- 负责人可以转交给有任务管理权限的人员，已有参与部门、认领、回复和完成记录保持不变，记录转交双方及时间。
- 已经生成的正式文件和版本记录不因取消或转交被删除、改写；未完成修订被取消时，既有正式版本仍保留。

## 9. 多范围检索与历史答案选择

### 9.1 本次对象与历史来源分开

本次任务的客户、制程、机型与历史检索来源分别设置。扩大参考范围不改变本次业务对象，也不改变来源资料归属。

支持添加多个历史来源组合，例如：

| 来源范围 | 客户 | 制程 | 机型 |
| --- | --- | --- | --- |
| ① | 客户 A | 制程甲 | 机型 X |
| ② | 客户 B | 制程乙 | 机型 Y |
| ③ | 客户 A | 制程丙 | 全部机型 |

检索这些范围的并集，并继续执行数据访问权限过滤。明确选择全部与历史资料范围未知是不同概念。

同一历史记录被多个范围覆盖时只展示一次；不同来源、条件或答案的候选保留。

### 9.2 范围调整

- 发起人选择任务默认来源范围，完成初次匹配。
- 部门可以为自己认领的条目增减有权访问的来源范围。
- 调整仅影响选定条目，不改变其他部门范围或回复。
- 重新匹配只更新候选，不自动覆盖已有答案、人工修改和完成状态。
- 替换答案时展示差异，由填写人决定。
- 保存实际采用的历史条目、内容版本和来源。

### 9.3 候选与草稿

| 检索结果 | 处理方式 |
| --- | --- |
| 明确适用、无冲突且可复用的历史答案 | 原文自动进入草稿，遵守整组答案一致性规则，等待部门确认 |
| 多份合理但不同的答案 | 展示候选及差异，由认领部门选择 |
| 相近但适用条件不明确 | 作为参考，不自动带入答案 |
| 没有可靠答案 | 保持待填写，由认领部门人工回复 |
| 来源原文件缺失 | 可检索参考，不自动带入，由部门核对采用 |

候选展示来源部门、客户、制程、机型、版本、完整答案、附带条件及原文入口。不按最新时间自动选定不同答案。

### 9.4 已有内容

- 按单元格保留新文件已有的真实答案。
- 答案字段组整体比较，不能只看目标单元格是否为空。
- 整组答案为空时，可按候选规则带入一份明确适用的历史答案；只有一部分为空时，已填内容与该候选对应字段一致、且映射明确，才自动补齐空白。
- 已填内容与候选存在差异，或一致性无法确认时，只展示完整候选及差异，由填写人决定，不自动拼接。
- 替换已有内容需展示差异，由填写人决定。
- 一条回复部分已填、部分为空时，不覆盖已填部分。
- 系统不自动从不同候选各取部分字段拼成一组答案。填写人主动选择或修改形成的新组合按人工回复记录，保留能够明确追踪的各部分来源，并重新确认完成。
- 已有内容和自动带入内容都需要部门确认，不能自动标为完成。

例如，现有回复为“节拍 3 秒”、备注为空，候选为“节拍 5 秒＋需要双工位”，系统不能仅把候选备注补入空白，拼成“节拍 3 秒＋需要双工位”。

## 10. AI 能力边界

### 10.1 首版允许

- 表格、表头、字段组和范围识别；
- 历史资料检索、候选推荐、差异与条件提示；
- 复用已确认模板及人工修正经验；
- 查找资料和展示可追溯原文。

### 10.2 首版禁止

- 自由生成新的设备能力、参数、实现承诺或验规答案；
- 将无依据推断直接写入正式答案；
- 通过模型复述历史答案后静默替代历史原文；
- 将不同配置或工况的能力拼成未经确认的新承诺；
- 自动确认完成或自动把新回复发布到历史库。

推荐历史记录后，由程序读取相应记录和版本的原内容。RAG 不视为消除错误的保证。

### 10.3 字段回填约束

需求／答案统一 JSON 并不意味着每条内容字段数相同。映射、合列和分列应遵守原文复用原则：明确对应的字段可以回填，同一份已选择答案的多段原文可以按确定规则组合，并遵守 9.4 的已有内容一致性检查；没有可靠边界的拆分、含义不对应的列，不应由 AI 自由改写后填入。不能以“按字段填入”为由自动混合不同候选。

具体映射与异常交互需用真实样本验证，不重新引入生成式业务承诺。

## 11. 完成、正式文件与修订

### 11.1 完成规则

- 所有选中的答案字段均填完，才能确认完成。
- 任意一个选中的答案字段未填完，即为未完成。
- 不引入必填／选填配置；不需要填写的列不选入答案字段组。
- 只有“请填写”“待确认”“后续补充”等占位内容不算填完，不能仅因非空就确认完成。
- 明确“不支持”“不满足”可以是有效答案；实质回复中包含待确认事项时突出提示，由填写人核对，不能按关键词直接否定整条内容。
- 整条无需回复时，由认领部门标记无需回复／不适用，并填写简短原因。
- 已有文字或自动带入内容不自动完成，仍由部门成员确认。
- 完成状态绑定实际确认的内容。未正式冻结的答案一经修改即回到待确认；来源变化需核对时按 12.2 处理。
- 不增加部门内部二次审批。

### 11.2 正式文件

- 全部条目已完成或已明确标记无需回复，且处理范围疑问、来源变化待核对事项均已解决，才能生成正式文件。
- 有未完成内容时允许下载草稿，不能标为正式完成。
- 由任务负责人检查完整性后生成正式文件。
- 文件内容对应已确认的任务结果，不能在生成时重新运行匹配而改变答案。
- 正式文件及对应内容版本留存，再次下载同一版本应取得对应存档。

### 11.3 正式完成后的修订

- 通过创建修订版继续修改，保留旧正式文件及对应记录。
- 修改的条目重新进入待确认，由负责部门确认完成。
- 原负责部门已退出任务时，需要修改或重新核对的条目转为待认领，由当前参与部门接手；原部门仅保留历史署名和操作记录。
- 未受影响条目沿用原确认结果。
- 需求、公共条件或表头配置变化时，提示需要重新核对的影响范围。
- 修订完成后生成新正式版本，并可查看差异。
- 不建设任务进行中更换源文件、自动迁移回复的功能；该能力与已确认的正式回复修订分开。

## 12. 任务结果沉淀与来源变更

### 12.1 选择入库

- 本次回复及修改过程自动保存在任务记录中。
- 任务完成后，集中列出新增、修改的答案。
- 各部门有资料维护权限的人员批量选择入库内容。
- 默认新增历史资料，不自动覆盖旧答案。
- 明确选择更新旧答案时保留版本。
- 本次订单的特殊回复可以仅保留在任务记录中。

### 12.2 来源更新、停用或删除

- 任务保留采用时的答案、版本和来源，不随资料库自动变化。
- 已采用来源的正文或可用状态在最后确认后发生变化时，进行中的任务标记来源变化、待核对，未核对前不能生成正式文件。
- 填写部门可以核对后明确继续使用任务中保存的旧答案，也可以替换后重新确认。核对记录绑定实际看到的来源版本或状态，不能把尚未看到的后续变更一并视为已确认。
- 仅名称、标签等非内容且不影响适用性的信息变化，只提示，不使完成状态失效；适用范围变化需按可能影响采用依据处理。
- 已生成正式文件保持不变。
- 停用、删除的资料退出新的检索；已有业务记录保留当时采用的事实内容。
- 来源提示不静默替换答案，重新核对沿用部门成员的确认动作，不增加审批流程。原负责部门不再参与时，按 8.2 转为待认领并保留原内容。

## 13. 原文溯源与文档资料

### 13.1 结构化资料的溯源

- 留存上传时的原件及其版本，后续资料修改不覆盖原件。
- 记录来源部门、上传与导入时间、导入时字段定义、可获得的条目位置。
- 每条历史资料和候选答案提供查看来源入口。
- 系统内预览原文件，具备准确定位信息时定位并突出来源内容，同时支持下载。
- 原始内容与后续人工修改记录分别可查。
- 来源关联绑定具体内容版本，不仅保存当前资料的文件指针。v1 来自文件 A、v2 来自文件 B 时，引用 v1 必须仍能追溯 A。
- 人工修改产生的版本标明基于哪个原文或内容版本修改，区分修改后答案与原件实际文字，不把原件展示成能够直接证明所有新修改的内容。
- 部门清洗后上传，系统留存的是清洗后的上传原件；清洗前完整文件只有实际提供并关联后才能追溯，不能自动还原。

### 13.2 无法结构化的文件

- PDF、无法结构化处理的 Word 支持整份上传到文档资料。
- 可以直接选择仅保存文档；提取失败时可以转存，无需再次上传。
- 支持按文件名、客户、制程、机型、部门、时间及标签查找。
- 能可靠提取正文时可支持全文检索；无正文索引时仍能依靠名称及分类查找。
- PDF 提供预览；Word 原件与预览副本分别保存。
- 预览失败不丢弃原件，显示状态和原因，支持重试及下载。
- 文档资料可作为人工参考，不把未经提取和确认的内容自动回填为历史答案。
- 本轮多范围需求主要针对回复时检索，不据此自动增加“每个归档文件必须关联多个范围”的要求。

### 13.3 文档重复与版本

- 同部门上传完全相同的文件时提示已存在，可以补充分类信息，不无意义新增重复文档。
- 同名但内容不同的文件，提示选择新文档或现有文档的新版本，不直接覆盖原件。
- 不同部门上传相同文件，保留各自管理及权限关系；底层物理存储是否复用属于技术实现，不据此合并权限或泄露其他来源。
- 搜索结果展示部门、版本和上传时间，区分同名文件。
- 内容版本及任务已经引用的文件版本保持可追溯，不因上传新版本而改变旧引用。

### 13.4 保存期限与清理

- 原始文档、正式回复文件及其版本记录默认长期保留，不按固定天数自动删除。
- 已无运行任务依赖的临时处理文件，以及可重新生成的预览缓存，可以自动清理；不能将原件、正式结果或其版本记录误归为临时文件。
- 存储空间不足时明确提示，不擅自删除正式资料。
- 本规则约束自动清理，不取消所属部门主动维护、删除错误历史条目的权限，也不改变电控清理错误条目的既定规则。
- 主动删除条目后，既有任务仍保留实际采用内容和版本；被引用文件的物理删除条件在详细设计中明确，不因条目删除自动破坏历史溯源。

## 14. 一期数据升级为统一 JSON 内容结构

### 14.1 已确认目标

一期四字段内容与二期扩展字段最终使用同一套 JSON 内容模型。新界面和业务流程不要求用户区分旧格式与新格式。

旧字段确定性转换：

| 旧字段 | 新结构 |
| --- | --- |
| Project | 需求字段项 |
| Specification | 需求字段项 |
| Acceptance | 答案字段项 |
| Remark | 答案字段项 |

### 14.2 保真要求

- 保留文本、空值、空字符串、字段顺序、记录身份、部门、适用范围和来源关联。
- 格式转换不通过 AI 改写或自动重解释旧内容。
- 不能仅因项目与规格相同就删除项目；旧系统补齐行为需有证据才能纠正。
- 旧系统字段名称不冒充已核实的原始表头。
- 当前内容及已保存的历史内容版本均可在新版系统读取、比较和恢复。
- 不用当前内容补造缺失的旧版本。
- 格式升级不增加业务内容版本、不重置引用次数、不改写历史操作者和业务时间。

### 14.3 溯源不完整的旧资料

| 实际情况 | 升级后行为 |
| --- | --- |
| 有原文件及准确位置 | 可定位预览 |
| 有原文件但缺位置 | 可预览文件，明确暂不能定位 |
| 原文件缺失 | 标明来源文件缺失，可检索参考但不自动带入 |

不强制全部重新上传，也不伪造原文、原表头或行列位置。

### 14.4 迁移后的复用资格

格式转换与复用资格分类分开处理。所有可取得的历史原值按 14.2 保留，分类本身不删除原内容，也不要求重新上传或逐条重新确认。

| 旧资料情况 | 迁移后处理 |
| --- | --- |
| 原本有效、内容完整、来源及适用范围明确 | 默认继续正常复用，不要求部门全部重新确认 |
| 答案空白、仅占位或存在未解决内容问题 | 待整理，不自动进入任务草稿 |
| 来源缺失或适用范围未明确 | 仅供参考，按既定规则由填写人核对采用 |
| 已停用、删除或隔离 | 保持原有效性状态，不因格式转换重新启用 |

多个条件同时存在时，从严限制自动带入并显示原因；不能因格式完整就视为业务答案合格。

切换前提供迁移分类汇总：正常可复用、仅供参考、待整理和原不可用资料的数量及原因。核对升级对实际使用范围的影响，不能只验证 JSON 已生成。

### 14.5 技术设计建议，尚非最终表结构

- 需求／答案正文采用带结构版本号的 JSON，有稳定字段标识。
- 部门、客户、制程、机型、权限、业务状态和来源关系保留便于约束和查询的结构化管理。
- 结构版本号与业务内容版本号分开。
- JSON 正文最终成为统一内容来源；过渡期读写策略应明确，避免两套可独立修改的正文长期并存。
- 采用先补充、转换核对、切换、再移除旧依赖的迁移方案，保留可审查证据。
- 新结构产生扩展字段后，不能声称旧程序可以无损接管；回退边界在技术方案中明确。

## 15. 工程保障与验收方向

下列内容作为实现与验证要求，不增加额外业务审批流程。

- 保存、认领、取消、转交和部门移除在服务端校验当前状态，过期页面不能静默覆盖。
- 草稿在刷新、断线恢复后可继续处理，保存失败有明确反馈。
- 重复提交与失败重试不重复导入、更新版本或生成正式业务记录。
- 原件、预览副本、结构化内容、正式结果文件的生命周期分开管理。
- 历史资料修改、停用、删除后，匹配与检索索引同步更新。
- 正式结果绑定实际确认的内容及版本，不受后台资料变动影响。
- JSON 升级对当前记录、版本记录、引用与执行记录进行一致性核对。
- 确认完成时绑定服务端已保存的内容版本；迟到的自动保存、过期页面或旧编辑会话不能覆盖更新内容并保留旧完成标记。
- 正式生成检查并冻结同一份已确认结果，处理与保存、来源核对之间的并发变化，避免文件内容与完成记录不一致。
- 各内容版本保留对应来源信息，切换当前来源不改写旧版本来源。
- 重审一期候选去重及范围限制：不同答案不能按项目＋规格提前丢弃；跨多个范围检索应通过索引、分阶段检索等方式支持目标规模，不能直接沿用固定 5,000 条作为二期业务拒绝门槛，也不能静默截断造成遗漏。
- JSON 切换门禁覆盖新版读取、编辑、版本比较与恢复、精确及语义检索、候选展示、回填导出和原件追踪；索引或向量仅在有效内容、模型及构造规则仍一致时复用，否则重建并验证。
- 迁移核对除记录数、版本数、字段顺序和空值外，还应以代表性旧资料完成实际检索、回填和溯源验证。
- 不因方便回填而改动未选择的单元格、公式、客户需求或其他内容。

### 15.1 真实样本验证清单

| 场景 | 重点观察 |
| --- | --- |
| 无项目列、回复合列、多列需求 | 识别、保存及回填是否准确 |
| 重名表头、多行表头、合并单元格 | 字段用途、范围和条目边界是否正确 |
| 多 Sheet、多表格、多区域 | 能否分别配置并完整核对范围 |
| 跨客户、制程、机型检索 | 来源范围是否准确，差异答案是否被保留 |
| 多部门并发认领、接手、移除 | 是否相互覆盖，草稿和完成记录是否保留 |
| 已有答案、空白答案、占位回复 | 是否误覆盖、误判完成或误入库 |
| 原文件预览与定位 | 内容是否可读、定位是否对应真实原文 |
| 已确认结果导出及修订 | 原格式与内容是否保持，版本是否可追溯 |
| 一期数据升级 | 值、空值、身份、版本与引用是否一致 |
| 失败、断线、重复操作 | 能否恢复且不产生重复或丢失 |
| 已有答案与候选存在差异，且部分字段为空 | 是否停止自动拼接并完整展示差异 |
| 所有选中字段非空但只有占位回复 | 是否仍按未完成处理，明确否定答案是否正常保留 |
| 确认完成后来源正文或可用状态变化 | 是否要求核对后再正式生成，非内容变化是否避免无谓重做 |
| 原部门退出后条目进入修订或待核对 | 是否回到待认领且保留原回复和历史记录 |
| 同名文件、相同文件及不同来源版本 | 是否避免覆盖原件、错指来源或扩大权限 |
| 迁移后复用资格分类 | 是否保留原值、正确显示限制原因，并避免无依据全部降级或重新启用 |

识别效果、匹配耗时、人工调整量和并发容量，应以代表性样本与现场规模建立验收基线，当前不虚构数值或准确率承诺。按少量用户、三个主要部门的实际场景设计，不为假想的大规模并发增加复杂组件；仍验证同时认领、同部门接手和保存冲突。用户数少不代表资料量或单文件规模小，文件处理与历史检索性能单独测量。

### 15.2 操作体验增强

- 提供集中的待处理视图，按本部门和当前任务筛选未认领、未填完、候选待选、来源变化及范围疑问。
- 当前回复、历史候选差异和原文支持就地对照，减少页面切换，并保持条件和限制可见。
- 支持连续处理下一条、批量认领和明确保存反馈；断线、保存失败及他人接手均清楚提示。
- 批量操作不绕过候选选择、答案一致性、认领权限及完成检查，不把提高操作速度解释为自动确认业务答案。

## 16. 首版明确不做

1. 多个部门共同编辑同一条验规答案。
2. 依靠 AI 自动决定历史资料的维护部门。
3. AI 自由生成新的验规答案或设备能力承诺。
4. 部门内部二次审批流程。
5. 下载编辑后重新上传并合并回复。
6. 任务填写中更换源文件并自动迁移回复。
7. 必填／选填字段配置：按所有选中的答案字段判断完整性。
8. PDF 原格式自动回填；本轮确认的是文档留存、查找与预览。

## 17. 后续详细设计待落实事项

这些事项不推翻已确认业务规则，也不视为已具备的能力：

- 最终 JSON 契约、字段标识、模板与内容版本关联方式，以及 API 和查询升级范围。
- 真实 Word／Excel 样本中的字段对应、合列分列及不能自动处理时的具体交互。
- 原文预览组件、转换方案、来源定位精度和受损文件处理边界。
- 被引用文件的主动物理清理条件、临时文件清理实现及存储容量；正式原件和结果长期留存、同公司预览下载共享范围已确认。
- 独立全库问答入口是否纳入首批；即使纳入，也不能越过已确认的正式回复生成限制。
- 使用人数不多、主要为机构／电控／智能化三个部门已确认；历史记录数量、常见及最大文件大小、条目数通过现有数据和样本统计，具体响应时间及同时使用场景据此建立验收基线。
- 一期迁移前的数据盘点、演练、核对方法和切换／回退方案。

正式开发前，以本稿为业务基线，结合代表性文件形成页面流程和技术方案，再检查是否存在与本稿不一致的行为。

## 18. 新增需求：历史资料与已填写验规文件对比

### 18.1 已确认的需求范围

- 用户上传需要检查的 Excel 或 Word 验规文件，以检查其填写内容是否有误。
- 对比参照来自历史资料库，由用户选择客户、制程、机型范围；支持沿用二期多来源范围选择能力。
- 本次需求不是指定两份历史文件进行位置差分，也不以某个固定历史文件作为唯一标准。
- 对比能力应纳入后续详细设计，与需求／答案字段组、历史候选、版本及原文溯源保持一致。

### 18.2 建议流程与边界，待详细设计细化

上传待检查文件 → AI 识别需求与现有答案字段组 → 核对识别范围 → 选择历史来源范围 → 按需求查找可参照历史条目 → 比较对应答案 → 展示差异与原文依据。

- 先对应业务条目，再比较答案；不能只按行号、列号或段落顺序判断内容是否填错。
- 自动检查以有权访问、范围适用且符合复用资格的历史资料为依据，记录实际参照的版本。
- 历史答案存在多个合理但不同候选时，展示候选差异，不任选最新一条作为唯一标准。
- 多字段答案默认对照同一份完整历史候选，不能从不同候选各取字段拼成一个“正确答案”。
- 结果需要区分：与参照一致、仅可确定的格式差异、答案内容不同、文件缺答、历史候选存在分歧、没有可靠历史依据，以及结构或对应关系尚不能确定。
- “与历史不同”不直接等于填写错误；“与历史一致”也不保证本次设备能力或业务承诺正确。界面显示实际对照范围和依据，由业务人员判断差异是否合理。
- 首版建议以只读检查报告为主，不自动覆盖待检查文件或修改历史库，不让 AI 生成正确答案。
- 报告建议显示原文件位置、当前要求与答案、历史候选原文、具体差异、部门、适用范围、版本及来源入口，并保存本次检查参照，避免库更新后报告含义变化。
- 仅归档、尚不能可靠结构化的文件不能显示为自动检查通过；保留原文预览和不能检查的原因。

### 18.3 现有能力与实现设计依据

当前 `FileComparePreviewRequest` 使用 `FileIdA`、`FileIdB`，现有文件对比要求两个文件同类型。Word 主要按段落序列比较，Excel 主要按 Sheet 与单元格位置比较。

新能力可复用文件上传、访问校验、解析、定位、差异展示及结果下载基础；需要新增资料库范围检索、业务条目对应、候选分歧处理和版本化检查结果，不能直接以现有位置差分结果判断业务答案正误。

本节新增需求范围已确认；对比报告分类、人工处理动作和是否允许后续修正回填仍属于详细设计内容，不默认改变现有“不自由生成答案”和“系统内填写”的原则。
