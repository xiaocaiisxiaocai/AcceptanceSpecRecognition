# 智能结构识别增强方案（收敛版）

## 结论

这不是一套全新的智能结构识别方案。

当前代码和已完成的 OpenSpec 变更已经覆盖了大部分基础能力，包括前置行扫描、多行表头、列映射规则、客户学习规则、结构健康检查、LLM 表头裁决、`SpecificationOnly` 识别和智能填充仅规格匹配。

后续真正需要讨论的增量只有两类：

1. 列映射规则未命中时，是否需要新增“语义召回”能力。
2. `SpecificationOnly` 是否要从“结构识别/智能填充能力”扩展到“数据导入入库能力”。

其中第 2 项涉及 API、数据模型、导入校验、查重和 Embedding 文本口径，必须单独走 OpenSpec。不能在普通方案文档里默认承诺。

本方案适用于【导入数据】和【智能填充】共用的智能结构识别阶段；但“识别出仅规格结构”不等于“数据导入可以缺项目入库”。当前仅规格能力已经可用于智能填充匹配，导入入库仍受现有必填字段约束。

## 现状对照

| 能力 | 当前状态 | 说明 |
| --- | --- | --- |
| 扫描前置行找表头 | 已有 | `HeaderDetectionScanRowLimit = 20` |
| 多行表头 | 已有 | `MaxHeaderRowCount = 6`，Excel/Word 解析支持 `HeaderRowCount` |
| 确定性列映射规则 | 已有 | `Equals / Contains / Regex` |
| 客户学习规则 | 已有 | 用户确认后沉淀客户级列映射规则 |
| 全局规则晋升 | 已有 | `GlobalRulePromotionCustomerThreshold = 2` |
| 结构健康检查 | 已有 | `DocumentStructureHealthCheck` |
| LLM 表头/结构裁决 | 已有 | `ILlmDocumentStructureAdjudicationService`，带预算和超时 |
| LLM 裁决后重提取 | 已有 | 合法结构会重新提取表格并重跑映射 |
| `SpecificationOnly` 结构标记 | 已有 | 结构识别、模板、确认卡均已有字段 |
| 智能填充仅规格匹配 | 已有 | `MatchingMode.SpecificationOnly`，由用户显式选择 |
| 数据导入缺项目入库 | 未成立 | 当前导入仍要求项目列/项目文本 |

## 问题边界

### 已有能力不再重复设计

以下内容只作为现状背景，不作为新增需求：

- 固定窗口扫描。
- 多行表头识别。
- LLM 按需结构裁决。
- 裁决预算和超时。
- 结构健康检查。
- `SpecificationOnly` 在结构识别和智能填充中的使用。

### 需要保留的真实问题

当前仍有两个真实缺口：

- 某些表头没有命中列映射规则，但业务上明显接近某个字段。
- 部分文档只有规格语义，是否要支持其进入历史规格库，目前边界不清。

## 增量 A：未命中列映射规则时的列语义召回

### 现状

`RuleBasedMappingStrategy` 已有两类召回：

- 规则关键词命中。
- Levenshtein 编辑距离近似。

但编辑距离只能处理字面相近的变体。它不能稳定解决无共享字面的语义映射，例如：

- `允收范围` -> `规格`
- `控制限` -> `规格`
- `检验结论` -> `验收`

这些例子不是简单字符串相似度能可靠解决的问题。

### 推荐路径

第一步先做数据统计，不直接新增识别层。

- 使用 `tools/SmartFillInsightReport` 或现有样本统计未命中表头 TopN。
- 统计每类未命中表头的出现次数、客户分布、最终人工映射字段。
- 区分“少量客户专用词”和“跨客户高频通用词”。

第二步优先补规则和学习。

- 客户专用词进入客户级列映射规则。
- 跨客户高频词进入全局列映射规则。
- 已有 `Equals / Contains / Regex` 和客户学习机制继续作为主路径。

第三步再判断是否需要 AI 召回。

只有当统计证明存在大量“规则无法覆盖但人工稳定映射”的表头时，才考虑新增 AI 召回。可选方向：

- LLM 只裁决列语义，不改变表头行。
- Embedding 只召回候选字段，不直接自动采用。

### 自动采用边界

未命中确定性规则、只靠语义召回得到的列，不得直接自动采用。

必须满足以下条件才可继续升级为可采用结构：

- 至少识别到规格列。
- 若要自动采用，必须有验收列。
- 重新执行结构健康检查。
- 没有重复列、越界列、数据区异常。
- 若存在多候选或低置信，进入人工确认。

## 增量 B：`SpecificationOnly` 的边界

### 当前已支持

当前系统已经支持：

- 结构识别结果标记 `IsSpecificationOnly`。
- 确认卡允许用户切换仅规格。
- 智能填充支持用户显式选择 `MatchingMode.SpecificationOnly`。
- 仅规格匹配存在多候选时降级人工确认。
- 文档只有规格语义时，结构识别可以识别为仅规格候选；智能填充在仅规格模式下可以按规格召回候选。

这些能力不需要重新设计。

### 当前未支持

数据导入仍要求项目列和规格列。

当前导入链路存在以下约束：

- Excel 导入校验要求 `ProjectColumn` 和 `SpecificationColumn` 必填。
- 规格写入服务要求 `Project` 非空。
- 历史规格库仍以 `项目 + 规格` 为主要查找键。

因此，不能直接声明“`规格 + 验收` 可以导入数据库并按仅规格模式处理”。

### 如果要支持缺项目导入

这属于实质行为变化，必须单独 OpenSpec。

需要明确：

- 项目字段为空时如何入库。
- 查重键从 `项目 + 规格` 如何扩展或退化。
- Embedding 文本使用 `规格` 还是占位项目 + 规格。
- 后续智能填充默认是否能命中这类数据。
- UI 如何提示“历史数据缺项目，匹配风险更高”。
- Word 和 Excel 两端是否同等支持。
- 导入预览、重复检测、执行历史如何展示。

在这些问题未定义前，`SpecificationOnly` 只能明确用于结构识别和智能填充匹配，不应默认扩展到导入入库。

## 建议实施顺序

### 阶段 1：统计和收敛

目标：证明是否真的需要新增语义召回。

任务：

- 统计未命中列映射规则的表头。
- 统计人工最终映射字段。
- 输出 TopN 未命中表头及客户分布。
- 判断哪些可通过规则补齐，哪些需要 AI。

验收：

- 有数据说明新增能力的必要性。
- 不新增运行时行为。

### 阶段 2：规则补齐

目标：用现有机制覆盖高频缺口。

任务：

- 补充全局列映射规则。
- 保留客户级学习规则优先。
- 补必要回归测试，避免宽泛规则误匹配。

验收：

- 高频未命中表头减少。
- 不引入新的自动采用误判。

### 阶段 3：AI 召回评估

目标：只在规则补齐不足时评估 AI。

候选方案：

- LLM 列语义裁决：适合低频复杂别名，成本较高。
- Embedding 字段召回：适合多同义表达，但需要定义字段向量库和阈值。
- 不新增 AI：若规则补齐已覆盖主要问题，则停止。

验收：

- 有明确阈值、调用预算、回退策略。
- AI 结果不能单独自动采用。

### 阶段 4：仅规格导入单独立项

只有当用户确认要让缺项目数据进入历史规格库时才启动。

该阶段必须创建 OpenSpec 变更，不能和列语义召回混在一起。

## OpenSpec 边界

无需 OpenSpec：

- 仅统计未命中表头。
- 仅补充列映射规则。
- 仅补充测试。
- 仅改文档说明。

需要 OpenSpec：

- 新增 LLM/Embedding 列语义召回。
- 改变 `/api/smart-config/recognize` 的输出契约。
- 允许缺项目导入入库。
- 改变导入必填字段。
- 改变历史规格查重键。
- 改变智能填充默认匹配模式。

## 测试重点

短期测试：

- 高频新增规则能命中目标字段。
- 宽泛规则不会误把说明行、标题行、数据行当表头。
- 只靠近似/语义召回的结果不会自动采用。
- `SpecificationOnly` 智能填充仍保持用户显式选择。

如果后续做缺项目导入，还需新增：

- Excel 缺项目导入。
- Word 缺项目导入。
- 缺项目数据查重。
- 缺项目数据 Embedding 缓存。
- 智能填充匹配缺项目历史数据。
- 执行历史和导入历史展示缺项目风险。

## 最终判断

当前最稳妥的做法不是新增一整层识别系统，而是先用数据证明问题规模。

建议先把方向收敛为：

1. 统计未命中表头。
2. 用现有列映射规则和客户学习机制补齐高频缺口。
3. 只有规则补齐不足时，再讨论 LLM 或 Embedding 列语义召回。
4. `SpecificationOnly` 导入能力单独立项，不和结构识别增强混做。
