# 单组织与菜单权限强制设计

## 目标
把当前“用户可挂多个组织并指定主组织”的实现收敛为“一个用户只能有一个组织”的系统规则，并在现有页面、按钮、API 权限之外补齐菜单权限，使左侧导航容器节点也能被角色独立控制。

## 设计结论
- 保留 `AuthUserOrgUnits` 关系表，但通过数据库唯一约束强制 `UserId` 只能对应一条有效组织关系。
- 历史多组织数据迁移时，优先保留 `IsPrimary = true` 的记录；如果没有唯一主组织，则按 `CreatedAt ASC, Id ASC` 保留第一条。
- 历史无组织用户在迁移时补到公司根组织，避免出现无组织上下文账号。
- 系统用户创建、编辑、查询接口统一改为 `orgUnitId` / `orgUnitName` 单值字段，不再暴露 `orgUnits[]`、`orgUnitIds[]`、`primaryOrgUnitId`。
- 权限模型从“页面、按钮、API”扩展为“菜单、页面、按钮、API”，顶层导航节点使用独立菜单权限码控制显隐。
- 菜单节点和页面节点分别做权限判断：菜单看 `menu:*`，页面看 `page:*`，按钮和接口维持现有规则。

## 影响范围
- 后端：系统用户 DTO、用户管理控制器、认证访问服务、数据范围服务、权限种子、权限类型枚举、路由权限接口
- 前端：系统用户 API、登录用户缓存、系统用户管理页、动态路由过滤、权限字典展示
- 数据库：`AuthUserOrgUnits` 历史数据清洗与唯一索引迁移、权限字典种子补充
- 测试：迁移、用户管理、登录权限上下文、菜单权限过滤、前端类型检查

## 关键决策
- 保留 `AuthUserOrgUnits` 表，不新增 `SystemUsers.OrgUnitId` 字段。
  - 原因：当前数据范围计算、种子初始化、查询加载均已围绕关系表实现，这次只做单组织收口，不值得推翻模型。
- 单组织必须由数据库唯一约束兜底，而不是只改接口。
  - 原因：否则历史导入、后台脚本或未来代码仍可能再次写出多组织脏数据。
- 历史数据按“主组织优先，否则最早记录优先”裁剪。
  - 原因：规则确定、可重复执行，且与现有“主组织”语义最接近。
- 历史无组织用户补到公司根组织。
  - 原因：根组织是当前系统里最稳定、最保守的默认组织上下文。
- 菜单权限只覆盖导航容器节点，不替代页面权限。
  - 原因：菜单是否显示和页面是否可访问是两个不同层次，拆开更清晰。

## 风险控制
- 单组织迁移后，少量历史账号会失去额外协作组织范围。
  - 控制：这是业务规则要求的纠偏；迁移规则固定且可审计。
- 数据范围服务目前显式依赖“主组织”概念。
  - 控制：改为直接读取唯一组织关系，移除 `IsPrimary` 运行时语义，避免双重概念并存。
- 菜单权限加入后，已有角色若未补齐菜单权限，可能出现“登录后菜单为空”的假故障。
  - 控制：种子初始化时为 `admin` 补齐全部菜单权限，为 `common` 补齐最小业务可见菜单。

## 实施边界
- 本次不调整组织树模型本身，仍保留公司/事业部/部门/课别层级与跳级能力。
- 本次不改变数据范围类型枚举，仅把“主组织及子树”解释为“当前用户唯一组织及其子树”。
- 本次不引入长期兼容字段，不保留 `primaryOrgUnitId` / `orgUnitIds` 的双写方案。
