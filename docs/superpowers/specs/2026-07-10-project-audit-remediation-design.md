# 全仓深度审核问题分批治理设计

## 1. 背景

`docs/项目深度审核与优化建议-2026-07-10.md` 在提交 `844b782` 基线上确认了 23 项开放问题：P0 1 项、P1 6 项、P2 12 项、P3 4 项。问题横跨仓库资产、功能正确性、工程门禁、运行时资源、Application 架构边界、前端质量和文档治理，不能作为一个无边界改动一次完成。

用户已确认：

- 采用风险优先、分批实施方式处理全部 23 项。
- 每批独立验证并创建本地提交，不推送远端。
- `output/` 只解除 Git 跟踪并保留本地文件，暂不重写分支历史。
- 真实业务样本解除跟踪并保留本地文件，仓库改用合成夹具。
- Production 不开放 Swagger，部署验收改用健康检查。
- 仅归档已经进入 `main`、可视为实际部署的 OpenSpec 变更。
- 批准新增 `@playwright/test`、将 Docker Node 20 统一到 Node 22，并固定当前浮动 NuGet 版本。

## 2. 目标

1. 消除报告中的 23 项开放问题，或对必须依赖外部事实的项目形成可验证、诚实的收口状态。
2. 优先处理敏感资产和用户可见功能缺陷，再处理资源、架构和维护性问题。
3. 保持现有 API 路由、数据库结构和主要业务行为兼容。
4. 每个批次都能独立测试、独立提交、独立回退。
5. 用测试、CI 和 OpenSpec 固定修复结果，避免同类问题再次进入仓库。

## 3. 非目标

- 不在本轮重写已发布 Git 历史。
- 不读取、展示或加工浏览器 Cookie、登录数据库和真实业务样本内容。
- 不把当前内网认证立即改造成互联网 Cookie/CSRF 架构。
- 不进行数据库 Schema 变更。
- 不改变页面视觉语言、主要交互流程或 API 路由。
- 不为了降低行数机械拆分文件，不引入与现有问题无关的抽象。
- 不归档仅存在于当前功能分支、尚未进入 `main` 的 OpenSpec 变更。

## 4. 方案选择

### 4.1 采用方案

采用“风险优先分批治理”：先仓库和功能，再门禁和运行可靠性，随后处理架构与前端，最后统一文档和归档。

### 4.2 未采用方案

- **按前后端子系统推进**：会使 P0/P1 被低优先级重构拖延。
- **一次性全量重构**：改动面过大，无法形成可靠的回归、审查和回退边界。

## 5. 总体设计原则

### 5.1 兼容性

- API 路径、请求字段和响应语义保持兼容。
- 分页修复只补齐数据，不改变现有筛选语义。
- 异常处理增强可诊断性，但不把合法空表改成错误。
- 架构迁移先移动物理所有权，再改变依赖注入和调用方，避免同时重写业务逻辑。

### 5.2 资源治理

- 后台工作必须由宿主管理，支持取消、背压和可观测性。
- 文件系统与数据库不伪装成分布式事务，使用明确、幂等的补偿动作。
- keyed lock 回收必须保证同一 key 不会并存两把锁。
- 大文件优先流式传输，不能流式处理的同步文档库要限制并发并在阶段间检查取消。

### 5.3 测试策略

- 缺陷先补能复现问题的测试，再修改实现。
- 结构守卫只用于架构边界，用户行为使用单元、集成或浏览器测试。
- 每批运行定向测试；批次里程碑运行全量后端、前端和 OpenSpec 验证。
- 真实 AI 继续 opt-in；真实 MySQL 使用 CI service container 做迁移和关键查询烟测。

## 6. 批次设计

### 6.1 批次 0：仓库敏感资产与配置治理

覆盖：P0-01、P1-01、P2-12。

#### 处理方式

1. 对 `output/` 执行仅索引移除，物理文件保留在本地；保持 `.gitignore` 的 `output/` 规则。
2. 对根目录本地业务样本执行仅索引移除，并增加覆盖该类文件的明确忽略规则。
3. 新增不包含客户信息的小型合成规格夹具，覆盖工具实际需要的字段和边界。
4. 将当前默认读取本地业务样本的工具改为默认合成夹具，同时保留显式输入路径。
5. 示例环境变量改用不可直接部署的占位值，数据库名改为稳定产品语义；共享环境必须显式覆盖。
6. 不执行 history rewrite；在文档中保留历史和会话失效待办。

#### 验收

- `git ls-files output` 无输出，本地 `output/` 仍存在。
- 三个真实样本不再被 Git 跟踪，本地文件仍存在。
- 工具使用合成夹具可运行，显式传入本地样本仍可运行。
- 报告和日志不出现真实样本内容或浏览器凭据内容。

### 6.2 批次 1：P1 功能正确性

覆盖：P1-02、P1-03、P1-05、P1-06。

#### 全分页选项

- 提供共享选项加载器，按后端实际 `pageSize <= 200` 遍历 `totalPages`。
- 支持 `AbortSignal` 或等价取消、最大页数保护、去重和稳定顺序。
- 智能填充、匹配配置、数据导入统一使用该入口。
- 增加超过 250 条客户、制程、机型的契约测试。

#### 删除和恢复错误

- 共享 helper 只识别 Element Plus 的 `cancel`、`close` 为主动取消。
- 网络、权限、5xx 和解析异常统一使用现有请求错误提取函数展示。
- 逐页替换已确认的单删、批删、恢复和重置路径。

#### 文档解析

- 合法空表继续返回空结果。
- 明确可降级的“不支持/无目标表”与“损坏/I/O/未知失败”分开表达。
- 失败日志只包含文件 ID、表索引、异常类型等诊断信息，不记录文档正文。
- API 返回项目现有异常中间件可处理的业务错误。

#### Production 文档

- 保持 Production 不启用 Swagger。
- Docker/IIS 文档统一使用健康检查端点作为部署验收。
- 不新增生产 Swagger 开关。

### 6.3 批次 2：CI、测试和构建门禁

覆盖：P2-01、P2-10、P2-11。

#### 前端只读门禁

- 先修正 Stylelint 对 Vue `v-bind()` 的配置误判并清零现有基线。
- 增加不修改文件的 `lint:check`、`format:check`、`stylelint:check`。
- CI 依次运行 lint、typecheck、test、build。

#### 后端质量门禁

- CI 显式启用 `TreatWarningsAsErrors=true`；仓库注释和实际配置保持一致。
- 启用 Coverlet 采集和报告，首轮仅记录趋势，不设置未经验证的覆盖率阈值。
- 增加 MySQL service container，执行空库迁移、应用启动和关键查询烟测。

#### 可复现构建

- 将浮动 NuGet 版本固定为当前已验证解析版本，不顺带升级 API。
- Docker、CI 和本地版本文件统一为 Node 22；固定 pnpm 基线。
- 审查 net8 下冗余 BCL 包引用，仅在编译和全量测试证明不需要时移除。

### 6.4 批次 3：运行时资源与文件一致性

覆盖：P2-03、P2-04、P2-05、P2-06。

该批次创建 OpenSpec 变更，描述后台任务、清理窗口、取消和故障行为。

#### 会话锁与清理

- 使用带引用计数的 keyed lock，最后使用者离开后安全回收。
- 增加可取消的 `BackgroundService` 定时清理 session/artifact manifest 和过期文件。
- 业务请求保留轻量兜底，但不依赖后续流量才能清理。

#### 文件一致性

- 原子写入临时路径始终在 `finally` 中做幂等删除。
- 文件落盘成功、数据库保存失败时删除目标文件并记录补偿结果。
- 补偿删除失败不覆盖原始异常，但必须可监控。

#### Embedding 预热

- 导入成功只向有界 Channel 投递一次预热信号。
- Hosted worker 合并重复信号，串行调用 manager，响应宿主停止令牌。
- 暴露最近开始、成功和失败日志，不创建无上限 `Task.Run`。

#### 内存与取消

- 下载接口改为流式返回并传递请求取消令牌。
- parser/writer 接口贯穿取消令牌；同步库内部不能强制取消时，在昂贵阶段前后检查取消。
- 对文档处理增加共享并发限制，默认值可配置。

### 6.5 批次 4：Application 边界与大型文件

覆盖：P1-04、P2-02。

该批次创建独立 OpenSpec 架构变更。

#### 迁移顺序

1. 将通过 `Compile Include/Link` 编译的 DTO 移至 `Application/Contracts`。
2. 将 provider adapter 移至真实 Application/Data/基础设施所有权位置。
3. 扩展架构测试，扫描所有控制器、中间件和 `.csproj` 源码链接。
4. 按控制器模块移除 `IUnitOfWork`，先迁移低耦合 CRUD/查询，再迁移文件和 AI 编排。
5. 将跨资源工作流从 `Api/Services` 下沉到 Application；Api 仅保留协议适配和宿主组件。

#### 大型文件拆分

- `AiServicesController`：拆为查询、命令、连接探测 Application 用例。
- `SmartConfigurationAppService`：拆识别编排、召回、融合和预算策略。
- `MatchingDtos`：按 API 契约域拆文件，不改变类型名和 JSON 契约。
- `useDataImportPage`：拆页面状态、目标加载、步骤编排和请求动作。
- 大型测试按场景域拆分，共享 fixture，不复制测试基础设施。

### 6.6 批次 5：前端认证、包体与浏览器测试

覆盖：P2-07、P2-08、P2-09。

该批次创建前端性能/验证 OpenSpec 变更。

#### 认证

- 本轮不改变 Cookie/localStorage 协议。
- 为并发 token 过期、刷新成功、刷新失败和单次跳转补测试。
- 部署文档明确当前内网边界和未来暴露面升级条件。

#### 包体

- 统计真实使用的 Element Plus 组件，只注册实际组件和插件。
- 优先使用现有工具链，不为按需导入额外增加依赖。
- 恢复有意义的 chunk warning 和 CI 预算，预算以当前构建基线和减量结果确定。
- 验证主要路由无组件或样式缺失。

#### 浏览器测试

- 新增 `@playwright/test` 和最小浏览器测试配置。
- 覆盖登录、超过 200 条范围选择、上传/导入、智能填充预览和下载。
- 默认使用合成数据和本地测试 API，不依赖真实 AI 或客户文件。
- CI 保存失败截图和 trace，不提交浏览器 profile。

### 6.7 批次 6：文档、产物和 OpenSpec 治理

覆盖：P3-01、P3-02、P3-03、P3-04。

- 统一 `openspec/project.md`、架构规格、架构图、README 和 CI 分支说明。
- Docker 文档补充 `api-backups`、离机备份、恢复和 `down -v` 风险。
- 重复 DOCX 只保留一个明确 fixture；其他文件的删除或移动在批次执行前再次确认。
- `docs/example.docx` 移到测试 fixture 所有权目录并更新引用。
- 通过 Git 祖先关系和 `main` 树确认部署状态，只归档已经进入 `main` 的 Complete 变更。
- 每次归档后运行 OpenSpec strict 全量校验。

## 7. OpenSpec 策略

以下行为需要先有提案并获得批准：

1. `harden-runtime-resource-lifecycle`：后台清理、预热队列、取消和文件补偿。
2. `refactor-application-boundaries`：Application 边界和架构守卫。
3. `optimize-frontend-delivery-validation`：包体预算和浏览器验证能力。

纯缺陷修复、文档修正、只读 CI 脚本和版本固定不单独创建行为规格。每个提案必须通过 `openspec validate <change-id> --strict` 后才能实施对应批次。

## 8. 提交与回退

- 每批至少一个主题提交；跨模块批次可按“规格/测试/实现/文档”拆成多个可独立审查提交。
- 不把格式化全仓、依赖升级和业务修改混入同一提交。
- 出现回归时只回退当前批次，不修改此前已验证批次。
- 不推送、不合并到 `main`；涉及远端 main 的操作继续遵守二次确认规则。

## 9. 完成定义

单项问题只有在以下条件同时满足时才能关闭：

1. 报告中的证据路径已被消除或有明确、可验证的边界说明。
2. 针对原始问题的测试或检查能够失败于旧实现、通过于新实现。
3. 相关定向测试通过。
4. 所属批次的全量门禁通过。
5. 文档、OpenSpec 和代码状态一致。
6. 已创建本地提交且工作树干净。

全部批次完成后执行：

- `dotnet test AcceptanceSpecSystem.sln -c Debug --no-restore`
- `dotnet build AcceptanceSpecSystem.sln -c Release --no-restore -p:TreatWarningsAsErrors=true`
- 前端 lint/typecheck/test/build
- Playwright 浏览器主流程
- MySQL 迁移烟测
- `openspec validate --all --strict --no-interactive`
- 仓库敏感路径、重复产物和 Git 跟踪状态检查

## 10. 已知限制与后续确认

- 旧 Git 提交仍包含浏览器 profile 和真实样本；历史重写不属于本轮已批准范围。
- 真实会话是否需要失效取决于 profile 是否使用过真实登录，必须由环境所有者确认。
- 依赖漏洞扫描需要联网授权，不能以本地静态检查代替。
- 重复 DOCX 的实际删除/移动属于不可逆文件操作，批次 6 开始前单独确认。
- 仅凭 OpenSpec `Complete` 状态不能判定已部署，必须以 `main` 中的实际代码和变更历史为准。
