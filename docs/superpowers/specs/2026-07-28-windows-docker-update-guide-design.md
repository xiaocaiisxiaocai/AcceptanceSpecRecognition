# Windows Docker 部署文档改造设计

## 目标

将 Windows Docker 的首次部署与后续生产更新统一维护在
`docs/DEPLOY-WINDOWS-DOCKER.md`，让操作者可以从固定入口完成更新，
同时避免删除数据卷、覆盖生产配置、跳过备份或绕过受控迁移。

## 文档结构

正式文档分为两条明确路径：

1. 首次部署：环境检查、克隆代码、创建本地配置、构建启动和健康验证。
2. 生产更新：原目录拉取、数据库离机备份、构建镜像、数据冲突预检、
   停止 Web/API、单实例受控迁移、依次启动 API/Web、历史数据抽查和回退。

生产更新使用本项目已经验证的 Windows PowerShell 命令，并特别说明：

- 始终在原 Compose 项目目录运行，不替换线上 `.env.docker`。
- MySQL 在更新期间保持运行，API 与 Web 分阶段停止和启动。
- 禁止 `docker compose down -v`、删除数据库容器或数据卷。
- SQL 备份在 MySQL 容器内生成，再复制到仓库外并校验 SHA256。
- PowerShell 出现 `>>` 代表命令被错误拆行；复杂 SQL 改用 MySQL 交互终端。
- 受控迁移只运行一个临时 API 容器，失败时不得启动新版本。
- `/health/ready` 和 Web `/` 是部署健康验证入口，`GET /login` 的 401
  不是前端健康失败。

## Agent 触发规则

项目 `AGENTS.md` 增加“Docker 部署与生产更新”规则。当用户表达“部署”、
“Docker 部署”、“生产更新”、“更新服务器”或同等意图时，助手必须：

1. 先完整读取 `docs/DEPLOY-WINDOWS-DOCKER.md`。
2. 在回复中给出该文档的项目内路径，并以文档为操作基线。
3. 默认只提供教程；未获得独立明确授权时，不执行生产、远端、容器或数据库写操作。
4. 部署步骤必须从 Git 拉取与版本核对开始，不得从构建或迁移中段开始。
5. 若现场配置与文档不同，先只读核对 Compose 文件、环境文件、服务名和持久化卷。

## 验证

本次为纯文档和规则修改，不执行生产部署或完整回归测试。提交前执行：

- Markdown 结构和代码块人工检查。
- 文档内路径、服务名、端口和命令与 `docker-compose.yml`、程序迁移参数交叉核对。
- `rg` 检查危险命令均带有明确禁止说明。
- `git diff --check` 检查格式问题。
