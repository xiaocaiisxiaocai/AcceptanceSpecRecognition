# 智能结构识别增强建议评估

分析日期：2026-07-06  
评估对象：Claude Code 提出的“更强大、更智能”结构识别增强方案  
结论：优先做“历史案例 Few-shot”和“低置信 LLM 表格裁决”，暂缓 Embedding、OCR、流式识别和 A/B 框架。

更新记录：2026-07-06 已完成第一阶段中的“历史模板案例注入 LLM Few-shot”。实现范围为复用 `DocumentTemplate` 查询同客户相似模板，并在 LLM 结构裁决请求中传入 `referenceCasesJson`；未新增数据库表，未改变识别 API 响应契约。

## 一、总体判断

Claude Code 的方向有一部分成立，但不能照单实现。

当前系统已经具备以下基础能力：

- 规则识别
- 客户模板匹配
- 客户域学习词
- 健康检查
- LLM 结构裁决
- 单文档 LLM 调用预算
- PromptTemplate 管理

因此增强应优先复用现有链路，避免另起一套复杂系统。

## 二、建议分级

| 建议 | 是否建议做 | 优先级 | 判断 |
|---|---:|---:|---|
| 历史成功案例 Few-shot | 建议做 | P0 | 当前已有 `DocumentTemplate`，可复用，不必新建大系统 |
| LLM 表格相关性增强 | 部分建议 | P0/P1 | 多表文档有价值，但只能作为低置信裁决，不能替代现有流程 |
| 主动学习/纠错反馈 | 建议做 | P1 | 业务闭环价值高，但要并入现有确认学习链路 |
| 视觉布局/合并表头理解 | 建议做 | P1 | 对复杂 Excel/Word 表头有实际价值，但实现成本中等 |
| Embedding 语义列映射 | 谨慎做 | P1 | 有价值，但应作为低置信 fallback，不能替代规则 |
| 跨格式知识迁移 | 暂缓 | P2 | 当前模板抽象不足，过早做会复杂化 |
| 多模态 OCR | 不建议近期做 | P3 | 外部依赖重，当前主链是 Word/Excel 结构化文档 |
| 流式识别 | 暂缓 | P3 | 主要改善体验，不直接提升识别准确率 |
| A/B 测试框架 | 暂缓 | P3 | 真实标注和埋点不足时收益有限 |

## 三、最值得做：历史案例 Few-shot

截图中的 `successful_structure_cases` 思路是对的，但不建议第一版新建表。

当前已有 `DocumentTemplate`，字段已经包含：

- `HeadersJson`
- `ProjectColumnIndex`
- `SpecificationColumnIndex`
- `AcceptanceColumnIndex`
- `RemarkColumnIndex`
- `HeaderRowIndex`
- `HeaderRowCount`
- `UsageCount`

第一版可以直接取同客户最近或高频模板，作为 LLM 结构裁决的参考案例注入 Prompt。

建议实现方式：

1. 在 `DocumentTemplateAppService` 增加查询同客户相似模板的方法。
2. 在 `SmartConfigurationAppService.TryFuseWithLlmStructureAsync` 构造 LLM 请求时传入相似案例。
3. 扩展 `LlmDocumentStructureAdjudicationRequest`，增加 `SimilarCasesJson` 或结构化案例列表。
4. 修改 `SmartConfigStructureRecognition` Prompt，增加“参考历史案例”区域。
5. 保持 LLM 只在健康检查失败时触发，不改变高置信规则路径。

预期收益：

- 不增加新学习入口。
- 不改现有主链。
- 只在低置信或结构不完整时触发。
- 能让 LLM 参考“该客户以前怎么认表头”。

## 四、第二优先：LLM 表格相关性裁决

当前 `DocumentIntelligenceService.ScoreTableRelevance()` 主要依赖：

- 表名
- 表头
- 预览文本
- 行列数

这对多表文档一般够用，但遇到“附件 A 验收清单”“会议纪要表”“变更履历表”混在一起时，可能不稳。

不建议直接替换现有打分函数。更合理的是：

1. 规则高置信时，不调用 LLM。
2. 多表且分数接近时，调用 LLM 做表格相关性裁决。
3. LLM 只返回候选表排序或是否相关，不直接覆盖列映射。
4. 继续受单文档 LLM 调用预算控制。

原因：

- 当前 `/smart-config/recognize` 返回扁平表格列表，不是只选择一个目标表。
- 直接替换表格打分会改变产品行为。
- LLM 应作为灰区裁决器，而不是主流程入口。

## 五、可做但放后：主动学习/纠错反馈

方向成立，但不能直接新增一条独立 `report-correction` 链路。

当前 `Confirm` 已经会保存模板和学习词，某种程度已经是学习入口。

真正缺的是：

- 用户确认前后的差异记录。
- 错误类型统计。
- 多次同类错误后自动提升规则。
- 区分客户专属规则和全局规则。

建议做法：

1. 在确认结构时记录 `beforeMapping` 和 `afterMapping`。
2. 保存差异摘要，不保存大体量原始文档。
3. 统计同客户同类错误次数。
4. 达到阈值后自动生成客户域 `ColumnMappingRule`。
5. 多客户共同出现后，再考虑提升为全局规则。

不要另开完全独立 API，避免出现两套学习入口。

## 六、可做但成本中等：视觉布局理解

复杂表头确实存在，例如：

```text
验收项目 | 技术参数
        | 标准值 | 实测结果
```

当前已经支持多行表头检测，但还没有真正理解父子表头关系。

该增强对 Excel 合并单元格、多层表头有价值，但涉及：

- 合并单元格展开
- 横向父级表头
- 多行表头扁平化
- Word 表格和 Excel 表格差异

建议放在 P1，不放 P0。

## 七、谨慎推进：Embedding 语义列映射

Embedding 方向不是错，但不适合第一批做。

原因：

- `設備商確認` 当前已经在验收列同义词中。
- `技术要求` 当前已经在规格列同义词中。
- 客户学习词已经接入规则主链。
- 短文本 Embedding 容易误判。
- 会引入 Embedding 服务依赖、向量缓存、模型版本和内网部署复杂度。

Embedding 真正适合处理灰区表头，例如：

- `供应商回复`
- `确认内容`
- `评议结论`
- `管控条件`

建议定位：

- 只作为低置信 fallback。
- 不替代规则识别。
- 不阻塞无 Embedding 服务的内网部署。

## 八、不建议近期做

### 1. 多模态 OCR

当前系统主链是 Word/Excel 结构化文档。

OCR 会引入：

- 外部服务或本地 OCR 部署
- 费用
- 识别准确率问题
- 隐私与数据边界问题
- 调试成本

除非客户确实大量上传扫描件，否则不建议近期做。

### 2. 流式识别

流式识别主要解决等待体验，不直接解决识别准确率。

当前更应该先提升结构裁决准确率。等识别链路稳定后，再做流式返回。

### 3. A/B 测试框架

没有足够真实标注样本时，A/B 测试容易变成形式。

当前更需要的是：

- 确认前后差异日志
- 小规模真实样本回放集
- 每次策略调整后的回归验证

## 九、推荐实施顺序

### 第一阶段：P0，1 到 2 周

1. 历史模板案例注入 LLM Few-shot。（已完成）
2. 多表低置信时 LLM 表格相关性裁决。

### 第二阶段：P1，2 到 4 周

3. 确认前后差异日志。
4. 从差异日志自动沉淀客户规则。
5. 多行/合并表头布局分析。

### 第三阶段：P2/P3，按真实需求推进

6. Embedding 灰区列映射 fallback。
7. 跨格式模板迁移。
8. 流式识别。
9. OCR。
10. A/B 测试框架。

## 十、最终结论

当前最应该增强的是：

1. 历史案例 Few-shot。
2. 低置信 LLM 表格相关性裁决。

这两项能复用现有基础设施，成本低，风险可控，对准确率提升直接。

暂时不建议优先做：

- Embedding 列映射
- OCR
- 流式识别
- A/B 测试框架

这些不是没有价值，而是当前收益/成本比不如前两项。
