# 智能填充功能审查报告

> 审查日期：2026-06-09
> 审查范围：匹配引擎核心 / LLM 流式裁决 / API 应用服务层 / 前端向导流程
> 审查方式：全代码只读审查 + 实测复现（深圳礼鼎 SL02 / 收放板机通用 / 通用投收板机，45 行语义改写样本）
> 审查结论：架构方向正确，降级安全（失败一律偏人工，不会误填），存在 3 个需优先处理的真实问题

---

## 一、总体结论

智能填充采用"四层确定性快路径 + Embedding 召回重排 + LLM 等价裁决"的分层匹配设计。整体评价：

- **方向正确**：把大量语义等价判断从 LLM 下沉为确定性规则（规范化层 + 冲突扫描器），并发限流、熔断、超时、重试隔离均较为扎实。
- **降级安全**：所有失败路径（Embedding 不可用除外）一律回退人工确认，不会误自动填充。
- **存在真实问题**：LLM 置信度未参与决策（误填风险）、CJK 单位正则误报、代码默认值与文档严重不一致。

---

## 二、直接解释实测中观察到的两个现象

### 现象 1：匹配预览出现"复核异常：LLM流式输出不可用，已转为人工确认"（45 行中 8 行）

**根因：Ollama 本地模型单行推理超时，并非改写质量或前端 bug。**

- 单行 LLM 超时默认 `LlmRowTimeoutSeconds = 120` 秒，重试 1 次（`MatchingModels.cs`）。
- 45 行约 25 行进入 LLM 裁决，4 并行下本地模型负载高，部分行单行推理 > 120s。
- 超时后后端写 `review.error` SSE 事件（`MatchingWorkflowSupportService.LlmPolicy.cs:86-94`），前端置 `item.llmReviewError` 并转人工（`useSmartFillLlmStream.ts`、`scoreDetail.formatters.ts:408-425`）。
- **与 `LlmMaxCallsPerBatch` 无关**：该上限实际默认 1000（非文档所写 20），且作用于同步匹配阶段，与流式复核是两个独立阶段。

错误字符串来源对照：

| 字符串 | 位置 | 触发条件 |
|---|---|---|
| LLM流式输出不可用，已转为人工确认 | `useSmartFillLlmStream.ts:205` | HTTP 请求失败（`!response.ok` 或 body 空） |
| LLM流式输出中断，已转为人工确认 | `useSmartFillLlmStream.ts:59` | SSE 读取中异常或流结束仍有 pending 行 |
| LLM复核未返回终态，已转为人工确认 | `scoreDetail.formatters.ts:422` | `stream.complete` 到达但该行仍 streaming（时序乱序） |
| LLM复核超时（>NNNs） | `MatchingWorkflowSupportService.LlmPolicy.cs:86` | 单行超时 |

### 现象 2：语义改写版总是"需要确认" —— 部分是引擎真实 bug

**"4边 vs 4边吸取"被判"存在未识别单位，禁止确定性自动通过"是确定的误报。**

- 单位 token 正则 `SpecCanonicalizer.cs:417` 末段 `[一-鿿]{1,4}` 把"数字后任意 1–4 个汉字"当作单位候选。
- "4边" 解析出单位 `边`，"4边吸取" 解析出 `边吸取`，两者集合不相等 → 报未识别单位冲突（`SemanticConflictScanner.cs:463-486`）。
- 豁免函数 `IsUnknownCjkUnitSeparatedByWhitespace`（`SpecCanonicalizer.cs:679`）只在数字与汉字间有空白时豁免，"4边吸取" 无空白逃不过。
- "边""边吸取" 根本不是量纲单位，是普通中文名词。此类中文名词都会误报。

## 三、问题清单（按优先级）

### 🔴 P1 — 优先处理

#### P1-1　LLM 置信度完全未参与决策（误填风险）

`IsHighConfidence`（`MatchingModels.cs:204`）：

```
Decision == AutoApply && (Score >= HighConfidenceThreshold || LlmEquivalence.Verdict == Equivalent)
```

LLM 自评的 `Confidence` 字段在 `LlmMatchingAssistService.cs:382` 被解析，但 `DetermineDecision` 与 `IsHighConfidence` 都只看 `Verdict==Equivalent`。**只要 LLM 判定等价，哪怕 confidence=0.01 也直接自动填充**，置信度自评形同虚设，是最实际的误填隐患。

**建议**：为 LLM Equivalent 增加 confidence 下限门槛，让"高置信自动 / 中置信可选 / 低置信转人工"三档真正生效。

#### P1-2　代码默认值与文档（CLAUDE.md）严重不一致

| 配置项 | 代码实际值 | 文档所写 | 位置 |
|---|---|---|---|
| LlmMaxCallsPerBatch | **1000** | 20 | `MatchingModels.cs:452`、`MatchingDtos.cs:107` |
| HighConfidenceThreshold | **0.95** | 0.98 | `MatchingModels.cs:16` |
| EnableLlmEquivalenceAdjudication | **true（开）** | 默认关闭 | `MatchingModels.cs:438` |

运维按文档判断会完全错判超时风险（1000 次 vs 20 次 LLM 调用是数量级差异）。

**建议**：以代码为准对齐文档，或确定权威值后统一。

#### P1-3　前端 LLM 流无超时兜底

若服务端不推 `stream.complete`，`llmStreaming` 永久为 true，"执行填充"按钮永久禁用（`SmartFillPreviewStep.vue:190`），只能刷新页面。`useSmartFillLlmStream.ts:150-251` 的 fetch 流无前端 deadline，仅依赖 AbortController 手动终止。

**建议**：前端增加 `AbortSignal.timeout()` 或定时器兜底，强制解除挂起的 `llmStreaming` 状态。

#### P1-4　CJK 单位正则误报（直接影响实测通过率）

见"现象 2"。`SpecCanonicalizer.cs:417` 正则缺少单位形态约束，把中文名词误当单位。

**建议**：对 CJK 单位候选引入白名单或形态校验（仅当汉字串能在 `_unitRoots`/SI 前缀分解中命中才视为单位 token），可消除整类中文名词误报，性价比最高。

## 四、架构层面改进建议

### 保留的优秀设计

- 语义判断从 LLM 下沉为确定性规则（规范化层 + 冲突扫描器）。
- 失败一律偏人工，不会误填。
- 并发限流（`LlmCallBudget` 原子计数）+ 熔断 + 超时 + 重试隔离。

### 可改进的架构问题

1. **决策逻辑分散在两处**：`SelectBestCandidateAsync` 三分支（`:799`）与 `DetermineDecision`（`:1448`）各自独立判断硬冲突/确定性自动通过/语义优先。同一套规则写两遍，硬冲突拦截、语义优先豁免散落 5 处，规则演进易漏改。**建议抽出单一 `DecisionPolicy` 对象集中所有阈值/门禁判断**。

2. **Severity 体系是字符串魔法值**（`"hard_conflict"`/`"warning"`/`"high"`），靠 `string.Equals` 散落比较。`identifier_conflict` 的 `"high"` 不在任何门禁集合内、只能靠 Warnings 列表间接拦截，重构易漏。**建议改为枚举 + 集中的"是否阻断自动通过"映射**。

3. **0.95 高置信阈值让 Embedding 快路径事实失效**：`CanDeterministicAutoApply` 要求 EmbeddingScore 与 FinalScore 同时 ≥0.95，极少触发，真正承担快路径的是字符串/规范化精确层，灰区几乎全压给 LLM。**建议用真实数据重新标定 0.90/0.95 两个阈值并对齐文档**。

## 五、修复优先级建议

优先修复 3 个 P1：

1. **P1-4 CJK 单位正则误报** —— 性价比最高，直接提升实测通过率，消除整类中文名词误判。
2. **P1-1 LLM 置信度门槛** —— 防误填，安全相关。
3. **P1-2 文档对齐代码** —— 防运维误判，低成本。

P1-3（前端流超时兜底）可与前端其他 P2 项一并处理。
