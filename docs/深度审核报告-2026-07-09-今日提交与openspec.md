## Codex 复核意见（2026-07-09）

我按当前仓库代码和 openspec 重新核对后，结论是：**报告中的核心高/中风险多数真实存在**。前 10 条中，除 #4 更准确地说是“预算上限导致的最坏超时风险”而非必现缺陷外，其余基本成立。后续低严重度项里有不少是维护性、测试质量或配置可发现性问题，不应和主路径功能 bug 混为同一优先级。

我认为需要优先回应和修复的点如下：

1. `null` 契约问题属实。后端 `int?` 会序列化为显式 `null`，前端类型写成 `?: number`，并用 `!== undefined` 判缺列；这会导致缺列门禁失效，Excel 路径还会把 `null` 折算为首列。
2. 仅规格首次导入主路径属实会被卡住。规则识别缺项目列时 `CalculateOverallConfidence` 直接返回 `0`，前端 `canSmartTableBeImported` 又要求 `confidence > 0`。
3. 模板复用污染链路可达。模板命中会返回 `Confidence = 1.0` 和空项目列；Excel 前端转换后项目列可能变首列；后端因项目列已有值而不走规格回填。
4. G5 错列抢占是有效风险。现有测试覆盖的是业务验收列表头在词表内的情形；当真实业务验收列表头未命中词表，而 `PSD_ACCEPTANCE / 最终验收通过` 存在时，当前规则和健康检查没有足够防线。
5. 语义召回端到端未闭环属实。后端返回 `semanticRecallSuggestions`，前端未声明、未展示；融合路径重建识别结果时也没有合并召回建议。
6. openspec 偏差属实。`user-interface` spec 要求提示“跨项目匹配风险”，当前前端只提示项目由规格补齐；`tasks.md` 4.3 已勾选但实现未达到。

- **证据链**：缓存键 `BuildStructureAdjudicationCacheKey` = 表头 + 已映射字段 + `HeaderRowIndex:HeaderRowCount:DataStartRowIndex`，**不含数据行数**；命中时 `CopyStructureCandidateForTable` 原样复制 `DataEndRowIndex`。而候选的 DataEndRowIndex 通常非空（规则候选在 `SmartConfigurationAppService.cs:470` 置为该表 `TotalRowCount - 1`，融合时 `DocumentStructureFusion.cs:116-118` 取 llm ?? rule）。下游 `NormalizeRowRange`（SmartConfigurationRecognizedTableFactory.cs:264-270）只做 `Math.Min(候选end, 当前表末行)` 的**越界夹紧，无法纠正偏小方向**。
- **失败场景**：同表头集合中**首个真正走裁决的表行数较少**（如文档先出现 30 行小表、后有同表头 50 行大表）：小表裁决结果 end=29 入缓存 → 大表命中缓存 → Math.Min(29, 49)=29 → 大表识别结果的数据范围止于第 29 行，**第 30–49 行不进预览、不进导入，静默丢失**。分页拆表"首页最长"的常见顺序恰好被夹紧掩护，但"小表在前"并不罕见。
- **测试为何没拦住**：新增的结构缓存测试用的是**同行数**的 3 张同构表，行数分歧场景无覆盖。
- **建议修复（一行）**：`CopyStructureCandidateForTable` 中不复制 `DataEndRowIndex`，置为 `null`（`FromCandidate` 的 `?? TotalRowCount - 1` 回退与 `NormalizeRowRange` 会按当前表正确重算）；并补一个"同表头、行数不同"的缓存命中测试断言各表 dataEndRowIndex 按自身行数计算。召回缓存无此问题（建议仅含列索引，与行数无关）。
- **建议在提交该批次前修复此项**；其余各项可按原样提交。

## Codex 继续处理 #4（2026-07-09）

本轮继续收口 #4，并同步修复 Claude 第二轮指出的结构裁决缓存行尾复用问题：

1. **新增识别级共享 LLM 总预算。** `SmartConfigurationOptions` 增加 `MaxLlmCallsPerRecognizeDocument=5`，`appsettings.json` 显式暴露该键；结构裁决与列语义召回都先共同扣减这个总预算，再扣各自通道预算。默认单次 recognize 最坏 LLM 等待从“结构 5 + 召回 5”收敛为总计 5 次，按当前 20s 超时约 100s，低于前端 120s 超时。
2. **保留通道预算的运维控制。** `MaxStructureAdjudicationCallsPerDocument` 与 `MaxColumnSemanticRecallCallsPerDocument` 仍生效，用于限制单通道占用；共享预算负责限制整单总等待。
3. **修复结构缓存 `DataEndRowIndex` 复用缺陷。** 缓存命中复制结构候选时不再复制 `DataEndRowIndex`，由当前表自身行数回退计算，避免“小表在前、大表在后”时静默截断长表数据。
4. **新增验证覆盖。** 后端新增共享预算测试，断言总预算为 1 时列召回与结构裁决合计只调用 1 次；新增同表头不同行数缓存命中测试，断言第二张长表的 `dataEndRowIndex` 按自身行数计算。前端运维守护测试同步检查新配置键。

剩余风险：若运维把单次 LLM 超时调到 25s 以上，5 次总预算仍可能超过 120s；若底层 LLM 客户端不尊重取消令牌，应用层超时也无法完全兜底。

## 确认的前 10 项发现（按严重度降序）

### 1.（高）null→首列：模板/融合路径的仅规格 Excel 静默污染主数据
- **位置**：`web/src/views/shared/smart-structure-recognition.ts:184`（toActualColumnNumber）
- **缺陷**：API 对缺失项目列返回显式 `null`（`int?` 序列化，未配 WhenWritingNull，测试已断言 JsonValueKind.Null），前端 TS 类型只声明 `number | undefined`，`toActualColumnNumber` 只判 `=== undefined`；JS 中 `usedStartColumn + null` 把 null 当 0，仅规格 Excel 表被静默赋 `projectColumn = 首列`。
- **失败链**：用户对仅规格 Excel 确认一次沉淀模板（confidence=1.0、projectColumnIndex=null）→ 下次上传同构文件 → `excelMapping.projectColumn` 被算成 1 → 请求带 `projectColumn=1 + isSpecificationOnly=true` → 后端 `ShouldBackfillProjectFromSpecification` 因 HasValue=true 不回填 → 首列（如序号 1,2,3）被当项目名写入主数据，污染"项目+规格"匹配键；预览页却显示项目=规格内容，与入库结果相反且无告警。纯规则路径被 confidence=0 挡住不可达，但模板（本功能"确认一次、模板复用"的主设计路径）与 Fused/LLM 路径完全可达。Word 路径不受影响。

### 2.（高）confidence=0 过滤：仅规格导入主路径整表被过滤，功能不可用
- **位置**：`web/src/views/data-import/dataImport.smartRecognition.ts:120`（canSmartTableBeImported）
- **缺陷**：门禁要求 `table.confidence > 0`，但规则识别的仅规格表（IsSpecificationOnlyCandidate 前提即缺项目列）在 `RuleBasedMappingStrategy.CalculateOverallConfidence`（:339-343）恒得 0 且全链路无人改写。
- **失败链**：上传无项目列的仅规格文档（首次导入无模板、LLM 结构裁决未配置/超时/失败的正常降级态）→ recognize 返回 `isSpecificationOnly=true + confidence=0` → 前端过滤提示"未识别到可导入表格"；用户在确认卡显式确认仅规格后 `replaceRecognizedTableWithConfirmRequest` 仍保留 confidence=0 再次被过滤，智能流程内功能不可用。前端夹具 `confidence: 0.98` 与后端替身 `Confidence=0.96 + ProjectColumn=null`（真实策略不可能产出的组合）掩盖了契约断裂。

### 3.（高）G5 守卫删除后"错列高分抢占"可直达 AutoApply
- **位置**：`src/AcceptanceSpecSystem.Core/Documents/Intelligence/Strategies/RuleBasedMappingStrategy.cs:154`
- **缺陷**：`caa691b` 删除 PSD 元数据列硬守卫后仅剩关键词覆盖度相对排名：元数据列 Contains 业务关键词得 0.935–0.957（'PSD_ACCEPTANCE / 最终验收通过'→0.935，裸 'PSD_ACCEPTANCE'→0.957），真实业务列表头为词表外新词时元数据列必赢；语义召回只查 `!HasValue`、LLM 裁决要求 `!CanAutoApply`，对"错列高分抢占"零防御。
- **失败链**：G5 变体表 `[PSD_ACCEPTANCE / 最终验收通过, 评议项目, 评议标准要求, 评审结论(词表外真验收列), 供应商说明]`：PSD 列以 0.935 赢下验收槽，总置信度 0.30×0.99+0.35×0.99+0.25×0.935+0.10×0.99≈0.98 ≥ 0.85 → 健康检查零 issue → AutoApply 错误结构，"是/否"元数据被当验收值导入。完整 13 列 G5 表会被歧义拦截降为 NeedConfirm（但错误预选保留），单诱饵列变体可完全绕过。现有 G5 测试只覆盖业务表头在词表内的情形。

### 4.（中）串行 LLM 最坏 200s > 前端 120s 超时：识别整单失败
- **位置**：`src/AcceptanceSpecSystem.Application/Services/SmartConfigurationAppService.cs:504`
- **缺陷**：列语义召回在逐表串行循环内新增 LLM 调用（复用 20s 裁决超时、无表头签名去重/合批），与结构裁决触发条件有交集（项目+规格已映射、缺验收），同表串行两次调用；预算默认召回 5 + 裁决 5，最坏 LLM 等待 5×20+5×20=200s（改动前 100s），而前端 axios 超时固定 120s 且未随本次变更调高。召回失败时 `GenerateWithFallbackAsync` 还会顺序打满所有已配置 LLM 服务（单次墙钟仍被 20s CTS 兜住）。

### 5.（中）null 缺列门禁全部失效：批量导入 400 惊吓 + Excel 静默首列

### 6.（中）融合路径静默丢弃语义召回建议，预算白耗、违反 api spec 场景
