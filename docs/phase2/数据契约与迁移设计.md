# 二期数据契约与迁移设计

日期：2026-09-21。状态：拟采用设计，未建表、迁移或变更运行配置。

关联：[总方案](../二期详细设计与实施方案-2026-09-21.md)；[业务确认稿](../二期需求讨论确认稿-2026-09-21.md)。

## 1. 数据设计原则

1. 需求与答案统一 JSON，保留字段边界及原文；JSON 不承担用户权限、认领或公司范围。
2. 记录身份、正文内容版本、源文件版本、模板版本、运行输入版本分别管理。
3. 当前正式正文以当前内容版本为准，不保留两套可独立编辑的四字段与 JSON 正文。
4. 自动采用或检查引用具体历史内容版本及来源快照，不引用会随时间变化的“当前记录”。
5. 原件不可变；预览与正式结果均为派生资产。原件上传去重不能合并逻辑权限。
6. 搜索文本和向量是可重建投影，不能在删除／停用后继续作为有效答案返回。

## 2. 拟定实体与关系

实体名用于表达职责，实际迁移时优先扩展现有稳定身份，避免无必要更换历史 ID。

| 实体 | 关键数据及职责 |
| --- | --- |
| `DocumentRecord` | 逻辑文档，CompanyId、OwnerOrgUnitId、名称、用途、分类、当前文档版本、可见／删除状态 |
| `DocumentVersion` | DocumentRecordId、版本号、FileAssetId、原始文件名、类型、上传人、时间；记录不可变 |
| `FileAsset` | 公司隔离的文件资产、相对路径、内容哈希、大小、类型、资产种类及保留状态；原件不可覆盖 |
| `DocumentDerivative` | 原件版本＋预览处理版本，对应预览资产、状态、错误、尝试次数；可重建 |
| `MappingTemplateVersion` | 模板归属、不可变版本、表头特征、字段与区域定义、发布状态 |
| `DocumentMappingVersion` | 某文件版本的实际映射快照，区域、字段、源位置、确认人与范围覆盖；不依赖模板当前值 |
| `ImportSession` | 文件／映射版本、上传部门、数据范围、识别与清洗进度、重复决议、导入幂等记录 |
| `AcceptanceSpec` | 复用现有记录 ID、公司／部门、当前内容版本指针、有效性、引用计数及并发版本 |
| `AcceptanceSpecContentVersion` | 复用现有记录／版本身份，增加 ContentJson、SchemaVersion、内容指纹、适用信息及复用资格 |
| `SpecVersionSource` | 内容版本与原文或任务结果的来源关联，字段定位、来源类别、关联时间；来源可多条 |
| `SpecSearchDocument` | 按内容版本构建的需求文本、可搜索属性、构造规则版本、索引状态及向量引用 |
| `ReplyTask` | 任务身份、公司、创建人与当前负责人、原始文档身份、当前工作版本／最后正式版本 |
| `ReplyTaskRevision` | 工作版本号、固定原件与映射、来源范围、状态、输入版本、正式快照及结果引用 |
| `ReplyTaskParticipant` | 任务参与部门及当前有效状态，参与增减事件；不作为历史署名的唯一来源 |
| `ReplyItem` | 任务版本内稳定条目、需求／答案 JSON、目标单元格集合、当前负责部门、工作状态、内容版本与来源核对标记 |
| `ReplyItemSearchScope` | 条目来源范围模式、实际范围组合、范围版本、所基于的任务默认范围版本及修改人 |
| `ReplyMatchRun` | 一次匹配的条目集合、各自有效范围快照、映射／答案输入版本、算法版本、运行完整性及候选快照 |
| `ReplyItemConfirmation` | 条目内容版本、结构版本、确认人／部门快照、已核对来源版本与状态 |
| `ReplyItemAdoption` | 每次采用的历史内容版本、字段映射、原答案快照及随后人工修改信息 |
| `ReplyResult` | 固定正式版本、结果资产、文件哈希、生成参数、确认快照；不可变 |
| `HistoryCheckRun` / `HistoryCheckItem` | 检查输入、范围及历史版本快照、运行完整性、条目对照结果与报告；详见检查设计 |
| `BackgroundJob` / `OperationReceipt` | 持久化异步执行、租约、取消、重试与幂等请求结果 |

不要求一次创建全部表。按总方案的阶段分批实现，表边界可在同等约束下简化。公司、部门、客户、制程、机型和时间保留普通查询字段及关系约束，不藏在可任意编辑的 JSON 中。

### 2.1 关键约束

- 每个内容版本在 `(AcceptanceSpecId, Version)` 下唯一；当前指针必须属于该记录。
- 每个文档版本在 `(DocumentRecordId, Version)` 下唯一。
- 每个任务版本、每个条目只允许一个当前负责部门。
- 实际写入单元格占用关系在同一任务版本内不能跨两个条目重叠；合并单元格按整体处理。
- 修改／完成使用期望版本，不以时间戳的大小猜测新旧。
- 技术并发令牌、业务内容版本和引用次数分别处理；增加引用次数不产生新正文版本，不让已采用答案触发无意义的来源待核对。
- 幂等键按公司、动作和目标主体隔离；同键不同输入返回冲突，不能复用前次结果。
- 引用既有内容不授予修改来源权；历史署名采用快照，不能因用户或部门停用而丢失。
- 当前历史资料查询排除已删除／停用状态，但已授权的历史任务回放读取自己的采用快照，不能被主记录的活动过滤器遮掉。

## 3. 内容 JSON 契约

以下为正常新资料的示意，不是迁移时对原值执行格式化的命令：

```json
{
  "schemaVersion": 1,
  "definitionVersionId": "mapping-version-example",
  "requirements": [
    {
      "fieldId": "f-project",
      "label": "项目",
      "sourceHeader": "检验项目",
      "semanticHint": "subject",
      "value": "定位精度"
    },
    {
      "fieldId": "f-specification",
      "label": "技术要求",
      "sourceHeader": "技术要求",
      "semanticHint": "requirement",
      "value": "重复定位误差不超过规定范围"
    }
  ],
  "answers": [
    {
      "fieldId": "f-response",
      "label": "供方回复",
      "sourceHeader": "供方能力",
      "semanticHint": "response",
      "value": "按约定方案实现"
    },
    {
      "fieldId": "f-note",
      "label": "补充说明",
      "sourceHeader": "说明",
      "semanticHint": "note",
      "value": null
    }
  ],
  "context": [
    { "fieldId": "f-section", "label": "章节", "value": "输送机构" }
  ]
}
```

### 3.1 校验和兼容

- `schemaVersion` 表示技术格式版本，与业务内容版本分开。
- 字段 ID 在所属定义中稳定且唯一，改标签不随意换 ID；不同模板的字段 ID 不自动表示语义相同。
- 数组顺序就是确认过的组合顺序，不能依赖 JSON 对象属性顺序。
- `value` 首版采用可为空的原文字符串；数字、单位、换行、否定词和限定条件不在存储时改写。数值解析结果是派生证据。
- `sourceHeader` 只存有来源依据的原表头；旧字段迁移没有依据时为 null，不伪造表头名称。
- `semanticHint` 是识别与比较的辅助信息，可为空或未知，不重新限制成固定四字段。
- JSON 不接受客户端伪造公司、维护部门、确认人、来源版本可用性等权限属性。
- 对字段数、长度、整体大小做显式校验并报具体错误，不静默截断正文。上限由样本和资源预算验证后确定。
- 未知结构版本拒绝按已知版本解释；未知新增字段遵循契约兼容策略，不直接丢弃。
- MySQL 使用原生 JSON 存储正文；应用层使用明确 DTO 序列化和校验。EF/Pomelo 的映射及测试库差异在 P2 做契约试验，不假定动态 JSON 查询可自动翻译成高效 SQL。

### 3.2 一期映射

`Project`、`Specification` 映射到 `requirements`，`Acceptance`、`Remark` 映射到 `answers`，字段 ID 使用 `legacy.project` 等固定迁移标识。

迁移时不调用当前会 Trim／空串归 null／重置引用计数的业务更新函数。原始值、空值、空串和顺序逐项复制，源缺失信息单独标记。后续正常业务修改再按新版本规则处理。

四字段只是一种既有定义。新资料可以使用任意已确认的需求／答案字段组合，旧资料不必人为补齐成更多列。

## 4. 物理位置与字段绑定

源定位独立于显示列名和正文：

| 文件 | 定位信息 |
| --- | --- |
| Excel | 文件版本、Sheet 名与内部识别标识、区域 ID、行列坐标、合并范围、表头路径及映射版本 |
| Word | 文件版本、表格 ID／序号、行及单元格结构位置、必要段落范围、表头路径及映射版本 |
| 旧资料缺位置 | 保留明确的文件关联和缺失状态，不按文本猜出一个确定位置 |

任务条目 ID 在该任务版本内生成并稳定保存，不以“项目＋规格”或当前行号作为全局身份。行排序、分页、筛选不能改变条目 ID。

填入答案前使用 `AnswerBinding`：目标字段 ID、来源字段 ID 列表、规则 `Direct` 或 `Concatenate`、明确的分隔显示方式、映射版本。自动绑定必须对应同一份完整历史候选，不能跨候选各取一段。无法可靠对应时保持待人工处理。

合列只做已确认顺序的原文组合；拆列不能根据 AI 自由改写技术内容。目标已填字段与候选不一致时，只显示完整候选和差异。

回填从不可变原件复制派生文件，按映射定位写入目标。未选单元格、公式、客户要求、合并区域及非目标内容不随意改变。答案文本按普通内容写入，不因以特殊字符开头而执行为公式。目标本身为公式、受保护或不可写结构时明确报该位置不能写，不能将保存文件成功当作已正确回填。

## 5. 适用范围、状态与复用资格

### 5.1 范围与来源不混用

每份资料保留来源客户／制程／机型及业务适用信息。来源说明从哪里取得，适用性说明在哪些条件下可复用，不能由跨范围检索直接推导通用。

每个适用维度表达 `Specific`、`AnyConfirmed`、`Unknown`；`Specific` 必须关联有效 ID，`AnyConfirmed` 需要明确的维护确认，旧空值迁移为 `Unknown`。首版单条资料沿用现有范围组合，不要求给所有原文件增加多重范围归属。

查询采用多组范围的并集。例如 `(A,甲,X)` 或 `(B,乙,Y)`；同组内维度取交集。查询界面选择“全部机型”只表示扩大检索，不能把资料中的 `Unknown` 改成通用。

### 5.2 条目级检索范围

任务版本保存默认范围及版本号，条目保存 `Inherit` 或 `Replace` 模式。部门在界面增减范围后，将最终完整组合保存为条目的覆盖范围，避免运行时用多个临时增减补丁猜测实际范围。

- 修改条目范围校验当前认领部门、权限和范围版本，不能变更别的部门条目。
- 使用默认范围时，也记录本次读取的默认范围版本；范围在提交到执行之间变化则要求刷新，不静默采用另一版。
- 每次 `ReplyMatchRun` 保存每条实际生效的范围列表、范围版本／指纹、文件与映射版本，以及候选和运行完整性。
- 任务默认范围更新不改写过去的运行；条目明确覆盖的范围也不随默认变化被覆盖。
- 重新匹配使用新的运行记录。旧候选和实际采用信息继续可审计，但只有仍满足当前采用校验的候选能进入答案。

### 5.3 状态分开保存

- 主记录有效性：活动、停用、删除、隔离，控制能否进入新的有效检索。
- 发布状态：草稿、正式，控制是否进入公司共享历史候选。
- 内容版本复用资格：`Reusable`、`ReferenceOnly`、`NeedsCleanup`，保存限制原因。
- 索引状态：待构建、就绪、失败，表示检索技术可用性，不代表业务答案是否有效。

最终自动带入条件取这些约束的交集，并检查本次候选适用性、字段映射、答案组一致性和来源完整性。不能用一个状态混淆“无效答案”和“索引尚未完成”。

## 6. 内容版本与来源

- `AcceptanceSpecContentVersion.ContentJson` 是正文事实来源，主记录保存当前版本指针。为列表和检索保留的摘要是派生投影，不允许独立编辑。
- 一次实质内容变更保存新版本、更新当前指针、维护引用规则和记录操作者；仅格式迁移不触发业务变更。
- 适用条件、复用资格和有效状态的变更必须有独立修订标识，来源核对不能只比较正文版本号。
- 每个内容版本可关联多个证据来源：不同文件中完全相同内容可追加来源关联。追加记录可审计，不把旧来源改指新文件。
- 任务采用时保存确切内容版本、原答案和实际展示的来源集合。以后新增证据来源不悄悄改变旧任务当时的依据。
- 人工修改标记为基于某个文件／旧版本／任务结果派生，不能将原文件当成修改后所有内容的逐字证明。
- 从任务结果入库时，以该任务已确认内容和正式结果作为直接来源，已有历史候选作为参考关联，避免把原本空白的客户文件冒充答案出处。
- 主记录停用、删除时移出新检索；有历史引用的正文和来源快照继续供授权回放。旧级联删除和全局活动过滤器必须复核，不能破坏已确认长期溯源规则。

## 7. 检索与缓存

### 7.1 共用查询流程

1. 校验公司权限、来源范围和本次用途。
2. 取当前正式、有效内容，区分可复用与仅参考。
3. 从已确认需求字段和必要上下文构建查询文本，不把目标答案混进去寻找“看起来正确”的历史记录。
4. 结合精确、规范化、关键词和语义检索召回候选，保持部门、适用条件和不同答案。
5. 核对对象、数值／单位／范围、否定及条件差异，生成可解释证据。
6. 返回候选版本、资格、映射建议、完整答案和检索完整性，不生成业务答案。

候选排序用于呈现，不作为唯一正确性证明。旧语义优先模式中允许 LLM 等价判定优先于硬冲突的分支需要调整：已确认关键条件冲突时，不因模型高分自动带入。需业务人工接受差异的内容仍留作参考。

### 7.2 投影与失效

正文提交和“待更新检索投影”事件在同一事务记录，后台有界更新。候选返回前再次核对主记录当前版本、有效性和权限，防止异步索引短暂滞后导致已删内容回流。

候选返回不能代替采用时的校验。候选携带内容版本、适用／资格／有效状态修订标识、来源修订及匹配运行 ID；自动带入和用户点击采用都通过同一用例，在短事务内核对这些标识、当前权限、条目答案版本及范围版本。

若候选展示后来源或权限已变化，拒绝旧候选的自动采用，返回可解释的冲突并刷新候选或引导人工参考；不能将失效候选悄悄升级为新的来源。采用成功后记录实际检查到的内容与状态修订，后续来源核对以此为依据。允许继续使用已保存旧答案的规则仅适用于已有采用快照的明确人工核对，不是新自动采用的绕过通道。

缓存键至少覆盖公司范围、内容／需求文本指纹、文本构造规则版本、模型身份与版本、用途。跨条目共享相同向量不等于把不同答案记录去重。

有记录等待索引、索引失败或检索服务失败时，结果明确表示未完整检索；检查报告不能把它计为“没有历史答案”或“全部一致”。支持用户主动使用手动查询与原文参考，不能静默降级后伪称 AI 检索完成。

投影升级并行重建，在验证完毕后切换有效版本；只因 JSON 外壳变化而正文构造完全未变时，可经验证复用已有向量，不盲目重算或盲目复用。

## 8. 文件保存与预览

使用逻辑文档与物理文件分离结构。相同公司内相同字节资产可做存储复用，但部门逻辑记录、版本、名称及权限关联分别保留。

| 上传情况 | 处理 |
| --- | --- |
| 同部门相同文件 | 提示已有逻辑文档，补充分类而非重复新增 |
| 同名不同内容 | 明确选择新文档或已有文档的新版本，不覆盖原件 |
| 不同部门相同文件 | 保留逻辑管理关系，物理去重不改变共享和维护权限 |
| 无法结构化 | 保留原件，进入文档资料，不伪造验规条目 |

预览状态独立为 `Queued/Processing/Ready/Failed`。上传成功立即可查；Word 转换失败不改变原件上传事实，也不触发删除。允许重试或下载。

PDF 预览和 Word 转 PDF／等效只读呈现通过受控访问端点提供。预览转换器作为适配接口，先验证现有能力和代表性样本，再决定组件；本稿不授权安装新依赖。扫描 PDF 首版至少支持预览和元数据检索，OCR 不作为默认已实现能力。

正式原件、正式结果、版本快照长期留存。临时资产需无运行租约、无正式引用才能清理；预览缓存允许重建。清理不能只按文件年龄或扩展名判断。

## 9. 一期升级策略

### 9.1 演练前盘点

只在明确的独立副本中操作。盘点范围至少包括：

- 全部历史主记录及活动／停用／删除／隔离状态，不能仅盘点活动查询结果；
- 当前正文、已有内容版本、引用事件和引用计数；
- WordFile 文件系统内容、数据库兼容二进制内容、实际可读性和哈希；
- 导入映射、仅规格补齐记录、执行回放、填充存档和文件来源关联；
- 公司／部门／客户／制程／机型关联完整性；
- 表头识别模板和规则版本；
- 正文、文件、版本和索引的数量、大小及缺失分布。

旧配置包含加密的 AI 服务凭据时，演练环境优先重新配置独立测试服务；不能复制一份数据库后把解密失败当成数据损坏，也不能盲目共用一期密钥和可写文件目录。

### 9.2 转换阶段

| 步骤 | 输入与动作 | 输出与门禁 |
| --- | --- | --- |
| M0 冻结盘点清单 | 记录源码、数据库一致性快照标识及对应文件清单哈希 | 可复查的演练基线，不写一期 |
| M1 扩充结构 | 新建 JSON／来源／映射结构，保留旧列 | 新版读适配可读取尚未转换记录 |
| M2 转换原件关联 | WordFile 内容转为不可变文件资产和文档版本，保留旧 ID 映射 | 实际字节、可读性、哈希与来源状态可核对 |
| M3 转换正文 | 每个旧记录和已存在版本按原值生成 JSON；不调用正常编辑业务逻辑 | ID、版本、计数、时间、值、空值和顺序不变 |
| M4 资格分类 | 确定性识别空白／占位、来源缺失、范围未知和有效状态 | 正常可复用／仅参考／待整理／原不可用分类报告 |
| M5 投影与索引 | 用新读取链路生成检索投影，按指纹验证或重建向量 | 不继续依赖旧四列构建不同的当前事实 |
| M6 功能验证 | 查询、版本比较恢复、历史检索、候选、对比、回填、溯源 | 数据保真之外，证明实际业务可用 |
| M7 切换演练 | 新接口统一使用新版内容，禁止旧写入口独立修改正文 | 单一正文写入来源，完整演练报告 |

转换任务记录实体类型、旧 ID／版本、源内容指纹、转换版本、结果 ID、状态和错误。重试同一输入不能生成重复内容版本；源数据变化时记录不一致，重新核对，不能跳过后声称全部完成。

### 9.3 资格分类规则

- 原本有效、正文完整、来源和适用范围明确：默认延续正常复用，不要求全部人工重新确认。
- 全空、只有占位、存在已知未解决问题：保留 JSON，进入待整理。
- 来源缺失或范围不明：保留 JSON，仅供参考，不能自动带入。
- 原不可用记录保持不可用。用户要求电控清理的错误条目不能在迁移中复活。
- 多个限制同时存在时保存全部原因，自动采用从严。

来源文件存在但没有定位，可保留可查文件关联，不编造行列。旧版本没有当时文件证据时，不能把当前 WordFileId 一律复制成该旧版本的确定来源。仅规格补齐有可靠记录时可显示派生标识；不能仅因项目等于规格就清洗旧正文。

### 9.4 写入切换与回退

开发副本演练与真实切换分别进行，不能把演练副本写回一期。

正式采用新结构前，需要明确旧系统写入边界：在受控切换窗口停写，或实现并验证增量追平方案；首版优先选择业务可接受的短停写窗口，不未经验证宣称零停机。真实操作另遵循项目维护流程和准确目标授权。

迁移运行保存共同基线：数据库快照／截止标识、文件清单中每个原件的身份和内容哈希，以及整个清单哈希。不能只用开始时间或文件名代表一致性。源系统有文件覆盖行为时，基线文件副本必须与数据库快照对应。

实际切换窗口中，在业务写入及会改动源数据、源文件的后台写入均受控后，固定最终截止点，执行最终差量扫描：补齐盘点后新增记录／版本／文件，重新核对变化、删除／停用与来源关系。所有源实体和文件都必须有迁移结果或明确的缺失处置记录，不能把已知旧文件缺失与本次漏复制混为一谈。

只有截止点后的写入被阻止、未迁移新增数为零、未覆盖变更数为零、未处理转换错误为零、文件差异均已核对，以及 M6 业务验证通过，才允许 M7 切换。具体数据库快照工具和停写操作在真实环境方案中明确；本稿不执行任何源系统停写。

迁移前验证可恢复的数据与文件备份。尚无二期新增写入时，可以按已验证副本恢复方案回退；出现扩展字段、部门任务及新正式结果后，旧程序不能完整表达这些内容，不能通过简单恢复旧库将新业务数据丢弃。此时保留二期数据，选择修复前进或专门设计的兼容恢复方案。

移除旧列是兼容期结束后的独立步骤，不作为首轮转换的前置条件。当前版本指针、索引和兼容读写路由应能证明不再依赖旧列后才移除。

## 10. 数据验收清单

| 类别 | 必须验证 |
| --- | --- |
| 保真 | 中文、繁体、符号、单位、换行、空串与 null、字段顺序逐项一致 |
| 身份 | 主记录、所有已有内容版本、引用事件的身份与关系不漂移 |
| 来源 | 不同版本来自不同文件、人工修改、多来源去重、文件缺失均正确呈现 |
| 模板 | 模板升级不影响旧导入及旧任务的字段解释 |
| 检索 | 多组范围、未知／通用区分、多个不同答案、索引滞后和错误均有正确结果 |
| 状态 | 已删除／隔离不复活，旧内容恢复创建新版本，完成快照不被后续更新覆盖 |
| 文件 | 原件不改写，正式结果可重复下载，缓存清理不伤及长期引用 |
| 并发 | 同条认领、保存、来源核对、正式生成的竞争有确定结果 |
| 演练 | 转换中断可恢复，重复转换不重复生成；旧库与文件副本可恢复 |

以上清单是后续实施门禁。本轮未运行数据迁移、未访问实际业务数据库，也未安装预览或检索依赖。

数据库迁移、JSON 类型、索引与事务竞争至少在独立 MySQL 环境演练；现有 SQLite 内存测试可用于定向逻辑回归，但不能替代目标数据库验证。
