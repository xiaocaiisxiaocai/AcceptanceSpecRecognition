# 历史答案对比检查详细设计

**状态**：二期详细设计草案  
**日期**：2026-09-21  
**上位方案**：[二期详细设计与实施方案](../二期详细设计与实施方案-2026-09-21.md)  
**需求基线**：[二期需求讨论确认稿](../二期需求讨论确认稿-2026-09-21.md)

## 1. 目标

本能力用于将一份已经填写的 Word／Excel 验规文件，与用户有权访问的历史验规资料库进行只读对比，帮助用户发现需要复核的差异、缺答、候选分歧及无法判断的区域。

系统输出的是“目标文件与历史依据之间的对比结果”，不是业务正确性裁决：

- “内容不同”不等于目标答案错误；
- “一致”不等于目标答案正确；
- “无可靠依据”不等于历史库中确定没有答案；
- 检索或解析失败不能伪装成“无候选”；
- AI 不生成、改写或补全验规答案；
- 检查过程不修改目标文件、历史资料或正式回复任务。

## 2. 范围

### 2.1 首版包含

- 上传一份 `.docx` 或 `.xlsx` 目标文件；
- 识别目标文件中的表格、处理区域、需求字段组和答案字段组；
- 保留 Sheet、表格、行列、单元格、段落及合并区域等原文位置；
- 选择多组客户／制程／机型历史来源范围；
- 按范围并集检索，并继续执行资料权限过滤；
- 先对齐需求条目，再按完整答案字段组对比；
- 保留多份合理但不同的历史候选，不自动选最新、不拼接候选；
- 展示原始值、格式差异、内容差异、候选来源及原文入口；
- 保存可重复查看的检查记录和报告快照；
- 首版生成可浏览的 HTML 报告，并提供明细 JSON 下载。

### 2.2 首版不包含

- 自动修复或写回目标文件；
- 将检查结果直接发布为历史答案；
- 创建、完成或替代正式回复任务；
- 部门认领、完成确认或部门内部审批；
- AI 自由生成答案、设备能力、参数或承诺；
- 从不同历史候选中自动抽取字段并组成新答案；
- 以现有“两文件物理差异”功能直接判定历史答案对错；
- 为报告引入文档资料库依赖。

## 3. 权限与参与边界

历史答案对比检查是独立的只读工具。用户具备检查权限，并对目标历史范围具有数据访问权限，即可发起检查；不要求先创建正式回复任务，也不要求部门认领条目。

建议拆分 `history-check:create`、`history-check:view`、`history-check:export` 和 `history-check:cancel` 权限，分别控制创建、查看、导出和取消。

历史候选查询、答案正文、原件预览、报告正文和下载继续执行当前调用者的数据访问规则。不得以检查创建者身份后台读取并向权限已撤销的用户返回冻结正文、原文或原件。

冻结报告字节保持不可变。每次列表、详情、站内报告和下载都重新检查当前权限；无权来源不返回正文、文件名、路径或其他受限元数据。若冻结 HTML／JSON 含有调用者当前无权查看的来源，拒绝完整下载；站内页面仅通过受控 API 展示仍有权的数据和拒绝原因，不在读取时改写原报告制品。

## 4. 页面流程

### 4.1 上传与范围选择

1. 用户进入“历史答案对比检查”。
2. 通过共用的 `/api/v2/documents` 上传一份已经填写的 Word 或 Excel 文件，取得 `documentVersionId`。
3. 系统校验文件类型、大小、内容结构和安全边界，计算文件哈希；检查模块不再保存另一套上传记录。
4. 用户添加一组或多组客户／制程／机型历史来源范围。
5. 系统显示每组范围的权限校验结果；无权范围不能提交。
6. 明确选择“全部”与资料本身“范围未知”分别展示，不互相替代。

### 4.2 结构识别与确认

1. 通过共用的 `/api/v2/document-versions/{id}/recognitions` 解析文件中的 Sheet、表格、段落、行列和合并区域。
2. AI 可以提出处理区域、表头、需求字段组、答案字段组和条目边界建议，并形成可确认的映射版本。
3. 页面展示原文件预览与识别结果，用户可以调整或排除区域。
4. 不可靠的映射必须显示疑问，不允许静默猜测。
5. 用户确认结构后，以 `documentVersionId` 和 `mappingVersionId` 创建检查；创建时冻结所引用的文档版本和映射版本。

结构确认只确认“如何读取本文件”，不确认答案正确，也不触发历史资料写入。

### 4.3 执行与查看

1. 创建成功后状态为 `Queued`。
2. 后台执行开始后状态为 `Running`。
3. 页面显示已处理条目数、总条目数、当前阶段及可取消状态。
4. 完成后进入 `Completed` 或 `CompletedWithGaps`。
5. 用户按结果维度、Sheet、表格、来源范围和候选状态筛选。
6. 用户可以查看目标原文位置、历史候选完整答案、来源版本和差异。
7. 用户可以打开 HTML 报告或下载明细 JSON。

## 5. 状态机

| 状态 | 含义 | 可进入状态 |
| --- | --- | --- |
| `Queued` | 已冻结输入，等待后台执行 | `Running`、`Cancelled`、`Failed` |
| `Running` | 正在解析、检索、对齐或生成报告 | `Completed`、`CompletedWithGaps`、`Failed`、`Cancelled` |
| `Completed` | 选定范围和纳入区域均已完成处理，报告可复现 | 终态 |
| `CompletedWithGaps` | 已生成有用报告，但存在明确的技术处理缺口 | 终态 |
| `Failed` | 无法形成可用报告，或冻结输入损坏 | 终态 |
| `Cancelled` | 用户取消，停止后续处理 | 终态 |

以下业务结果本身不导致 `CompletedWithGaps`：

- 无可靠历史依据；
- 多候选分歧；
- 需求条目无法可靠对应；
- 目标答案缺失。

这些是完整执行后可能得到的正常结果。只有检索失败、文件区域解析失败、资源限制导致未处理、快照不完整等技术原因，才属于执行缺口。

若所有历史范围均检索失败，不能生成“无候选”报告，应进入 `Failed`。若部分范围失败但其他范围完成，可进入 `CompletedWithGaps`，并逐范围标明失败原因。

## 6. 输入快照

检查一经创建，必须冻结目标文件二进制、名称、类型、大小和 SHA-256，以及纳入、排除和疑问区域、Sheet／表格／段落边界、需求与答案字段组、稳定字段标识和原文位置。

同时冻结用户选择的多组历史范围、创建时的权限查询条件、结构识别模型与提示模板、人工调整结果、条目对齐算法、答案比较算法和格式归一化版本。检查保存 `documentVersionId`、`mappingVersionId` 及对应内容哈希，不复制出可独立修改的第二份映射正文。

目标文件后续重新上传或修改，不改变已有检查。需要对新文件检查时创建新记录。

## 7. 原字段定位

每个识别字段至少保存检查内稳定 `fieldId`、字段角色、标签、文档类型、原始提取文本、显示文本、空值状态、识别来源、置信提示和人工调整记录。

Excel 字段另存 Sheet、表格、行列、单元格地址及合并区域主单元格；Word 字段另存表格、行列或段落序号。

定位信息必须指向目标文件快照，而不是当前磁盘中的同名文件。若只能定位到文件或表格，不能伪造精确单元格、行列或段落位置。

## 8. 历史范围与候选快照

每组历史范围单独保存客户、制程、机型选择，“全部”维度和“范围未知”状态，创建时权限过滤结果，以及检索开始、完成、失败和重试信息。

正式检索前，必须在一致性读取边界内生成 `HistoryCheckBaselineManifest`：列出当时范围内且有权访问的各记录当前生效正式内容版本 ID、复用资格、适用范围、内容哈希、来源版本、是否已建立可用索引，以及索引构造版本。已停用和被替代的旧版本不自动成为当前检查标准；仅供参考资料与可靠依据分别标记。Manifest 完成后才开始候选检索；候选快照是 Manifest 的命中子集。

多个范围按并集检索。同一内容版本被多个范围命中时只展示一次，但保存所有命中范围。不同来源、适用条件、内容版本或答案内容继续作为独立候选。

候选快照至少保存历史记录和内容版本、需求字段组原文、完整答案字段组原文、客户／制程／机型、适用条件、来源部门、可公开的来源摘要、原件版本、可获得的位置、内容哈希、候选资格、命中理由、取得时间和检索算法版本。

报告之后不得用历史库当前内容替换快照。来源被更新、停用或删除时，冻结报告仍记录当时比较事实；站内查看时由独立动态附层显示当前来源状态，下载报告只注明“数据截至时间”，不声称包含下载时状态。

## 9. 需求条目对齐

对比必须先对齐需求条目，再比较答案。不得直接按行号、单元格地址或段落序号把目标答案与历史答案配对。

建议采用以下顺序：

1. 用已确认的需求字段组形成目标条目；
2. 在选定范围和权限内检索历史记录；
3. 先执行稳定标识、确定性字段和精确文本匹配；
4. 再用规则归一化和语义相似度排列候选；
5. 用适用范围、条件及完整需求字段组排除明显不适用项；
6. 保留达到可靠门槛的全部候选，不强制压成一条；
7. 无法可靠判断时标记 `UnableToAlign`，不猜测对应关系。

AI 或向量相似度只用于识别和排序候选，不能把低置信候选提升为可靠依据，也不能生成缺失的需求或答案文字。

目标文件中重复出现同一需求时，每个原文位置分别产生检查项；报告可以提示重复，但不能擅自合并目标行。

## 10. 整组答案比较

每个已对齐条目按确认的完整答案字段组比较。字段以稳定标识或明确映射对应，不能因为列序相近就自动对应。

比较规则：

- 保留目标原始值和候选原始值；
- 原始值逐字段完全一致时，内容结果为 `ExactMatch`；
- 仅可确定的换行、首尾空白或布局空白不同，保守归一化后一致时为 `FormatDifference`；不能删除数值、标识符或独立条款内部有意义的空白，无法确认时按内容差异保留；
- 数字、单位、正负号、比较符、标点、大小写或正文文字变化均不得折叠成格式差异；
- 双方有值且不满足上述一致规则时为 `ContentDifferent`；
- 目标答案完整性独立记录为 `targetAnswerState`；候选存在与否不影响识别目标空白；
- 目标额外字段没有可靠历史映射时为 `NotCompared`，并标记字段无法对应；
- Excel 公式同时保存公式和可取得的显示值；缓存结果不可用时不猜测结果；
- Word 样式可作为展示差异，不作为答案语义一致的唯一依据。

`targetAnswerState` 取 `Complete`、`PartiallyMissing`、`Empty`、`Placeholder` 或 `UnableToRead`，同时保存 `missingTargetFieldIds` 和 `placeholderTargetFieldIds`。只有“待确认”等占位内容的字段另行标出，不能只因非空就计为已填；实质回复含相同字样时不按关键词误判。

缺答、占位和不可读取的具体字段标记独立保留，汇总状态不得隐藏其他问题。部分字段为空时仍保留完整字段组；没有历史候选时也必须显示目标缺答状态，不能把“无可靠依据”解释为已填完。系统不得从候选 A 取一个字段、候选 B 取另一个字段形成“标准答案”。

## 11. 正交结果模型

检查项分别记录需求对齐、历史依据、目标答案完整性和逐候选内容比较，不使用单一“正确／错误”状态。

### 11.1 对齐维度 `alignmentStatus`

- `Aligned`：目标需求条目已有可靠对应；
- `UnableToAlign`：无法可靠对应；
- `AmbiguousAlignment`：存在多个需求对应关系，无法安全收敛。

### 11.2 依据维度 `evidenceStatus`

- `SingleReliableCandidate`：只有一份可靠答案；
- `EquivalentCandidates`：多份候选按确定性原文比较完全一致，或仅有已定义的保守格式差异；不得由 LLM 推断“语义相同”；
- `CandidateConflict`：存在多份合理但不同的答案；
- `NoReliableBasis`：检索成功，但没有可靠答案；
- `RetrievalUnavailable`：检索未成功，不能判断是否有候选。

### 11.3 候选比较 `candidateComparisons`

每个保留候选分别产生一项 `candidateComparison`，包含候选记录与版本、逐字段差异及 `comparisonStatus`：`ExactMatch`、`FormatDifference`、`ContentDifferent` 或 `NotCompared`。无法进行候选内容比较时统一使用 `NotCompared`，不再设置第二个同义枚举。

顶层只保存 `alignmentStatus`、`evidenceStatus`、`targetAnswerState`、缺答字段和候选比较集合，不保存暗示唯一标准答案的 `selectedCandidateId` 或单一 `comparisonStatus`。即使只有一个可靠候选，也通过集合表达。

`CandidateConflict` 必须独立保留。即使目标答案与其中一份候选完全一致，结果仍为：

- `evidenceStatus = CandidateConflict`；
- 候选 X 的 `candidateComparison.comparisonStatus = ExactMatch`；
- 同时展示其他分歧候选及其条件。

报告不得把该组合简化成“答案一致”。

## 12. 检索失败与重试

每个范围检索都记录独立状态。超时、权限服务失败、数据库错误、索引不可用或取消均记录为技术结果，不能转成零命中。Manifest 内应参与检索但尚未按冻结索引构造版本建立索引的内容版本，标记为技术缺口；不得因此得出“无可靠依据”。

重试必须使用同一 Manifest、同一内容版本和同一索引构造版本，不得混入历史库最新版本。若权限变严，只能从 Manifest 中排除当前无权项；权限扩大也不追加新版本，应创建新检查才能使用扩大后的基准。

同一执行步骤使用幂等键，重复投递不能重复创建检查项、候选快照或报告版本。

## 13. 数据对象建议

检查聚合统一命名为 `HistoryCheckRun`。按职责保存目标、映射、范围、`HistoryCheckBaselineManifest`、候选快照、`HistoryCheckItem`、候选比较、报告制品和审计事件。上述快照可以使用受版本保护的 JSON 或关系表，复用既有 DocumentVersion 和 DocumentMappingVersion，不要求一项职责新建一张表。

大字段使用 JSON 时仍应保留结构版本号。检查状态、创建人、权限归属、时间、文件哈希和报告版本保留结构化列，便于约束和查询。

## 14. API 草案

检查 API 统一前缀为 `/api/v2/history-checks`；文档上传与识别复用主方案接口。

| 方法与路径 | 用途 |
| --- | --- |
| `POST /api/v2/documents` | 共用接口：上传目标文件并创建文档版本 |
| `POST /api/v2/document-versions/{id}/recognitions` | 共用接口：识别结构并形成可确认的映射版本 |
| `POST /api/v2/history-checks` | 引用 `documentVersionId`、`mappingVersionId` 和多组范围，冻结输入并创建 `Queued` 检查 |
| `GET /` | 分页查询有权查看的检查记录 |
| `GET /{id}` | 获取状态、进度、缺口和报告摘要 |
| `GET /{id}/items` | 分页查询检查项及正交结果 |
| `GET /{id}/items/{itemId}` | 查看目标原文、全部候选、差异和来源 |
| `POST /{id}/cancel` | 取消 `Queued` 或 `Running` 检查 |
| `GET /{id}/report` | 查看冻结的 HTML 报告 |
| `GET /{id}/report.html` | 下载 HTML 报告 |
| `GET /{id}/details.json` | 下载机器可读的完整明细 |

创建接口要求 `Idempotency-Key`。识别请求不创建正式检查记录；只有用户确认映射和范围后，才以文档版本和映射版本创建 `HistoryCheckRun`。

## 15. 报告设计

首版报告格式采用以下设计选择，属于实现方案，不扩大为新的业务承诺：

- HTML：面向人工查看，可按 Sheet、结果维度和来源范围导航；
- JSON：面向审计、问题复核及后续工具读取，包含完整明细；
- 不首版生成 PDF、DOCX 或修改后的目标文件；
- 不依赖文档资料库，报告保存在检查制品自己的存储命名空间；
- HTML 和 JSON 共享同一报告数据快照和格式版本；
- 每个制品保存 SHA-256；调用者当前仍有完整权限时，重复下载取得同一内容；
- 报告页明确展示“差异不等于错误，一致不等于正确”。

HTML 对目标原文、历史原文、文件名、标签和错误信息执行上下文安全编码，不把文档内容当 HTML、脚本、模板或指令执行；不加载文件内宏、外链或活动内容。报告采用限制性内容安全策略，不嵌入密钥、访问令牌、绝对存储路径或连接信息。

冻结 HTML／JSON 是截至生成时间的不可变制品。站内页面的“当前来源状态”和权限提示属于独立动态附层；完整下载需对制品包含的来源执行当前权限检查，不能通过动态改写冻结字节伪装成原报告。

HTML 摘要至少包含：目标文件信息、历史范围、执行状态、技术缺口、各维度数量、候选分歧列表、无法对应列表和逐条差异。

JSON 至少包含：检查 ID、快照时间、算法版本、目标哈希、映射摘要、范围检索状态、检查项、全部候选、原始值、归一化结果、位置和来源版本。

## 16. 审计与生命周期

记录创建、开始、完成、失败、取消、重试、查看来源和导出行为；审计记录不保存凭据、绝对路径或超出用户权限的数据。目标、映射、候选和报告快照作为一组证据管理，删除检查不得影响历史原件、内容版本或正式任务。物理清理前确认没有报告或审计引用；过期且未创建检查的临时上传可清理，已创建检查的目标快照不再按临时文件处理。

## 17. 验收场景

1. **多范围并集**：选择三组客户／制程／机型，命中同一历史版本时报告只展示一次，并保存全部命中范围。
2. **权限过滤**：用户无权访问的历史资料不参与候选；报告生成后权限撤销时，创建者身份不能绕过当前权限，必要时拒绝完整下载。
3. **目标冻结**：创建检查后覆盖或重新上传同名文件，原检查结果和目标哈希不变。
4. **结构调整**：AI 识别错误时，用户调整答案字段组后再创建检查，报告按确认映射执行。
5. **需求先对齐**：目标文件插入行、改变列顺序或移动段落，不因物理位置变化产生整片“内容不同”。
6. **整组比较**：答案由多个字段组成时，逐字段显示差异，但整组候选保持完整，不跨候选拼接。
7. **候选分歧**：目标与候选 A 完全一致、与候选 B 不同，结果仍保留 `CandidateConflict` 并展示 A、B。
8. **格式差异**：仅换行和首尾空白变化时标记 `FormatDifference`；数字、单位或符号变化标记 `ContentDifferent`。
9. **缺答边界**：目标为空或部分为空时独立记录 `targetAnswerState` 和缺答字段；即使结果为 `NoReliableBasis + NotCompared` 也继续显示文件缺答。
10. **无法对应**：无法可靠识别需求条目或字段映射时标记无法对应，不由 AI 猜测。
11. **部分检索失败**：一个范围超时、其他范围完成时状态为 `CompletedWithGaps`，失败范围不显示为零候选。
12. **全部检索失败**：不能生成“历史库无答案”的结论，状态为 `Failed`。
13. **来源变更**：冻结报告记录生成时事实和截至时间；站内动态附层提示当前来源状态，不改写报告字节。
14. **只读保证**：执行、取消、重试和导出均不修改目标文件、历史资料或正式回复任务。
15. **报告复现**：相同检查的 HTML 与 JSON 使用相同快照，条目数量、候选版本和结果维度一致。
16. **基准复现**：重试只读取同一 Manifest；新增或更新的历史版本不混入旧检查，未索引版本形成明确技术缺口。
17. **候选级结果**：每个候选有独立比较结果，顶层不暗选候选；`EquivalentCandidates` 只能由确定性原文或保守格式规则得出。
18. **HTML 安全**：文档原文中的标签、脚本、链接或指令只作为编码文本展示，不执行且报告不包含密钥。

## 18. 实施权衡

- 现有文件对比模块的上传、安全读取、Word／Excel 解析、资源预算、位置 DTO 和制品下载能力可以复用。
- 现有文件对比按两个文件的段落顺序、Sheet 序号和单元格位置求差异，不能直接复用为历史资料库对目标文件的业务判断核心。
- 新模块应复用底层解析端口，新增“目标条目提取—历史检索—需求对齐—整组答案比较”编排，避免把库记录伪造成第二个文件。
- 保存候选快照会增加存储，但能保证历史资料变化后报告仍可解释和复现；首版选择可追溯性优先。
- HTML 加 JSON 比 PDF 更容易保留交互导航和完整结构化证据；若后续需要固定版式 PDF，应从冻结报告快照派生，不重新检索历史库。

## 19. 开发前门禁

- 统一 JSON 内容结构、稳定字段标识和答案字段组契约已经明确；
- 历史内容版本、复用资格、来源版本和权限查询具备可调用接口；
- 代表性 Word／Excel 样本覆盖多 Sheet、多表格、合并单元格、多行表头、部分缺答和多答案字段；
- 确认格式归一化规则不会吞掉数字、单位、符号或正文差异；
- 明确检查制品存储、保留期和物理清理规则；
- 用真实规模样本确定单文件条目数、候选量、执行时间和并发资源基线；
- 所有失败路径均能区分“无可靠依据”和“检索／处理未完成”。
